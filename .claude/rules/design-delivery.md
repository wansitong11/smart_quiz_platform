# 设计说明交付规范（design-delivery）

适用：任何「设计 / 方案 / 新能力 / 大改」的说明与 spec（含 `$to-spec` 产出）。
原则：正文按「开发对产品经理」的方式讲业务逻辑，关键逻辑把「怎么实现」融进同一段；完整签名/伪代码/全部分支放「附录」。

## 正文（给产品 / 给人看，含开发参考）

正文以业务为主，默认大白话。每个逻辑点按需写：

- 目的：这个逻辑解决什么。
- 触发：什么时机 / 输入会触发它。
- 规则与步骤：一步步讲清做什么，关键步骤顺带写「怎么做」。
- 结果：最后产出什么。
- 边界与异常：什么情况不算、失败 / 满 / 超时等会怎样。
- 可改点：想调整行为时，改哪条规则 / 哪个阈值。

正文的默认写法是「一个开发向另一个开发讲逻辑」：
先说清这条逻辑要解决什么、按什么顺序做、每步产出什么；需要落地时，用自然语言说明关键做法，
必要时才点一下对应的类/方法/配置作为路标，点到即止。

不要通篇堆项目内部的英文类名、方法名、字段名和错误码；读者不应该先记住这些名字才能看懂逻辑。
内部命名、精确签名、字段类型、分支条件、错误码映射放附录；正文只保留理解逻辑所必需的最小名称。
必要处可以加项目内代码标识符（类名/方法名/字段名/配置键/错误码）作辅助，但要服务于理解：
点一下即可，必要时用一句话说明它在流程里做什么，不要让名称本身变成阅读门槛。

判断标准：一个熟悉业务但没看过这段代码的开发，读完正文能复述逻辑、说出大致怎么实现；
要看到一堆英文名才能拼出逻辑，就说明正文写偏了。

验收：产品能复述流程、知道怎么改；开发能看出关键逻辑怎么实现，不用先翻附录。

## 附录（给 AI / 实现层）

附录需包含代码实现和描述，且必须自足：另一个模型只读附录、不看正文，就能完整实现、无需任何猜测。
每个正文逻辑点单独放附录，用编号与正文关联，写全下面内容：

- 入口与签名：Controller / 事件 / 调度的方法签名、参数与返回值类型。
- 数据：表 / 字段名与类型、配置键与默认值、状态取值与含义。
- 步骤映射：正文每步对应哪个方法、参数与返回值怎么流、调用顺序。
- 状态与分支：完整状态机 / 所有分支条件 / 边界与异常处理。
- 可改点映射：正文每个「可改点」对应哪个类 / 配置 / 常量。
- 缺失即补：缺接口、DDL、错误码、校验规则时直接写清，不允许「实现时再定」。

附录允许并鼓励类名 / 方法名 / 字段名 / 配置键 / 类型完整写出；目标是零猜测实现。
附录不全 = 还没到可实现阶段，补全再进实现。

附录除了代码实现，也要包含让人看懂的描述，不能只堆签名和代码。每个新增或修改模块在代码前先用几句话说明：
它负责什么、输入从哪里来、按什么顺序处理、产出或副作用是什么；涉及并发、重试、
冷却、幂等、事务、异常传播时，写清关键状态和失败路径。代码本身再对不易一眼看出的
分支和顺序加简短注释，重点解释「为什么这样做」，不要逐行翻译语法。

### 代码与讲解

- 每个较完整的代码块前，先写实现职责、关键输入输出、执行顺序和失败路径，不能只贴代码。
- 代码注释优先解释业务意图、状态变化、并发保护、条件更新和异常分支；简单赋值、Getter/Setter、
  POJO 和样板配置不要求逐行注释。
- 修改现有代码时，标出插入位置、修改前后行为差异和影响范围；关键片段加注释，不能只给一段
  没有上下文的 diff。
- 代码中的注释用于辅助理解，不能替代缺失的签名、默认值、状态分支、错误码和测试点。
- 不完整的示例必须明确标成「示意」并说明缺失部分；正式附录仍必须满足零猜测实现。

## 验收标准

- 正文过「PM 测试」：没看过代码的产品经理能看懂逻辑、知道怎么改。
- 正文过「开发参考测试」：关键逻辑的实现方式已融进描述，开发能看出大致做法，不用先翻附录。
- 附录过「实现可读测试」：读者能看懂关键代码为什么这样写、执行顺序和失败路径，不是只看到一堆可拷贝代码。
- 附录过「零猜测测试」：换一个模型只读附录，能直接写出可编译、可运行的实现，不用追问、不用补决策。

## 交付节奏

- 分 2–3 轮：正文结构 → 正文逻辑 + 附录映射 → 边界与失败模式；每轮用户确认再继续。
- 实现前用一句话复述「要做的到底是什么」，用户点头才动手。
- 优先 Usage-first：先给用例（README Quick Start），用户确认用法对，再展开内部结构。

## 展示形式与篇幅

- 对话框直接回复：只给正文（PM 风格）骨架 + 摘要；附录落盘 `docs/design/` 文档。
- 完整版正文 + 附录落盘文档；对话里只给摘要 + 路径。

## 语言约束

- 正文以具体业务名词与自然语言为主；必要处可用项目内代码标识符（类名/方法名/字段名/配置键/错误码）作辅助，点一下并说明它在流程里做什么，不堆标识符。
- 附录每个方法先讲「输入 → 做了什么 → 输出 → 副作用」，再用简短代码注释补充关键分支、顺序和原因；不要求逐行注释。
- 禁止：显然 / 直接 / 同理 / 如前述 / 封装了 XX 能力（必须说「X 调 Y 得到 Z」）。
- 附录涉及真实文件用 `模块/包` 路径或绝对路径。

## 示例（示意，以当前代码为准）

### 正文：错题本算分

- 目的：告诉学生这次练习答对的比例，用来决定要不要继续推送这道题。
- 触发：学生提交一份练习的答案后。
- 规则与步骤：统计总题数和答对题数，用 `score = round(correct * 100.0 / total)` 算出 0~100 的得分；10 题对 7 题 = 70 分。
- 结果：写回这次练习的得分；连续 3 次满分则把该题标为「已掌握」。
- 边界与异常：得分 0 或 100 都合法；无答题记录时不参与计分。
- 可改点：想改「几次答对算掌握」，改「连续满分次数」这个阈值。

### 附录：对应实现

- 入口：`EvaluateStreamConsumer.onMessage(...)`
- 得分：`score = (int) Math.round(correct * 100.0 / total)`，写回 `practice_answers.score`（0..100）
- 状态：连续 3 次 `score == 100` → `WrongQuestionStatus.MASTERED`
- 可改点映射：阈值抽到 `@ConfigurationProperties`，如 `app.wrong-book.mastery-streak=3`

这段实现负责在学生提交答案后计算本次得分，并根据连续满分次数推进错题的掌握状态。
输入是本次练习的答题记录，输出是写入数据库的分数和可能更新的状态；得分先计算完成，
状态只在得分有效且达到连续满分阈值时推进。

```java
// 入口：消费一次答题提交，完成计分并更新错题状态
public void onMessage(...) {
  // 后续写库和状态判断共用同一个得分，避免重复计算产生不一致
  int score = (int) Math.round(correct * 100.0 / total);

  // 只有满分才推进连续满分次数；其他分数按实际规则重置或保持不变
  if (score == 100) {
    // 达到配置中的连续满分阈值后，才标记为已掌握
    updateMasteryIfReachedThreshold(...);
  }
}
```

注释只解释计分结果为什么被复用、状态为什么只在满分时推进；具体签名、完整分支和阈值来源
仍需在上面的附录条目中写全。
