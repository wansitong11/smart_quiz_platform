# Redis Stream 采用单分发线程与有界 worker 并发

状态：accepted（2026-11-02）

项目原先每个 Redis Stream 消费者只有一条线程，重业务直接占住消费线程，导致单实例内任务串行。
决定继续把 Redis Stream 作为持久任务源，每个 Stream 固定 1 条分发线程，只负责读取和入队；
本地使用有界在途队列，多个 worker 出队后先原子领取，再执行原有业务方法，业务终态写入成功或
重投成功后按消息 ID ACK。worker 池由中心化 `StreamWorkerRegistry` 按消费者 key 创建，每个功能
保留独立线程数和队列容量配置。

## Considered Options

- 继续单线程消费：实现简单，但一个慢任务会阻塞同类后续任务，无法利用单实例并发。
- 直接开多条 claim 线程：实现较简单，但同一 JVM 内 pending 回收游标和消费节奏会互相干扰，
  且分发与业务执行仍耦合在消费线程里。
- 本地无界队列：能快速消费 Redis，但突发流量会把内存打满，无法形成背压。

## Consequences

- 分发线程不再执行重业务，消息可以并行进入 worker。
- ACK 从业务代码收口到基类，失败隔离以单条消息为边界。
- 业务内部线程池继续保留，外层消费并发与内层任务并发分别配置。
- 未完成任务在停机或崩溃时不 ACK，继续依赖 Redis Pending List 和现有自动回收机制。
- 识别等已经使用页级并行的消费者必须限制外层 worker 数，避免两层并发相乘突破 provider 配额。
