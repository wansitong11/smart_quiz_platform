## 一、这次实际发生了什么

用户新建“全部资料问答”会话 14，提问：**spring ai都要学习些什么呢**。
用户消息为 35，助手消息为 36，检索轨迹为 18。

数据库保存的回答末尾为：

```text
**出处**
- 《Spring_AI使用指南》（3 段）
- 《语文知识点》（2 段）
- 《小学数学知识点汇总（1）》（3 段）
```

正文介绍 Spring AI 的基础、ChatClient、Embedding、RAG 等内容；错误出处已经保存在这条助手消息里，
不是前端显示了另一个会话的链接。也不能因为正文看起来合理，就认为检索没有污染。

## 二、证据与原因

### 2.2 第一层：召回与保底不等于“确实能回答”

本问题按现有长度档位使用 topK=8、普通召回最低分 0.28，候选请求上限为 8×3=24。
跨资料规则先给候选资料各取最多两段，再按向量分补齐剩余名额。
向量相似只意味着文本存在一定关联，不保证包含 Spring AI 学习内容。
所以语文、数学只要进入候选池，就可能在保底和补齐阶段占据名额。

本次没有启用新增分数筛选：Java/YAML 默认 false，本地 `.env` 无 relevance 覆盖，
同一请求的 INFO 日志也没有开启筛选时必打的“RAG 相关性筛选”记录。
这与上一轮交付保留关闭的决定一致，不是用户忘开一个已经验证成功的功能。

但只打开它也不够：前两轮真实留出都出现过高分数学片段通过门槛的失败，见 `RAG检索相关性筛选-验证报告.md`。
本次未保存完整候选及各片段分数，不能倒推出五个无关片段的原分数、原名次，或保证某组阈值一定能修复这条请求。

### 2.3 第二层：所有直接命中被自动标为“出处”

工具化流程把组装后保留的直接命中交给收集器；回答结束后按资料 ID 聚合这些片段生成出处。
没有核对“最终回答是否使用了该片段”，也没有核对“原文能否支持答案中的某句话”。
即使模型只根据 Spring AI 作答，后端仍会把同时检索到的数学和语文列出来。

三个出处计数相加为八段，且零工具调用，能确认错误出处来自本轮预检索直接命中的汇总。
只隐藏两个链接无法去除已经进入模型上下文的无关原文；反之，筛掉无关原文也不自动证明剩余资料都被答案引用。
“检索相关性”和“答案出处真实性”是两道不同的判断。

## 三、推荐方案

目标：回答模型接收前先排除无关证据，同时保留数学跨块连续性及真正需要两份资料的问题。
首阶段尽量轻量，第二阶段仍逐字输出；引用只认本轮有效证据，不再自动汇总全部检索命中。
沿用现有查询服务、模型注册器、结构化输出和原文组装，不改切分、不迁移向量、不扩大 6000 token 预算。

### 3.1 当前采用：一次轻量复核，再流式回答

```text
授权范围内召回 → 现有选择、补邻与预算控制 → 准备带编号的证据单元
→ 第一次模型调用：只返回保留编号 → 后端校验并删去未保留单元
→ 第二次模型调用：用保留原文流式回答 → 按有效引用生成出处
```

轻量化放在任务、输入和输出三个方面，不靠任意截断正文：

- **任务只做取舍**：判断证据能否回答本问题或必要子问题，不写答案、不改写问题、不生成摘要、不输出长理由。
- **输入限于已准备给回答模型的原文**：不再把整篇文档、全部历史、全量 24 个候选再发送一次。
  沿用现有最终上下文不超过 6000 token 的正文预算，另外计入短提示词、问题和编号的开销，
  不能把 6000 误称为整个复核请求的总 token 上限。本次直接命中八段；其它问题仍按现有 topK 档位。
- **不拆断语义**：直接命中及已装入的必要同代邻居组成证据单元，复核和保留按单元处理，
  不把解释条件所在的邻居割掉，也不从每块只截几个关键词。重叠原文应去重，避免重复计费。
- **只看本轮问题**：有指代时使用已有流程解析的明确问题，不再附整段历史让复核模型猜测主题。
- **输出只要编号**：例如下面的短 JSON，不附正文或逐段解释。所有编号均为本轮局部标识，不信任模型自填资料名。

```json
{
  "keepIds": ["E1", "E3"]
}
```

例如 E1、E3 属于 Spring AI、E2 属于数学，复核仅返回 E1、E3，第二阶段便不接收 E2。
这些编号只是示例，不对应本次现场 UUID。模型看到的资料正文属于不可信数据，不能覆盖复核系统规则。
复核先使用已有配置中可用、支持短结构化输出的低价非思考模型；不能随意新建供应商、填写密钥，
也不硬编码某个尚未验证可用的模型。通过注册器取客户端，通过公共结构化入口解析和校验。

这个轻量选择有明确局限：复核只检查已经进入预算的证据，不重新搜索被前序选择或预算丢掉的原文。
因此不声称它同时修复了召回率、资料保底和预算分配的全部问题；这些仍由原有回归与新留出题分别检查。

### 3.2 第二次保持流式，不返回整包 JSON 答案

```text
第二次输入：复核通过的编号原文与问题
→ 正常流式回答，在正文引用对应编号 → 后端验证并汇总出处
```

不再要求第二次返回 answer + usedChunkIds 的完整 JSON，也不等待整包 JSON 才展示文字。
首阶段会增加开始回答前的等待，但开始回答后的逐字输出保持原有形式；不能宣传首字延迟完全不变。

检索命中、复核通过及答案引用分开记录。模型在流式正文中引用本轮证据编号，
后端只允许引用复核通过、且实际提供给回答模型的证据，再映射真实 UUID 和 kbId 汇总出处。
尚未通过复核或因预算没提供的原文不能借编号混入；已装入的必要邻居应有可追溯映射。
两份资料确实各有必要证据时都允许保留和引用，不设数学/语文资料名黑名单。
未知、跨会话和缺失编号不能回退成“所有命中都是出处”；具体流式编号格式及失败提示需在实现附录冻结。
合法编号不自动证明每句话都被原文支持，仍需真实答案核对，不等同于第三次独立模型审计。

### 3.3 调用、失败与费用边界

- 常规资料问答为一次短复核加一次回答生成，不再增加第三次“检查答案”的模型调用。
  首阶段不带工具、不写入 ChatMemory、不循环换词、不二次改写、不自动补搜，模型输出长度设短上限。
- 现有问题改写、必要工具往返及公共重试仍可能产生其它调用，不把整个会话请求宣传为严格只有两个 HTTP 请求。
  复核重试须由公共调用入口限制，不另写业务循环；超时上限、输出 token 上限和选用模型在正式设计中冻结并实测。
- 请求内同一明确问题、相同原文版本复用复核结果；工具又取得全新原文时仍需复核，不能为凑“两次”让新证据绕过闸门。
  不未经设计就增加跨用户缓存，避免权限、资料代次与隐私问题。
- keepIds=[] 是正常无证据，跳过资料回答生成，走现有无命中提示；不是为凑两次还要调用回答模型。
- 超时、结构化回包非法或未知编号不当成空数组，也不恢复全部候选；应返回明确复核失败提示，不生成看似已核验的出处。
- 同步、流式及工具路径共用复核和证据编号合同；LLM 调用保持事务外，计量、额度、限流沿用现有机制。
- 输入仍有真实阅读成本，少输出只降低输出开销，不能因此称复核近乎免费；记录首字等待、复核耗时、usage 与费用。

用户已决定采用轻量两阶段方向，本文据此更新；尚未冻结完整配置与接口合同，不在本轮讨论中修改业务实现。

### 3.4 其它选项

| 方法 | 取舍 |
| --- | --- |
| 暂时指定《Spring_AI使用指南》再问 | 可以立即规避其它资料，但不算全库模式修复 |
| 只取消跨资料保底 | 能减少弱结果被抬入，但无关片段可能本来就在高分名次中，不够完整 |
| 只调分数或减少 topK | 前两轮已暴露局限，也可能损失跨块证据，不继续盲调 |
| 单次完整 JSON 回答包 | 用户为保留现有流式体验决定不采用 |
| 专用 reranker | 本轮先用现有低价文字模型做短复核；后续按质量与耗时评估，现有 embedding 接口不等于重排接口 |
| 先按摘要选择一份资料 | 可能误伤双主题问题，不作为唯一闸门 |
| 隐藏链接、资料名黑名单或清库 | 掩盖问题或破坏正常使用，不采用 |

## 四、验收方法

1. 将这次原问题固定为开发回归样例，使用当前新资料代次，不再当作全新留出。
2. 执行前冻结新的技术、数学追问、语文和真实双资料题，标注必要证据与禁止来源。
3. 分别检查召回、待复核单元、keepIds、回答模型的实际上下文、引用编号与最终出处，并核对原文支持情况。
4. 本问题的 Spring AI 原文通过，数学与语文单元不进入回答模型上下文，也不进入答案引用和出处。
   复核模型看到无关单元属于预期，不把“进入复核输入”误报为“进入回答上下文”。
5. 数学四步原文及补邻不丢失；双资料问题两份必要原文同时保留。
6. 验证非法/缺失编号、模型失败、超时、工具追加和流式分片；失败不能偷偷把全部检索命中重新列为出处。
7. 分别记录复核阶段、回答阶段与整个请求的调用数、首字等待及费用；验证开始回答后仍逐字输出。
   正式实施按 T3 回归。本轮未改代码，没有重复跑无关编译/测试。
