# RAG 切分语义连续性设计稿

状态：**已实施并验证**。本稿围绕已讨论的短篇、结构简单资料，采用“章节路径回填 + 相邻片段回补”。已有知识库不批量迁移；摘要、假设问题、模型生成背景、复杂表格和 OCR 纠错不属于本轮。正文描述方案，附录是独立实施契约。

### 开发诊断

本地启动时可设置 `APP_AI_RAG_CONTEXT_DIAGNOSTICS_ENABLED=true`，重新发起问题后，在后端日志搜索 `RAG_CONTEXT_DIAGNOSTIC`。日志列出直接命中和相邻补入的片段 ID、资料 ID、序号、相似度、超预算跳过数、邻居读取错误数，以及实际拼接的资料上下文。直接命中与邻居都可能包含相同章节附近的内容，判断邻居回补须看 `neighbors`，不能仅看最终文本。该开关默认关闭，日志包含资料原文，排查结束应关闭并按需要清理诊断日志；不应在生产环境开启。诊断只记录开启后发生的请求，不能还原过去的请求。

当前仅 Markdown 标题产生章节路径；TXT 等格式即使有“第一章”也不会自动识别，需整理为 Markdown 并重新上传或重新向量化。全部资料检索按相似度召回后可能按资料配额保留多个来源，不保证每个来源都与问题相关；定位具体原因时需结合候选分数和配额，诊断上下文中的 `direct` 只反映最终保留的直接命中。

## 1. 目的与范围

上传资料后，系统把正文切成多个片段。条件和结论可能落在相邻片段，单独召回一块会漏掉限制；正文脱离标题后，“该比例”“上述申请”等指代也可能失去背景。

本轮采取两条互补规则：

1. 给每块 embedding 输入补上资料名和明确的章节路径，帮助检索理解主题；回答上下文也展示资料名和路径。
2. 直接命中一块后，按原文顺序补回同一资料、同次向量化中的相邻块，帮助模型同时看到条件、例外或指代对象。

Markdown 按明确标题识别章节；其他格式不猜测标题。文档解析、权限、现有问答工具、ChatMemory 和对象存储继续沿用。无需为每块生成摘要、问题或背景说明，也不引入新的模型调用。

本方案不能保证召回本身正确，也不能修复离命中块很远的指代、复杂表格的行列关系、原文错误、OCR 误识别或英文断词。资料缺少证据时仍应如实说明。

## 2. 上传和存储

### 2.1 从原文件到片段

上传后沿用现有异步流程：从 OSS 下载原文件并提取文本，识别 Markdown 标题，按章节分块，再生成向量。没有标题的正文仍保留；非 Markdown 文件作为无章节路径的正文处理。

每个章节按约 800 token 的目标分块，优先在换行和句末标点结束。所有块按顺序拼接必须还原该章节进入分块器的正文，不能静默丢掉短尾。单资料超过块数上限时任务失败，旧正式向量保持可用。

每次向量化生成一个新的父文档 ID，各块记录连续序号和总块数。标题路径、资料名也作为本次向量化的快照保存。

### 2.2 资料名、章节和正文如何进入向量

例如资料名“退款规范”、章节“订单系统 > 退款规则 > 特殊商品”、正文“申请后补充凭证。”，实际传给 embedding 模型的文本是：

```text
[资料：退款规范]
[章节：订单系统 > 退款规则 > 特殊商品]
申请后补充凭证。
```

模型返回数字向量。保存时，向量写入 `vector_store.embedding`，而 `vector_store.content` **只保存**“申请后补充凭证。”。资料名、章节路径和定位信息写入 `metadata`；前缀不写回正文。这样向量能利用背景，检索返回的仍是片段原文。

### 2.3 原文、OSS 和 metadata 分别做什么

| 内容 | 位置 | 作用 |
| --- | --- | --- |
| 用户上传的原文件 | OSS/RustFS | 下载、重新解析、重试或手动重新向量化 |
| 解析后的片段正文 | `vector_store.content` | 检索和构造回答上下文 |
| 向量 | `vector_store.embedding` | 相似度检索 |
| 资料及片段定位信息 | `vector_store.metadata` | 筛选来源、查找邻居、显示章节及诊断 |
| 向量化配置快照 | `knowledge_bases.vector_config` | 排查资料使用的切分策略 |

不新增正文表。OSS 保留原文件；向量表保存解析后的片段，二者并非同一份数据。正常问答直接读取向量表的正文和邻居，**不在每次提问时下载 OSS 原文件**。需要重新解析或重新向量化时才读取 OSS。

metadata 的核心字段是：`kb_id` 标识资料；`parent_document_id` 标识本次向量化代次；`chunk_index` 和 `total_chunks` 标识片段位置；`document_title` 和 `section_path` 保存背景快照；`chunk_strategy` 区分新旧策略。metadata 是定位和解释数据的附加信息，不代替正文，也不代替知识库权限校验。

## 3. 检索和回答

### 3.1 先授权，再找邻居

提问时先按当前用户、共享状态以及 ALL、CATEGORY 或 SELECTED 范围取得可访问且已向量化的资料 ID，再沿用现有向量检索。空授权范围直接返回，不向“空列表表示全库”的底层接口传空列表。

直接命中的片段再次校验所属资料。对新策略片段，系统批量查找同一 `kb_id`、同一 `parent_document_id` 下序号紧邻的前后块。默认前后各一块，可配置 0–2 块。旧片段缺少定位信息时保留直接命中，不猜测邻居。

邻居只用于补充上下文，不算新的直接检索命中。不存在的文首或文末邻居自然跳过；重新向量化期间旧代次邻居已被替换时，保留原直接命中，不混入新代次。

### 3.2 预算与顺序

直接命中按相关度优先、完整地装入上下文；邻居使用剩余预算。重复片段只放一次，超过预算的片段跳过，不截断正文。若所有有效直接命中都装不下，返回“资料片段过长”的提示，不调用回答模型。

最终按资料分组，同一代次的片段按原文序号排列。每块展示当前资料名、可用的章节路径和正文；当前名称查不到时回退向量化时的名称快照。直接命中、邻居和章节背景共同进入模型，但提问计数、相关度和出处只依据直接命中，避免重复计数。

同步问答、普通流式、工具化预检索和资料搜索工具使用同一组装规则。工具化问答仍允许模型按现有机制决定是否再次调用工具。

## 4. 失败、兼容和切换

- 授权查询失败时返回现有错误，不把错误解释成“无资料”，也不回退全库。
- 邻居查询或名称查询失败时记录错误；前者保留直接命中，后者使用名称快照。
- 不合法、重复、未授权、跨资料或跨代次的邻居丢弃。
- embedding、OSS 和外部调用在事务外；锁定资料、校验任务代次、替换向量和更新快照在同一个短事务中。失败回滚，旧正式向量保留。
- `app.ai.rag.section-neighbor-enabled` 默认关闭。开启后，新上传和手动重新向量化使用新策略；已有资料不自动重建。关闭后使用旧切分与旧上下文组装；已写入的新向量仍可检索。
- 出现问题时关闭开关并重启即可回滚；不删除旧资料或已生成的向量。

## 5. 验收与现有证据

功能验收应检查可确定的行为：切分不丢正文、标题路径正确、embedding 输入与存储正文分离、相邻块不会跨资料或代次、权限隔离、预算和异常降级、四个入口一致、事务失败保留旧向量，以及必要的全量回归。具体用例见附录。

模型对照用于观察实际收益：固定资料和问题，分别运行新旧策略，记录送入模型的完整上下文、答案、条件和主体是否正确、资料外拒答、耗时及真实 usage（不可得时明确记为不可得）。这类统计不等同于确定性的功能验证。

已有 48 题、每题三次的对照中，条件题完整证据率从 91.67% 提升到 100%，指代题两组都是 100%；部分基线条件回答出现材料张冠李戴，新策略样本未出现相同材料错误。旧题集基线已经很高且语料有重复填充，存在天花板，不能据此证明新策略适用于所有真实资料。完整数据和人工复核限制见 [验证报告](RAG语义连续性-验证报告.md)。

此前稿件提出“条件和指代各提高至少 25 个百分点”并据此判未通过。该阈值已写入旧稿，但当基线达到 91.67% 或 100% 时数学上不可能达到，不能单独作为判断功能正确与否的依据。**本稿建议将它从功能验收门槛移为效果观察，并保留原始结果；这是本次需审核的验收口径变更，不视为用户已经批准。** 默认开关继续关闭，待功能缺口和真实资料抽样核对后决定启用。

## 附录 A：独立实施契约

### A.1 模块与接口

| 模块 | 职责与接口 |
| --- | --- |
| `MarkdownSectionParser` | `parse(String content, boolean markdown)` 返回 `List<Section>`；`Section` 含不可变 `path` 和 `body` |
| `SectionChunker` | `split(String body, int targetTokens, int maxChunks)` 返回有序正文块 |
| `KnowledgeBaseVectorService` | `vectorizeAndStore(Long kbId, String content, String documentTitle, String originalFilename, String attemptId, Runnable heartbeat)` 编排分块、写入和提升；保留旧重载 |
| `LlmEmbeddingConfig` | 在 `getEmbeddingContent(Document)` 中仅为新策略构造背景前缀，保留原 `call` 委托和计费、限流边界 |
| `VectorRepository` | 用 `NeighborKey(long kbId, String parentDocumentId, int chunkIndex)` 批量查邻居，返回 `NeighborChunk(String id, String content, Map<String,Object> metadata)` |
| `RagContextAssembler` | `assemble(List<Document> hits, Set<Long> authorizedIds)` 返回状态、文本、直接命中、邻居、资料 ID 和 token 数 |
| `KnowledgeBaseQueryService` | 统一授权、检索、调用 assembler 并把结果交给四个入口 |

### A.2 标题和分块

标题仅识别 Markdown 中最多三个前置空格的 `#` 至 `######`，标记后须有空格或制表符；围栏中的内容保持正文，不解析标题。标题出现时结束前一段正文，更新该级及其下级标题；连续标题允许父标题没有正文。无标题内容路径为空。换行统一为 `\n`，章节首尾空白按解析器规则去除；分块的可逆性以解析后的 `Section.body` 为准，不宣称等同原文件字节。

分块目标沿用 `chunkSize=800`，上限沿用 `maxNumChunks=10000`。按 Unicode code point 逐步扩展，使用 `CL100K_BASE` 的 `countTokensOrdinary` 计数；超过目标时回退到块后半段最后一个换行或句末标点，没有边界就按当前 code point 边界结束。单个 code point 已超目标时也必须前进。超出块数上限抛 `BusinessException(ErrorCode.KNOWLEDGE_BASE_VECTORIZATION_FAILED, ...)`，不写正式向量。

### A.3 写入和 metadata

资料名依次取非空的 `documentTitle.strip()`、`originalFilename.strip()`、`知识库`，按 code point 保留前 80 个；路径由标题以 ` > ` 连接，保留最后 160 个 code point。每次向量化创建父 UUID 和任务 UUID。每块正文放 `Document.text`，metadata 写入：

```text
kb_id=pending:{kbId}:{jobId}
kb_target_id={kbId 的十进制字符串}
kb_vector_job_id={jobId}
chunk_strategy=section-neighbor-v2
parent_document_id={父 UUID 字符串}
chunk_index={从 0 开始的整数}
total_chunks={同代总块数}
document_title={名称快照}
section_path={路径，无路径时为空字符串}
```

新策略的 embedding 输入为 `[资料：{document_title}]\n`，路径非空时追加 `[章节：{section_path}]\n`，最后追加正文。缺正文或名称、路径不是字符串时抛参数错误；其他策略原样使用正文。批量写入仍沿用每批最多 10 块和现有心跳。

### A.4 事务与邻居

`activateVectorJobAndUpdateSnapshot` 在事务内锁定知识库行，校验状态为 `PROCESSING` 且 attempt 匹配，删除旧正式向量，将当前 `jobId` 的 pending 行提升为正式 `kb_id` 并移除两个临时字段，更新块数、策略快照和完成时间。任何一步异常均回滚；调用方清理当前 pending 行。模型调用和 OSS 读取不进入事务。

邻居 SQL 使用批量绑定的 `VALUES` 三元组，匹配 `metadata->>'kb_id'`、`parent_document_id`、`chunk_index`，同时限定 `chunk_strategy='section-neighbor-v2'`。只构造 `0 <= index < total_chunks` 的键；结果再次校验授权、UUID、整数类型、索引范围和三元组。重复三元组整组丢弃；单行 metadata 解析失败跳过并记录，SQL 错误由 assembler 降级为直接命中。

### A.5 上下文组装

`ContextResult` 包含 `Status status`、`String text`、`List<Document> directHits`、`List<Document> neighbors`、`List<Long> knowledgeBaseIds` 和 `int tokens`；状态为 `NO_HITS`、`READY`、`TOO_LONG`。默认 `maxTokens=6000`、前后各 1 块，前后范围 0–2，预算最小 1024。

1. 过滤未授权、空正文和重复 document ID；分数降序，null 和非有限值排最后，同分保留输入顺序。
2. 逐块尝试完整渲染直接命中，超预算跳过并继续；无有效命中为 `NO_HITS`，有有效命中但一块都装不下为 `TOO_LONG`。
3. 对保留的直接命中批量查询邻居，依次按距离由近到远、先前后后尝试加入，已选 ID 或超预算跳过。
4. 名称批量查询一次；异常或未找到时依次使用 `document_title`、`未知资料`。
5. 资料按最高直接命中分数排序；同资料按父代次首次命中顺序分组，代次内按块序号排序，旧格式块按原命中顺序置后。
6. 每块渲染 `[资料：名称]\n`、可选 `[章节：路径]\n` 和正文；块间用 `\n\n---\n\n`。每次试算完整渲染后的 token，返回不可变列表。

### A.6 入口与状态

授权查询按 `OwnerScope.effectiveOwnerId()` 获取可访问且 `COMPLETED` 的资料：ALL 使用全部结果，其他范围与请求 ID 求交集。检索结果按同一授权集合再次过滤。授权异常传播到现有错误路径。

同步、普通流式、工具化预检索、`searchKnowledge` 开启时均执行 assembler。`NO_HITS` 维持入口既有无结果行为；`READY` 使用组装文本，计数、出处和最高分只看直接命中；`TOO_LONG` 使用“资料片段过长，当前无法完整提供上下文，请缩小检索范围或拆分资料。”。预检索过长时不调用回答模型；模型已运行后调用搜索工具遇过长，只能向模型返回该提示。过长单独记录，不标成无命中。工具化出处合并预检索和工具直接命中，按 document ID 去重，邻居不增加段数。
