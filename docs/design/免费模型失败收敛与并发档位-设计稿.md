## Problem Statement

接入免费模型后，试卷切题链路出现两类失败，且这两类的成因和修法完全不同：

1. **结构切题返回「字段说明」而不是「题目数据」**。`paperId=57`（2 页、约 1002 字、只有 1 个结构分块）在 165.7 秒后返回约 7993 字符，内容开头是 `"$schema"`、`"type": "object"`、`"properties"`，后端解析结果是 `nodes=null`。这不是 429、不是超时、也不是 JSON 截断，而是模型把输出格式说明当成了答案。现有重试没接住，因为 `StructuredOutputInvoker` 只对「调用或解析抛异常」重试，而这次 JSON 反序列化成功了，只是业务字段为空。
2. **答案/解析批次被本地 RPM 门直接拒绝**。`paperId=53` 的解析批次在 10 毫秒内连续失败，根因是本地 `AiUsageGate.tryAcquire` 抛 `AI_RATE_LIMIT_EXCEEDED`，不是模型返回错。这一类靠降低瞬时并发、等待窗口、退避重试可以改善。

本设计只解决「失败收敛」和「免费模型并发档位」两件事，不改变切题对外接口、不改 `BlockTreeDTO` 字段、不新增平行重试框架。

## Solution

做四件事：

1. **P0：给结构化输出加「语义校验 + 定向重试」**。让调用方能把「解析成功但内容不满足业务要求」也纳入统一重试，并在第二次请求时告诉模型「上次返回的是 schema，不是数据」。
2. **P0：加固结构切题 Prompt**。把「输出格式说明」和「要返回的数据」在提示词里彻底区分开，并让模型可以省略可选字段、不要为了填满字段而编造。
3. **P1：免费模型统一并发闸门**。每次模型调用都按“实际 Provider + 模型 + 模态”判断是否免费；免费调用进入全局并发闸门，文本、识图、Embedding、音频分别限流，付费模型保持原并发。
4. **P1：结构化调用限流退避**。对限流、超时、连接中断这类「值得重试」的失败，在统一入口做指数退避加随机抖动，避免 2 次重试立刻撞同一 RPM 窗口。

# 正文（业务视角）

## 改造点 A：语义校验与定向重试

- 目的：把「模型回包能解析，但业务字段是空的/不对」也纳入结构化输出的统一重试。现在只有解析报错才会重试，像「返回了 schema、`nodes` 为空」这种结果会被当成成功返回，等业务层发现时已经晚了。
- 触发：结构切题调用模型后，得到 `BlockTreeDTO`；它反序列化成功，但顶层 `nodes` 为空。
- 规则与步骤：给统一的结构化输出入口增加一个可选的「语义校验器」。调用方传一个判断条件（结构切题传：`nodes` 不为空），并传一句「如果校验不通过，第二次要告诉模型什么」。入口拿到模型结果后先跑这个校验器；不通过就按现有重试循环再调一次模型，第二次的提示词里追加那句定向说明，而不是笼统地写「上次解析失败」。
- 结果：`paperId=57` 这种「返回 schema」会被识别为失败并自动定向重试一次；重试仍失败时，回到原来的统一失败路径，错误码和信息保持不变。其他没有传校验器的调用方行为完全不变。
- 边界与异常：校验器为空表示「不启用语义校验」，完全兼容现状；语义校验失败计入现有最大重试次数；定向说明不会原样透出给用户，最终只返回安全的兜底文案。
- 可改点：每个调用方可以自定义校验条件和定向文案；结构切题想改成「`nodes` 非空且每个节点行号合法」，只改它传入的校验器。

## 改造点 B：结构切题 Prompt 加固

- 目的：让模型不再把「输出格式说明」当成要返回的内容。当前把格式说明直接贴在提示词后面，小模型很容易整段抄回来。
- 触发：`PaperStructureService` 组装结构切题提示词时，把提示词正文和 `BeanOutputConverter` 生成的格式说明拼在一起。
- 规则与步骤：在格式说明前加一句明确的分隔语「下面是字段说明，不是答案，不要原样输出 schema」；同时在提示词正文里补两条规则：①顶层只能有 `subjectKey / totalScore / nodes / warnings` 四个字段，禁止输出 `$schema / type / properties / required` 和示例题；②参考解析、考点、评分规则只在原文明确给出时才填，不确定就填 `null`，不要编造。
- 结果：模型返回「数据对象」的概率提高，输出 token 和耗时下降，也降低被截断的概率。
- 边界与异常：不改 `BlockTreeDTO` 的字段和解析逻辑；可选字段本就允许为 `null`，模型省略不会影响下游。
- 可改点：想再收紧输出，可进一步把结构阶段的字段说明换成手写的精简版（本期不做，见 Out of Scope）。

## 改造点 C1：免费模型统一并发闸门

- 目的：免费模型容易被上游限流、排队或超时。限制要跟“这一次实际调用到底用了哪个模型”绑定，而不是只看启动配置，也不能只限制文本模型。
- 触发：所有通过 Provider 注册表发起的模型调用。同步 Chat、流式 Chat、Embedding 包装器都会经过同一个闸门。
- 判定规则：先查当前生效价格；同一 Provider + 模型 + 模态的输入、输出、缓存价格全为 0 时判定免费。价格表没有记录时，回退到 `app.ai.free-models` 中声明的文本 / 识图 / Embedding / 音频 Provider，避免种子价格尚未同步时漏掉限制。`auto-activate` 只控制平台是否自动切换默认 Provider，不参与“当前模型是否免费”的判断；管理员手动绑定免费模型同样受限。
- 限流规则：文本、识图、Embedding、音频各有一组全局信号量，默认都是 1。多个用户同时使用免费模型时共享同一组许可，不做用户级配额。付费模型直接放行，不等待。
- 结果：免费文本调用最多 1 个在途，免费识图最多 1 个在途，免费 Embedding 最多 1 个在途，免费 TTS/ASR 共享 1 个音频许可；调用结束后立即释放许可。试卷解析在免费文本模型下把批大小从 3 降到 2，减少单批输出长度和截断风险。
- 边界与异常：等待许可被中断时恢复中断标记，并抛可重试的 `AI_RATE_LIMIT_EXCEEDED`。免费判定依据价格表，管理员改价后下一次调用即生效；没有价格记录时使用配置兜底。语音 TTS 在单次 `synthesize` 期间持许可，ASR 在实时会话生命周期内持许可，会话关闭或失败时释放。
- 可改点：四类许可数和免费解析批大小都走 `app.ai.free-model-concurrency.*`；关闭闸门用 `enabled=false`。

## 改造点 C2：结构化调用限流退避

- 目的：限流、超时、连接中断是瞬时问题，同一秒重试大概率还是失败。给这类失败加指数退避和随机抖动，让重试错开高峰期。
- 触发：结构化输出入口在重试循环里捕获到「值得重试」的失败（本地限流、上游 429、超时、连接中断）。
- 规则与步骤：这类失败在下次尝试前先睡一小段，时长按「基础时长 × 2 的尝试次数次方」增长，再加一个随机抖动，并封顶。解析失败、语义校验失败不算「值得重试的瞬时失败」，不额外等待，保持现状。
- 结果：结构分块、答案键、解析等所有走统一入口的调用，遇到限流/超时都会错峰重试，而不是立刻再次撞门。
- 边界与异常：视觉单次入口不重发、不参与退避，保持现状；等待被中断时恢复线程中断标记并按失败返回，不无限等。
- 可改点：基础时长、封顶时长、抖动范围都抽成配置。

## Testing Decisions

- 只测外部行为：测「语义校验失败会触发一次定向重试且成功」「语义校验最终失败返回安全文案」「可重试失败会退避后重试」「文本、识图、Embedding 的零价格模型都判定免费」「有非零价格时不限流」「免费文本许可耗尽时后续调用等待」。
- 退避的睡眠抽成一个可覆盖方法，测试用子类把睡眠置空并记录是否被调用，避免真实等待拖慢单测。
- 新测试沿用仓库现有的 `@Nested` + 中文 `@DisplayName` 风格。
- 本次改动落在 `common/ai`（公共能力）与 `resume`（配置与执行器），按 T3 收尾：定向测试通过后跑全量 `./gradlew :app:test --no-daemon`，输出只看尾部 `Select-Object -Last 60`。

## Out of Scope

- 不改 `BlockTreeDTO` 字段，也不把结构阶段拆成「只出切题字段」的轻量 DTO；输出契约精简后续单独评估。
- 不动态重算 Redis 侧 `PAPER_EXTRACTION` 的并发上限；本期靠模型调用前的统一闸门控制实际并发，Redis 门继续只当上限。
- 不把 `paper-extract` Stream worker 纳入自动档位；它是跨卷调度层，与单卷内 AI 并发不是同一旋钮，需要时用 `APP_STREAM_PAPER_EXTRACT_WORKERS` 单独调。
- 不新增平行分层、不绕过 `StructuredOutputInvoker` / `AiUsageGate` / `BoundedExecutor`。

## Further Notes

- 管理员账号当前绕过本地 `AiUsageGate`，所以管理员复现时看到的失败更可能是模型输出问题或上游限制，不是本地 RPM 门。
- 降低并发能提高「限流/超时」场景的稳定性下限，但不能保证模型不再回 schema；后者必须靠语义校验和 Prompt 加固解决。

### 数据

- `semanticValidator`：`java.util.function.Predicate<T>`；为 `null` 表示不启用语义校验。
- `semanticRetryInstruction`：语义校验失败后追加到第二次 system prompt 的一句话，允许为空。
- `BlockTreeDTO`：`app/src/main/java/interview/guide/modules/resume/service/BlockTreeDTO.java`，顶层字段 `subjectKey / totalScore / nodes / warnings`。

### 步骤映射

1. `invoke(...)` 的循环体改为：
   ```java
   T result = invokeProvider(...);
   if (semanticValidator != null && !semanticValidator.test(result)) {
       throw new StructuredOutputSemanticException(semanticRetryInstruction);
   }
   recordAttempt(contextTag, STATUS_SUCCESS);
   recordInvocation(contextTag, STATUS_SUCCESS, startNanos);
   return result;
   ```
2. 循环开始前计算 `attemptSystemPrompt` 的规则改为：
   - 第一次尝试：`securedSystemPrompt`。
   - 后续尝试且 `lastError instanceof StructuredOutputSemanticException semantic`：调用新方法 `buildSemanticRetrySystemPrompt(securedSystemPrompt, semantic)`。
   - 其余：沿用现有 `buildRetrySystemPrompt(securedSystemPrompt, lastError)`。
3. 新增方法：
   ```java
   private String buildSemanticRetrySystemPrompt(
       String securedSystemPrompt, StructuredOutputSemanticException error) {
       StringBuilder prompt = new StringBuilder(securedSystemPrompt);
       if (retryAppendStrictJsonInstruction) {
           prompt.append("\n\n").append(STRICT_JSON_INSTRUCTION);
       }
       prompt.append("\n\n上次输出虽然能解析，但内容不满足要求。");
       if (error.retryInstruction() != null && !error.retryInstruction().isBlank()) {
           prompt.append("\n").append(error.retryInstruction());
       }
       return prompt.toString();
   }
   ```
4. catch 分支里，在记录 `lastError` 与 `recordAttempt(FAILURE)` 之后，按 `e instanceof StructuredOutputSemanticException` 区分日志：语义失败记「语义校验失败，准备定向重试」；其余沿用现有文案。
5. 循环耗尽后仍走现有 `throw new BusinessException(errorCode, failureMessage(errorPrefix, lastError), lastError)`。

### 状态与分支

- `semanticValidator == null`：跳过语义校验，行为与现状完全一致。
- 语义校验失败且 `attempt < attempts`：进入下一次循环，`attemptSystemPrompt` 用语义重试文案，不再说「解析失败」。
- 语义校验失败且已是最后一次：抛出 `BusinessException`，`errorCode` 为调用方传入值，message 为 `errorPrefix + "请稍后重试"`（对结构调用即 `试卷结构化失败：请稍后重试`），不包含定向文案。
- `VisionRequestRejectedException`：仍立即抛出，不参与语义校验与退避。

### 可改点映射

- 是否启用/怎么判断：调用方传入的 `Predicate<T>` 与 `String semanticRetryInstruction`。
- 最大重试次数：`app.ai.structured-max-attempts`（`APP_AI_STRUCTURED_MAX_ATTEMPTS`，默认 2）。

### 测试（A）

- `app/src/test/java/interview/guide/common/ai/StructuredOutputInvokerFailureTest.java` 新增用例：
  - 第一次 `callSpec.content()` 返回 `{"subjectKey":null,"totalScore":null,"nodes":null,"warnings":null}`，第二次返回含非空 `nodes` 的合法 JSON；`maxAttempts=2`；断言 `requestSpec.call()` 调用 2 次、第二次 `system(...)` 参数包含传入的 `semanticRetryInstruction` 且不包含「上次输出解析失败」。

### 步骤映射

1. `LlmProviderRegistry` 用当前用户实际选择创建 / 复用 ChatClient，并提供该 Provider 的模型名。
2. 每次 Chat 或 Embedding 调用进入 `AiCallRecorder` 的 Advisor / 包装器。
3. `AiCallRecorder` 把 `providerId`、`model`、`modality` 传给 `FreeModelConcurrencyGate.acquireIfFree(...)`。
4. 闸门用当前价格判断是否免费；价格缺失时回退配置。免费调用按模态获取许可，付费直接执行。

6. 试卷解析切批时调用 `effectiveAnalysisBatchSize()`，免费文本模型取 `analysisBatchSize`，否则取 `answerProperties`。

### 状态与分支

- `enabled=false`：闸门全部放行，不改变任何并发。
- 价格记录存在且非全 0：按付费处理，不限流。
- 价格记录存在且全 0：按免费处理，进入对应模态闸门。
- 价格记录不存在：匹配 `free-models` 配置的 Provider 才按免费处理。
- `autoActivate`：不参与免费判定；它只影响启动时是否自动切默认 Provider。
- 多用户：共享同一组全局许可，不做用户级配额。

## C2：StructuredOutputInvoker 限流退避

### 入口与签名

- 修改 `app/src/main/java/interview/guide/common/ai/StructuredOutputInvoker.java`。
- 构造器新增读取三个退避配置字段：`int retryBackoffBaseMs`、`int retryBackoffMaxMs`、`int retryBackoffJitterMs`（来自 `StructuredOutputProperties`）。

  ```java
  }
  ```

### 数据

  ```java

  ```
- `application.yml` 在 `app.ai` 结构化段落新增：
  ```yaml

  structured-retry-backoff-max-ms: ${APP_AI_STRUCTURED_RETRY_BACKOFF_MAX_MS:5000}
  structured-retry-backoff-jitter-ms: ${APP_AI_STRUCTURED_RETRY_BACKOFF_JITTER_MS:500}
  ```

### 步骤映射

1. `invoke(...)` 的 catch 分支在 `if (attempt < attempts)` 内、记录日志之后，追加：
   ```java
   if (RetryableFailureClassifier.isRetryable(e)) {
       long delay = retryBackoffDelayMs(attempt);
       if (delay > 0) {
           try {
               sleepRetryBackoff(delay);
           } catch (InterruptedException interrupted) {
               Thread.currentThread().interrupt();
               break;
           }
       }
   }
   ```
2. 新增私有方法：
   ```java
   private long retryBackoffDelayMs(int attempt) {
       long base = Math.max(0, retryBackoffBaseMs);
       long exp = base * (1L << Math.max(0, attempt - 1));
       long capped = Math.min(exp, Math.max(base, retryBackoffMaxMs));
       long jitter = retryBackoffJitterMs <= 0 ? 0
           : ThreadLocalRandom.current().nextLong(Math.max(1, retryBackoffJitterMs));
       return Math.max(0, capped + jitter);
   }
   ```
3. `VisionRequestRejectedException` 仍在 catch 顶部直接 `throw`，不进入退避；语义失败不满足 `RetryableFailureClassifier.isRetryable`，不等待，保持 A 的行为。

### 状态与分支

- `RetryableFailureClassifier.isRetryable(e)` 为 true：`AI_RATE_LIMIT_EXCEEDED`、`AI_SERVICE_TIMEOUT`、transport 失败、`VisionRequestRejectedException`（后者不会走到这里）。
- 解析失败 / 非法 JSON / 语义失败：`isRetryable=false`，不等待，保持现状。
- `sleepRetryBackoff` 被中断：恢复中断标记并 `break` 出重试循环，进入最终失败抛出。
- `attempts=1`（视觉单次入口）不重试，因此不会走到退避。

### 可改点映射

- 基础/封顶/抖动：`APP_AI_STRUCTURED_RETRY_BACKOFF_BASE_MS` / `APP_AI_STRUCTURED_RETRY_BACKOFF_MAX_MS` / `APP_AI_STRUCTURED_RETRY_BACKOFF_JITTER_MS`。

### 测试（C2）
