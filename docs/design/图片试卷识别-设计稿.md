## 1. 现状与根因

已核实（不是推测）：

| 事实 | 影响 |
| --- | --- |
| 样本 PDF：2.41MB、**4 页 / 4 个图像对象 / 0 个字体对象** | 纯扫描件，没有文字层 |
| `DocumentParseService` 里显式关闭了图片提取（`PDFParserConfig` + `NoOpEmbeddedDocumentExtractor`） | Tika 只能拿到空文本；上传时会直接报「无法提取文本，请确保不是扫描版 PDF」 |
| 上传白名单只有 `pdf / doc / docx / txt / md / rtf`，上限 10MB | jpg/png 进不来 |
| `PaperQuestionExtractionService` 只吃文本 | 即使拿到图片也没有入口 |
| 当前配置的模型：qwen3.5-flash / kimi-k2.6 / deepseek-v4-flash / glm-5 | **没有视觉模型**，必须新增 |

所以缺的不是"再调一次 Tika"，而是**一条独立的"图片 → 文本"前置链路**，它产出文本后再汇入现有切题/作答/批改/报告。

## 2. 目标与非目标

**目标**

1. 上传扫描版 PDF / 拍照图片，能把整份试卷转成**保留版式的文本**（题号、选项标签、分值、大题与小节标题）
2. 识别结果可逐页预览、编辑、重传、删除，确认后才进入切题
3. 识别失败可重试；单页失败不影响其它页
4. 识别文本进入现有 `PaperQuestionExtractionService`，后续作答/批改/报告完全复用
5. 含图题至少不丢信息：题目能追溯"来自第几页"，并能查看原页

**非目标**

- 不识别手写作答、不做纸面自动判分
- 不做透视矫正、自动裁题图、去阴影
- 不支持 HEIC 原生上传（前端先转 JPG，或提示用户转换）
- 不把识别结果直接变成结构化题目（仍由切题阶段负责，见 §4.2）
- 不做跨设备/跨页的智能拼题（跨页题干交给切题阶段的整卷文本处理）

## 3. 用 Spring AI 的哪些能力实现（核心）

这件事在 Spring AI 里由**三块能力**拼起来，没有黑魔法：

### 3.1 多模态输入：把「一页图」变成模型能看的消息

Spring AI 2.0.1 的消息模型原生支持媒体附件：

- `org.springframework.ai.content.Media(MimeType, Resource)`：一张图的载体（MIME + 字节/资源）
- `ChatClient.prompt().user(u -> u.text(...).media(media...))`：`PromptUserSpec.media(...)`
- 等价的低层写法是 `UserMessage.builder().text(...).media(...)`（`UserMessage` 实现 `MediaContent`）

底层 `OpenAiChatModel` 会把它序列化成 OpenAI 兼容协议里的 `image_url`（base64 data URI），
所以只要**模型本身是视觉模型**（本文用 DashScope 的 `qwen-vl-max`），现有 OpenAI 兼容客户端就能直接发图，
不需要引第三方 OCR SDK、也不需要换 HTTP 客户端。

```java
// 一页 JPEG（由 PDFBox 渲染或用户上传的图片规范化而来）
Media pageImage = new Media(MimeTypeUtils.IMAGE_JPEG,
    new ByteArrayResource(jpegBytes, "page-" + pageNo + ".jpg"));
```

### 3.2 结构化输出：让模型按「页级 schema」返回，而不是自由文本

识别结果不是一段散文，而是一页一个对象。项目里已有统一封装 `StructuredOutputInvoker`，
它内部用的是 Spring AI 的 `BeanOutputConverter<T>`：

1. `outputConverter.getFormat()` 自动把 Java record 生成 **JSON Schema**，追加到 system prompt；
2. `chatClient.prompt()...call().entity(outputConverter, spec -> spec.validateSchema())`
   由 Spring AI 解析 JSON 并做 schema 校验；
3. `StructuredOutputInvoker` 负责**重试 + 修复型提示 + 引号修复 + 指标**（项目已有能力，不要另写一套）。

本设计新增的页级 schema：

```java
public record PageRecognition(
    int pageNo,
    String text,        // 保留版式的转写文本（题号/选项/分值/标题）
    boolean hasFigure,  // 本页是否含图（几何图/表格/插图）
    String notes        // 识别异常说明，如「第 3 题选项被裁切」
) {}
```

### 3.3 需要扩展的一处：`StructuredOutputInvoker` 支持媒体附件

现状 `callStructuredOutput` 只拼了 `.user(userPrompt)`，没有 media 入口。
**给现有封装加一个多模态重载**（而不是在业务层绕开它，AGENTS 规则要求结构化输出统一走它）：

```java
// 新增重载
public <T> T invoke(ChatClient chatClient, String systemPromptWithFormat,
                    String userPrompt, List<Media> media,
                    BeanOutputConverter<T> outputConverter, ... ) {
    // 其余重试逻辑完全复用；只是调用时带上 media
}

// 内部
var call = chatClient.prompt()
    .system(systemPrompt)
    .user(u -> {
        u.text(userPrompt);
        if (!media.isEmpty()) {
            u.media(media.toArray(Media[]::new));   // ← Spring AI 多模态入口
        }
    })
    .call();
return call.entity(outputConverter, spec -> spec.validateSchema());
```

重试时会把同一张图再发一次（图片 token 会重复计费），所以**单页失败最多重试 2 次**（见 §10）。

### 3.4 客户端与 Provider：在 `LlmProviderRegistry` 增加「默认视觉客户端」入口

现有 registry 用「provider 配置 → OpenAI 兼容客户端」的方式建模型，所以**不用新写客户端类**。
但识别服务里不该写死 `getPlainChatClient("dashscope-vl")`——"图片 → 文本"以后还会被
图片追问、手写批改、截图答疑复用，provider id 和模型名散落在业务代码里就不好换了。
所以在 registry 里补一个默认视觉入口，是更合适的边界：

| 新增方法 | 作用 |
| --- | --- |
| `ChatClient getDefaultVisionChatClient()` | 取默认识图模型的**视觉专用客户端**；识别服务只调这一个 |
| `ChatClient getVisionChatClientOrDefault(String providerId)` | 显式指定 provider（空 / `"default"` → 视觉默认），给以后按学科或成本切模型留口子 |

```java
// LlmProviderRegistry
public ChatClient getDefaultVisionChatClient() {
    return getVisionChatClientOrDefault(null);
}

/**
 * 视觉任务的独立客户端：单轮、无工具、无记忆、无文本兜底话术。
 * 注意：空白 id 必须解析成「视觉默认」，不能交给任何按文本默认解析的方法。
 */
public ChatClient getVisionChatClientOrDefault(String providerId) {
    String id = isBlank(providerId) || "default".equalsIgnoreCase(providerId.trim())
        ? resolveDefaultVisionProviderId()
        : providerId.trim();
    if (isBlank(id)) {
        throw new BusinessException(ErrorCode.VISION_PROVIDER_NOT_CONFIGURED,
            "未配置识图模型：请设置 app.ai.default-vision-provider，"
                + "并确认该 Provider 已启用且标记为支持图片输入");
    }
    assertVisionCapable(id);   // 不存在 / 已禁用 / 未声明支持图片 → BusinessException
    return clientCache.computeIfAbsent(id + ":vision", key -> createVisionChatClient(id));
}

/**
 * 视觉客户端走独立工厂：以后要加/去 Advisor、调参、换观测，都不会波及文本链路。
 * 当前刻意不挂任何 Advisor —— 原因见本节「视觉客户端挂什么」。
 */
private ChatClient createVisionChatClient(String providerId) {
    OpenAiChatModel chatModel = getChatModel(providerId);   // 复用底层模型缓存，不重复建 HTTP 客户端
    ChatClient.Builder builder = ChatClient.builder(chatModel);
    log.info("[LlmProviderRegistry] Created vision ChatClient (no advisors) for {}", providerId);
    return builder.build();
}
```

四个关键点：

1. **默认项必须独立**：`app.ai.default-vision-provider`（默认 `dashscope-vl`），不能复用
   `default-chat-provider`。文本默认是 qwen3.5-flash，把图片发给它只会在厂商侧拿到 400，
   而且错误信息与"识别失败"对不上，排查成本很高。
2. **不做静默回退**：视觉 provider 缺失 / 禁用 / 未声明支持图片时，直接抛
   `BusinessException(VISION_PROVIDER_NOT_CONFIGURED)` 并指明该改哪个键。宁可第一次调用就报清楚，
   也不要悄悄换文本模型、最后表现为"这一页识别出空文本"。
3. **能力显式声明，不靠模型名猜**：Provider 增加 `supports-vision`，由配置的人勾选。
   用 `qwen-vl`/`glm-4v` 之类的命名去推断，换厂商或换命名规则就会失效。
4. **和运行期切换保持一致**：chat / embedding 的默认值都支持"数据库覆盖 yml"，视觉默认照同一套走，
   在 AI 管理界面就能换模型，不必改配置重启。

#### 视觉客户端挂什么（为什么不复用 `getPlainChatClient`）

`getPlainChatClient` 的名字容易让人以为它"什么都不挂"，实际它会给客户端加
`SafeGuardAdvisor`——敏感词命中时返回固定话术「抱歉，我只能协助面试相关的任务。」
对识图来说这是错的：

- 这段拒答文案与试卷识别场景无关，用户看到会一头雾水；
- 语文阅读理解原文里出现"忽略之前的指令"这类句子完全正常，属于**误伤**，
  一次误伤就是整页识别失败；
- 视觉模型的任务是"照抄页面"，本来就不该被文本护栏改写。

所以视觉链路**自己建客户端、自己决定挂载哪些组件**，与 `:plain` / `:agent` / `:voice`
并列成第四种缓存键（`id + ":vision"`）：

| 组件 | 视觉客户端是否挂 | 原因 |
| --- | --- | --- |
| `SafeGuardAdvisor` | **不挂** | 拒答话术面向面试问答，且会误伤试卷原文 |
| `MessageChatMemoryAdvisor` | **不挂** | 单页识别无多轮上下文；记忆反而会让第 3 页受第 2 页影响 |
| `ToolCallingAdvisor` / `SkillsTool` | **不挂** | 没有要模型调用的外部能力，图已经在消息里 |
| `SimpleLoggerAdvisor` | 默认不挂 | 需要排查时**只在这里**临时打开，不污染文本链路 |
| 底层 `OpenAiChatModel` | 复用 `getChatModel(providerId)` | 模型与 HTTP 客户端按 provider 缓存，换的只是外层 ChatClient |

这条边界也是以后加能力的入口：要统计每页图片 token，就在 `createVisionChatClient`
里加一个只属于视觉链路的 Advisor；要换识图厂商，只改 provider 配置，不动这个工厂。
`reload()` 清空 `clientCache` 时 `:vision` 条目一起失效，无需额外处理。

配置与存储：

| 位置 | 字段 | 说明 |
| --- | --- | --- |
| `application.yml` | `app.ai.default-vision-provider: ${APP_AI_DEFAULT_VISION_PROVIDER:dashscope-vl}` | 兜底默认值 |
| `llm_global_setting` | `default_vision_provider_id VARCHAR(64) NULL` | 运行期覆盖；为空则用 yml |
| `llm_provider_config` | `supports_vision BOOLEAN NOT NULL DEFAULT false` | 该 Provider 的模型能否接收图片 |
| `ProviderConfig` / `LlmProviderEntity` / `ProviderDTO` | `supportsVision` | yml 种子、持久化、界面展示 |

```yaml
app:
  ai:
    default-vision-provider: ${APP_AI_DEFAULT_VISION_PROVIDER:dashscope-vl}
    providers:
      dashscope-vl:
        base-url: https://dashscope.aliyuncs.com/compatible-mode/v1
        api-key: ${AI_BAILIAN_API_KEY}
        model: ${AI_VISION_MODEL:qwen3.8-flash}
        supports-vision: true
        supports-embedding: false
```

解析优先级（`resolveDefaultVisionProviderId()`）：

```
llm_global_setting.default_vision_provider_id（非空）
  → app.ai.default-vision-provider（非空）
  → 空 → 抛 VISION_PROVIDER_NOT_CONFIGURED
```

既**不继承 `default-chat-provider`，也不继承 `default-embedding-provider`**。三者语义不同，
混用只会把"文本模型收到了图片"这种错误推迟到运行期。

> 生效规则沿用现有约定：Provider **一旦落库，数据库就是权威来源**。而现有
> `LlmProviderBootstrapService` 只在 `llm_provider_config` 为空时才从 yml 导入，
> 所以**已有环境不会自动出现 `dashscope-vl`**。落地方式二选一，实现时按第 1 条：
> 1. bootstrap 改成"补齐 yml 中缺失的 provider"，已存在的行一律不覆盖；
> 2. 在「设置 → 模型 Provider」里手动新增 `dashscope-vl` 并填 Key。
>
> 第 1 条有个副作用：管理员主动删掉的预设 Provider 会在下次启动被补回来。
> 如果不能接受，就只对 `dashscope-vl` 做一次性的"不存在才插入"，并在启动日志里写明。

调用侧因此只依赖 registry，不感知具体厂商：

```java
ChatClient visionClient = registry.getDefaultVisionChatClient();
PageRecognition page = structuredOutputInvoker.invoke(
    visionClient, systemPrompt, userPrompt, media, PageRecognition.class);
```

- 视觉客户端是独立工厂产物，不继承 `getPlainChatClient` 的 `SafeGuardAdvisor`，
  也不挂 `SkillsTool` / `ChatMemoryAdvisor` / ToolCalling —— 识别是**单轮无状态**任务；
- 与切题/批改共用同一套 registry，换模型、API Key 加密、失败提示都可复用。

> 注意：**切题用的不是这个客户端**。视觉模型只在「识别阶段」把图片转成文本；
> 之后的切题仍然走默认文本模型（`getPlainChatClient()` → 现有 `PaperQuestionExtractionService`）。
> 两者是两次独立调用、两套 prompt，不能混用——把图片发给非视觉模型会直接报错，
> 把切题交给视觉模型则是白付图片 token。

### 3.5 明确不用的部分

| 能力 | 为什么不用 |
| --- | --- |
| `ChatMemory` / `MessageChatMemoryAdvisor` | 识别是单页无状态，没有多轮上下文 |
| Tool calling（`@Tool`） | 没有需要模型调用的外部能力；图已经在消息里 |
| 流式（`stream()`） | 需要的是完整 JSON，流式反而增加聚合与解析复杂度 |
| `VectorStore` / RAG | 识别不涉及检索 |

## 4. 整体流水线

### 4.1 输入先归一成「页」

| 输入 | 处理 |
| --- | --- |
| 图片（JPG/PNG） | 每张图 = 一页；按上传顺序编号；单张 ≤50MB；按 EXIF 方向摆正（手机拍照常见） |
| PDF | 用 PDFBox 打开；**逐页**判定有没有文字层（见 4.2） |
| 多文件 | 一次最多 10 个（PDF 页数之和也 ≤10），按上传顺序合并为同一份试卷 |

任何输入最终都变成 `List<Page>`（pageNo 从 1 开始），后续逻辑与文件类型无关。

### 4.2 逐页判定：这一页用文本还是识图

先分清两件事，避免混淆：

| 阶段 | 用什么模型 | 判断依据 |
| --- | --- | --- |
| **识别阶段**（图片 → 文本） | 视觉模型（`dashscope-vl`）**或不用模型** | 这一页有没有可用的文字层 |
| **切题阶段**（文本 → 题目树） | **永远是普通文本模型** | 不看文件类型，只看文本 |

也就是说：**"用识图还是文本"只在识别阶段决定，而且是逐页决定的；切题阶段不参与这个判断。**

#### 判定规则（`PaperRecognitionService.decideSource(page)`）

对 PDF 逐页用 PDFBox `PDFTextStripper`（`setStartPage(n)/setEndPage(n)`）抽出该页文本，
然后按顺序过三道闸：

```
① 抽不到文本（空白 / 图片页）
      → IMAGE（渲染 + 视觉模型）

② 抽到了，但"像坏码"：U+FFFD 或控制字符占比 > 20%
   或可打印字符占比 < 60%（常见于没有 ToUnicode 的自定义字体）
      → IMAGE（视觉模型兜底，PDF 里那层文字不可信）

③ 抽取质量正常：
      有效字符（汉字/字母/数字，不含空白）≥ 30  → TEXT（直接用，零模型成本）
      含行首题号（如 "1." "2、"）              → TEXT（短页但有题目，不能用图片兜底）
      < 30 且无题号                              → IMAGE（大概率是封面/扫描页）
```

判定结果写进 `paper_pages.source`（TEXT / IMAGE），所以**每一页为什么走哪条路是可查的**，
也支持人工干预（见下）。

#### 几个容易踩的边界

| 情况 | 判定 | 说明 |
| --- | --- | --- |
| 扫描仪生成的 PDF 带一层 OCR 文字（隐藏文字层） | TEXT | 有可信文字层就不用再花视觉 token；如果 OCR 层质量差，用户在预览页点「用识图重做此页」 |
| 数字版 PDF 的某一页是整页插图 | IMAGE | 该页文字层为空，正常走视觉 |
| 有文字层但页面里有几何图 | TEXT | 文字照常用文本；图不参与识别，题目仍可通过"查看原页"看图 |
| 纯图片上传（JPG/PNG） | IMAGE | 没有文字层可判，直接视觉 |
| 同一份 PDF 文字页 + 扫描页混合 | 逐页不同 | 这是不做"整份一刀切"的原因 |
| 短封面页（只有标题） | IMAGE（<30 且无题号） | 多花一次视觉调用，换取不漏内容；≤10 页时可接受 |

#### 人工兜底

预览页每页提供「**用识图重做此页**」按钮：即使判定为 TEXT，用户发现文字层是乱码或漏内容时，
可以强制该页转成 IMAGE 重跑（`source` 改为 IMAGE + 重投该页），不需要整份重来。

#### 渲染与识别的区别（内存相关）

- **渲染**：为了预览与"查看原页"，每一页都会渲染成 JPEG 存 S3（逐页渲染、即时释放）；
- **识别**：只有 `IMAGE` 页才把这张 JPEG 发给视觉模型。

所以"渲染了 10 页"不等于"调了 10 次视觉模型"。

### 4.3 为什么是「先转写、后切题」两段，而不是让 VLM 直接出题目 JSON

| 方案 | 评价 |
| --- | --- |
| VLM 一次同时做识别 + 结构化出题 | 省一次调用，但模型的识别错误会**直接变成结构化字段**（题号错位、选项串行），后面没有校验机会；跨页材料合并也更难 |
| **VLM 只做「保留版式的转写」→ 现有切题链路**（本设计） | 多一次调用，但切题阶段已有题号对账、分批、去重、补抽、题型判定、分值兜底，能接住识别噪声；且文字层页面与扫描页共用同一条切题路径 |

所以：**视觉模型只回答"这一页上写了什么"，"这页有几道题、每题什么结构"交给现有切题**。

### 4.4 状态机

```
[上传]
  └─> RECOGNIZING（异步，逐页识别）
        ├─ 全部页 READY ──────────> NEEDS_REVIEW（预览校对）
        ├─ 部分页 FAILED ────────> NEEDS_REVIEW（失败页标红，可重传该页）
        └─ 全部失败 / 文件损坏 ──> FAILED（保留原文件，可整份重试）

[NEEDS_REVIEW] --用户改文字/重传单页/删页--> NEEDS_REVIEW
[NEEDS_REVIEW] --用户点「确认并切题」--> EXTRACTING（现有 paper:extract 异步任务）
[EXTRACTING]  ──> READY（现有「试卷概览」，可开始作答）
```

识别状态与切题状态**分开存**：识别是 `recognition_status`，切题仍是 `analysis_status`，
避免把两种异步任务揉进一个字段（现有恢复调度器也各管各的）。

### 4.5 逐页识别流程（单页）

```
1. 取该页字节（PDF 渲染 或 上传图片）
2. 规范化：长边 ≤2000px、JPEG quality 0.85、≤1.5MB
3. 组多模态消息：system(转写规则 + JSON schema) + user(第 N 页提示) + media(图片)
4. StructuredOutputInvoker.invoke(...) -> PageRecognition
5. 校验：text 非空；长度异常（<20 字且 hasFigure=false）视为可疑，记 note
6. 落库 paper_pages.text / has_figure / notes，状态 READY；异常则 FAILED + error
```

**内存约束**：服务器只有 1.87GB，PDF **必须一页一页渲染**（`PDFRenderer` 单页 → 写 JPEG → 释放），
禁止把 10 页全部渲染进内存（10 页 × 2000×2800×3B ≈ 168MB，叠加 JVM 会触发 OOM）。

### 4.6 题号 → 页码的映射（"查看原页"怎么定位）

整页转写是按页做的，切题是按整卷文本做的，两者之间需要一个锚点：

1. 合并各页文本时在**页首**插入标记：`<<<PAGE:3>>>`；
2. 切题前把标记剥掉，但把**每个题号的起止页**算出来（`questionNo → (pageFrom, pageTo)`）；
3. `InterviewQuestionDTO` 增加 `sourcePageFrom` / `sourcePageTo`（可空），组装题目时写入；
4. 题目卡片显示「第 3 页」或「第 3–4 页」→ 调 `GET /api/papers/{id}/pages/{n}/image` 查看原页。

文字层页面同样参与映射（它本来就是按页抽的文本），所以混合 PDF 也能定位。

### 4.7 题目跨页 / 跨图怎么办

**先给结论：内容连续性天然成立，不需要"跨页拼题"这个动作。**

合并后的整卷文本是 `第1页全文 + 第2页全文 + …`，而 `splitByQuestionNo()` 只按"行首题号"切块：
第 3 题从第 3 页开始、在第 4 页结束，它仍然是一个完整的块（因为中间没有新的题号）。
`groupIntoBatches()` 只在**题与题之间**分批，单题超过批次上限时会**独占一批**，不会把一道题切成两半。

真正会出问题的是**页边界上的三件事**，必须在合并阶段处理：

| 风险 | 后果 | 处理 |
| --- | --- | --- |
| **续页重复题号**：VLM 在第 4 页顶部又写了一次「3.」或「3.（续）」 | `dedupeAndSort()` 按题号去重、**保留首个** → 第 4 页的续写内容被整块丢弃（题干/选项缺一半） | 合并时识别"与本页之前最后一个题号相同的行首题号"，**删掉题号前缀**当续文拼接，并写 warning |
| **页眉页脚混入**：姓名/学校/班级/"第 3 页 共 4 页"/网址 | 混进题干或选项，污染切题与展示 | 合并前按行清洗（正则：`第?\s*\d+\s*页`、`共\s*\d+\s*页`、纯数字行、学校/班级/姓名/学号、日期、URL） |
| **只记一个页码** | "查看原页"只能看到题干前半 | 记录 `sourcePageFrom/pageTo`，卡片显示「第 3–4 页」 |

#### 合并算法（`PageTextMerger`）

```
lastOpenQuestionNo = -1        // 截至上一页末尾"还没结束"的题号
for page in pages(按 pageNo 升序):
    lines = stripHeaderFooter(page.text)         // 去页眉页脚/页码/姓名学校
    if lines 为空: continue

    head = 第一个非空行
    m = 行首题号正则(head)
    if m != null && m.no == lastOpenQuestionNo:   // 续页重复题号
        head = 删掉 "3." / "3、" / "3.（续）" 前缀
        warnings.add("第 pageNo 页顶部重复题号 m.no，已按续页合并")

    merged.append("<<<PAGE:" + page.no + ">>>\n").append(lines.join("\n"))
    lastOpenQuestionNo = 本页最后一个题号（没有则沿用上一个）
```

配套两条：

1. **Prompt 约束**：明确告诉模型「如果本页是上一页某道题的继续，**不要重复题号**、不要补写上一页内容、直接接着写」；
2. **切题兜底**：合并后统计"行首题号序列"（现有 `splitByQuestionNo` 已经能拿到），
   在预览页显示「识别到 23 个题号（1–23 连续）」；若出现重复/缺号，确认前就提示，
   而不是等切完题才发现少了一道（对应 `docs/待优化事项.md` 1.2）。

#### 关于 `dedupeAndSort`（现有逻辑不改）

它按题号"保留首个"是为了丢弃分批重叠产生的重复抽取。跨页续写**在合并阶段就已经解决**，
所以不会走到"重复题号二选一"那一步；如果合并后仍然出现重复题号，说明页面确实被重复识别，
此时按现有规则保留首个并写 warning 是可接受的。

### 5.1 `practice_papers` 新增字段（识别任务与恢复）

```sql
ALTER TABLE practice_papers
  ADD COLUMN recognition_status VARCHAR(20) DEFAULT 'NONE',  -- NONE/PENDING/PROCESSING/NEEDS_REVIEW/READY/FAILED
  ADD COLUMN recognition_error  VARCHAR(500),
  ADD COLUMN page_count         INTEGER,
  ADD COLUMN recognition_attempt_id VARCHAR(64),            -- 与切题一致：attempt 代次防旧任务写终态
  ADD COLUMN recognition_updated_at TIMESTAMP(6),           -- 心跳/卡死恢复
  ADD COLUMN recognition_recovery_count INTEGER DEFAULT 0;
```

### 5.2 新表 `paper_pages`（页级状态，识别的唯一事实来源）

```sql
CREATE TABLE paper_pages (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  paper_id BIGINT NOT NULL REFERENCES practice_papers(id),
  page_no INTEGER NOT NULL,
  source VARCHAR(8) NOT NULL,          -- TEXT / IMAGE
  status VARCHAR(16) NOT NULL,         -- PENDING / PROCESSING / READY / FAILED
  text_content TEXT,                   -- 该页转写文本（可人工编辑）
  has_figure BOOLEAN DEFAULT false,    -- 本页是否含图（几何图/表格/插图）
  notes VARCHAR(500),                  -- 识别异常说明
  image_key VARCHAR(500),              -- 渲染/上传的页图在 S3 的 key（文字页为空）
  model VARCHAR(50),                   -- 识别用的视觉模型
  error VARCHAR(500),
  attempt INTEGER DEFAULT 0,
  updated_at TIMESTAMP(6),
  CONSTRAINT uk_paper_page UNIQUE (paper_id, page_no)
);
```

页图存 S3：`papers/{paperId}/pages/{pageNo}.jpg`（私有；通过后端接口按归属校验后读取，不暴露直链）。

**为什么按页建表**：识别是"部分成功"的典型场景——第 3 页糊了、其它 3 页是好的。
页级状态让重试、人工修正、删除页都只动一行，不用重跑整份。

## 6. 接口

全部按 `OwnerScope` 校验归属，越权统一 404（沿用现有约定）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |

## 8. 识别 Prompt（每页一次）

system prompt（由 `BeanOutputConverter` 自动追加 JSON Schema）：

```
你是试卷数字化助手。请把这一页试卷图片转成保留版式的文本。

规则：
1. 只转写印刷体内容；忽略手写答案、老师批改痕迹、印章、涂改。
2. 保留题号、选项标签（A. B. C. D.）、括号里的分值、大题与小节标题。
3. 表格转成 Markdown 表格；数学公式用 LaTeX（$...$）。
4. 不要作答、不要补全看不清的内容；无法辨认处写 [无法辨认]。
5. 页眉页脚中的姓名、学校、页码可以省略。
6. 如果整页没有可识别文字，text 返回空字符串，并在 notes 说明。
```

user prompt：

```
这是第 {pageNo} 页（共 {pageCount} 页）。
```

输出就是 §3.2 的 `PageRecognition`（`text/hasFigure/notes`）——**模型只负责"看清"，不负责"切题"**。

## 9. 失败、重试与边界

| 场景 | 处理 |
| --- | --- |
| 单页识别失败（超时/模型报错/JSON 不合法） | 该页重试 2 次（指数退避）；仍失败 → `FAILED`，其它页照常可用 |
| 部分页失败 | 预览页标红，用户可「重传该页」或「删除该页」；确认时若仍有 FAILED 页，默认阻止，可勾选「忽略失败页继续」（writing warning） |
| 整份失败（所有页失败/文件损坏） | `recognition_status=FAILED`，保留原文件，可整份重试 |
| 视觉模型未配置/模型不支持图片 | `getDefaultVisionChatClient()` 内校验 provider；抛 `BusinessException(VISION_PROVIDER_NOT_CONFIGURED)`，提示「未配置识图模型，请检查 app.ai.default-vision-provider 与 Provider 的支持图片标记」 |
| 同一页并发重试 | 页级 `PENDING→PROCESSING` 条件更新 + `attempt` 代次（与现有切题任务同模式），旧任务不能写终态 |
| 进程崩溃/重启 | `PROCESSING` 超时（如 5 分钟）由恢复调度器重置为 `PENDING` 并补投（沿用现有 recovery 模式） |
| 重复确认 | `recognition_status` 已是 `EXTRACTING/READY` 时幂等返回，不重复投递 |
| 删除到 0 页 | 拒绝（400），至少保留 1 页 |
| 页数 >10 / 单张 >50MB / 非图片 PDF 页超限 | 上传时直接拒绝并给出具体原因（第几个文件、实际页数） |

## 10. 成本与配额

| 项 | 值 |
| --- | --- |
| 单份页数 | **≤10 页**（已定） |
| 单次上传文件数 | **≤10 个**（已定） |
| 单张图片 | ≤50MB，长边 ≤2000px，JPEG q=0.85 |
| 单页重试 | ≤2 次（重试会重复计图片 token） |
| 单用户每日识别 | **50 页/天**（我暂定，见 §15；用 Redis `recognition:pages:{userId}:{yyyyMMdd}` 计数） |
| 是否调用模型 | 只有 `IMAGE` 页调用；文字层页面零成本 |

单页图片 token 约 1~2k（取决于分辨率），一份 10 页全扫描的卷子大致在 1~2 万图片 token 量级；
**具体价格以 Provider 账单为准**，本设计不写死金额。

限流沿用 `@RateLimit`：上传接口按 IP 收紧（如 5 次/小时），每日页数配额在业务层用 Redis 计数并给出
「今日剩余 X 页」的可读提示。

## 11. 安全与隐私

1. **图片会外发**到第三方视觉模型（当前为阿里云 DashScope）：首次使用需在界面/文档明确告知，不静默上传；
2. 页图存**私有 S3**，只能通过后端接口按 `owner_id` 校验后读取；不生成公开直链；
3. 删除试卷时**连带删除** `paper_pages` 与 S3 页图（复用现有删除链路，避免孤儿文件）；
4. 日志只记录 `paperId/pageNo/attempt/duration/model`，**不打印图片字节与整页文本**；
5. 页眉里的姓名/学校仍会随图片进入模型——prompt 允许省略，但**不做打码**（见 §15 的已知边界）。

## 13. 验收标准（用 `六上语文期末练习.pdf` 实测）

1. 上传该 PDF：识别出 **4 页**、判定为 4 个 `IMAGE` 页（0 字体对象），逐页渲染成功；
2. 预览页能看到每页原图与转写文本，题号连续、选项标签齐全、分值括号保留；
3. 人工对照该卷：确认后切出的**题数与总分与人工标注一致**（含跨页题干）；
4. 任选一页把文本改错再改回、重传单页、删除一页，状态与页号重排正确；
5. 断网/模型报错时该页 `FAILED`、其它页可用；重试成功后恢复 `READY`；
6. 混合 PDF（前两页文字、后两页扫描）：文字页不调用视觉模型，后两页正常识别；
7. 越权访问他人试卷的 `/recognition`、页图、确认接口 → **404**；
8. 11 页 / 第 11 个文件 / 非图片格式 → 上传即拒绝且提示具体原因；
9. 识别中重启应用：`PROCESSING` 页能被恢复调度器重新投递，不丢卷；
10. 确认后进入现有切题 → 作答 → 批改 → 报告，**不新增任何作答/判分分支**。
11. **跨页用例**：把第 3 题人为切成两页（前一页到题干中部、后一页接选项），
    确认切题后题干与选项完整、题数不变、`sourcePageFrom/To` 为 3/4，且预览提示"续页重复题号已合并"。
