## 一、目标与非目标

**做**：给业务数据加"归属人"，所有读取/写入/删除/导出入口都按归属过滤；越权访问统一返回 404。

**不做（本轮）**：
- 不做团队/班级共享（P2 再议）；
- 不改登录鉴权本身（已实现 JWT + RBAC）；
- 不做行级权限的细粒度（如"只读他人资料"）——本轮是"完全隔离"。

## 二、现状与风险

### 2.1 现状

业务表**没有任何归属列**（除了 `oral_practice_sessions.user_id` 和 `refresh_tokens.user_id`）。
实测数据库中 25 张表，与用户数据相关的 14 张全部是"全局共享"：

```
practice_papers(试卷)  paper_analyses(切题摘要)  practice_sessions(测验/练习会话)  practice_answers(作答)
knowledge_bases(资料)  knowledge_base_questions(题库)  kb_categories(分类)
rag_chat_sessions  rag_chat_messages  rag_session_knowledge_bases  rag_query_traces
vector_store(pgvector)  study_plans(学习计划)  oral_practice_*(语音)
```

### 2.2 两个必须先处理的硬伤（不只是"能看到别人数据"）

| 约束 | 现在的行为 | 后果 |
| --- | --- | --- |
| `practice_papers.file_hash` **全局 UNIQUE** | B 上传与 A 相同的试卷文件时，去重逻辑命中 A 的那条记录 | **B 直接看到/操作 A 的试卷**（连"猜 id"都不用） |
| `knowledge_bases.file_hash` **全局 UNIQUE** | 同上 | **B 上传相同资料会直接拿到 A 的资料记录**，进而读到 A 的向量库内容与问答上下文 |

还有 `kb_categories.code` 全局 UNIQUE —— 分类目前是系统级共享字典（见第五节决策点）。

**结论**：光加 `owner_id` 不够，必须同时把这两个唯一约束改成「按归属人唯一」，否则隔离是漏的。

## 三、隔离模型

### 3.1 归属语义

- 统一列名 **`owner_id`**（`BIGINT NOT NULL REFERENCES users(id)`），除 `vector_store` 外所有业务表都加（`vector_store` 通过 `kb_id` 间接隔离）。
- "谁创建谁拥有"：上传者 = 试卷/资料的所有者；发起者 = 会话/问答的所有者。
- 子表（`paper_analyses`、`practice_answers`、`knowledge_base_questions`、`rag_chat_messages`、`rag_query_traces`、`rag_session_knowledge_bases`）**不单独加 owner**，一律通过父级（paper / session / kb）过滤——避免两份真相不一致。

### 3.2 管理员的可见性（决策点 1）

建议：**默认只看自己的**；`ROLE_ADMIN` 额外可以在列表页勾选「查看全部用户数据」（显式开关，落到接口参数 `scope=all`）。
理由：管理员平时也在用平台，默认全局视图会让他分不清"我的"和"别人的"；显式开关既方便运维，又不会误操作。

### 3.3 共享数据（不加 owner）

- `roles` / `permissions` / `user_roles` / `role_permissions` / `users` / `refresh_tokens`：认证体系，已有语义；
- `llm_provider_config` / `llm_global_setting`：全局系统配置，仅 `provider:manage` 可读写；
- `kb_categories`：见决策点 2。

## 四、数据模型改动

### 4.1 加列 + 回填 + 约束

迁移分三步（同一个脚本内完成，避免长时间不可用）：

```sql
-- 1) 加可空列（避免大表加 NOT NULL 直接锁表）
ALTER TABLE practice_papers   ADD COLUMN owner_id BIGINT REFERENCES users(id);
ALTER TABLE practice_sessions ADD COLUMN owner_id BIGINT REFERENCES users(id);
ALTER TABLE knowledge_bases   ADD COLUMN owner_id BIGINT REFERENCES users(id);
ALTER TABLE rag_chat_sessions ADD COLUMN owner_id BIGINT REFERENCES users(id);
ALTER TABLE study_plans       ADD COLUMN owner_id BIGINT REFERENCES users(id);
ALTER TABLE oral_practice_sessions ADD COLUMN owner_id BIGINT REFERENCES users(id);

-- 2) 存量数据回填（见决策点 3，默认划给 admin）
UPDATE practice_papers SET owner_id = (SELECT id FROM users WHERE username='admin') WHERE owner_id IS NULL;
-- 其余表同理

-- 3) 唯一约束从"全局"改成"按归属人"
ALTER TABLE practice_papers DROP CONSTRAINT idx_practice_paper_hash;
CREATE UNIQUE INDEX idx_practice_paper_owner_hash ON practice_papers (owner_id, file_hash);
ALTER TABLE knowledge_bases DROP CONSTRAINT idx_kb_hash;
CREATE UNIQUE INDEX idx_kb_owner_hash ON knowledge_bases (owner_id, file_hash);

-- 4) 查询索引
CREATE INDEX idx_practice_papers_owner ON practice_papers (owner_id);
CREATE INDEX idx_practice_sessions_owner ON practice_sessions (owner_id);
CREATE INDEX idx_knowledge_bases_owner ON knowledge_bases (owner_id);
```

> 回填后再单独一个脚本把 `owner_id` 置为 `NOT NULL`（可选；建议保留可空以兼容历史数据，由代码层做"无归属视为不可访问"处理）。

### 4.2 不需要改的表

`paper_analyses` / `practice_answers` / `knowledge_base_questions` / `rag_chat_messages` / `rag_query_traces` / `rag_session_knowledge_bases` / `vector_store`：通过父级过滤。

## 五、访问控制实现方案

三个候选，**推荐 A**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 服务层集中守卫 + 带 owner 的查询（推荐）** | 新增 `OwnerGuard`（取当前用户 id、`requireOwnedPaper(id)` 等）；Repository 增加 `findByIdAndOwnerId` 风格方法；所有列表查询强制带 owner | 改动点集中、可读、易测试；缺点是要逐个人工过一遍入口（29 个 Service） |
| B. JPA `@Filter` 自动注入 owner 条件 | 实体上加 `@FilterDef/@Filter`，在 Web 请求内启用 | 代码最少，但**异步/后台线程（消费者、调度器、恢复任务）没有请求上下文**，容易漏或误伤；调试困难 |
| C. 数据库 RLS（Row Level Security） | 用 `SET LOCAL app.user_id` + 策略 | 最安全，但每条连接/事务都要设置会话变量，与连接池、Redis 消费线程叠加后复杂度高，运维成本大 |

**A 的落地细节**：

1. `common/security/OwnerGuard`（或放 `modules/auth/security`）：
   - `Long currentOwnerId()` → 从 `CurrentUserHolder` 取，未登录抛 401；
   - `boolean isAdmin()`；
   - `void requirePaper(Long id)` / `requireKnowledgeBase(Long id)` / `requireSession(String sessionId)`：查不到**或不属于当前用户**时统一抛 `BusinessException(ErrorCode.NOT_FOUND, "资源不存在")`。
2. Repository 统一改为"带 owner"：
   `findByIdAndOwnerId`、`findByOwnerIdOrderBy...`、`countByOwnerId`、`deleteByIdAndOwnerId`；
   `@Query` 里的 `where` 全部追加 `and t.ownerId = :ownerId`。
3. **写入路径**：创建时由统一入口注入 owner（`OwnerGuard.currentOwnerId()`），禁止由前端传 ownerId。
4. **越权返回 404 而不是 403**：403 会暴露"这条记录存在"，404 更安全。

## 七、异步与后台任务

| 场景 | 处理 |
| --- | --- |
| Redis Stream 消费者（切题 / 向量化 / 出题 / 评估） | **入队时已校验归属**，消费端只按 id 处理即可，不重复校验（否则后台线程没有用户上下文）；但要把 owner 一起写进 payload 便于排查 |
| 卡死任务恢复调度器 | 按 id 扫描，语义不变；日志里带 ownerId |
| Redis 会话缓存（`sessionCache`） | 缓存 key 仍是 sessionId；**读取时必须经过服务层的 `requireSession`**，不能直接信任缓存 |
| 向量化 / 出题任务 | 任务 payload 不需要 owner，但生成的数据落在带 owner 的 kb / 会话下 |

## 八、前端影响

基本**不需要改数据逻辑**（后端过滤后自然只看自己的），需要的是体验细节：

1. 越权/已删除资源 → 后端返回 404 → 前端展示"资源不存在或无权访问"，并给"返回列表"按钮（现有的 404 分支已具备）；
2. 新用户所有列表为空 → 空态文案已有（试卷/资料/记录/错题本各有空态）；
3. 管理员「查看全部」开关（决策点 1 若选"可见全部"）需要在列表页加一个 scope 切换；
4. 用户管理页（`/admin/users`）不受影响。

## 九、迁移与上线

1. **先上后端**（加列 + 过滤 + 校验），此时行为是"只看自己的"，但旧数据仍属 admin；
2. 观察 1~2 天，确认没有越权报告；
3. 可选：把 `owner_id` 置 `NOT NULL`、删除临时兼容分支。

**回滚**：只回滚代码、保留列即可（列的默认值为 NULL，代码旧版本不读它）——所以加列脚本不需要回滚。

### 10.1 越权用例矩阵（必须逐条通过）
