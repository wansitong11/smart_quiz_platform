# 视觉识别失败重试反馈与切题状态修复 - 设计稿

> 用途：审批用设计稿。针对 `paperId=38` 第 8 页坐标结构错误、第 2 页传输超时、
> 以及「识别未确认却被切题恢复器补投」三个问题。
> 状态：待审批，未实施。
> 前置事实：2026-10-30 本地日志与数据库；`paperId=38`，文件
> `四年级（上）语文第五单元情景测试卷-_.pdf`，共 8 页。
> 关联设计：`视觉调用稳定性改造-设计稿.md`、`题干图一致性与识别失败诊断-设计稿.md`、
> `试卷上传统一与高并发改造-设计稿.md`。

## 0. 结论摘要

本次不是要再叠一层「多试几次」，而是把视觉识别失败后的处理拆成三条明确规则：

1. 识别前把坐标格式说死，让模型第一次就更可能输出正确结构；
2. 识别后如果结构错，把「哪一行、哪个字段、期望什么、实际是什么」带回下一次请求；
3. 连续纠错仍失败时，不再整页盲目重抽，改为「先拿文字、再按需拿图形坐标」的两阶段兜底。

同时修两个独立问题：

- 第 2 页那种连接中断只重试一次有界重试，不无限等待；
- 识别完成但用户还没确认时，后台恢复器不能误判成「切题卡住」而提前切题。

本轮不引入新视觉模型，不改 Redis 生产消费协议。

## 1. 验收用例（先看用法）

### 1.1 正常扫描卷

用户上传一份 8 页扫描试卷。识别完成后：

- 第 3 页显示「已完成」，其余文字页正常进入校对；
- 第 8 页即使第一次坐标结构错误，也会在带原因重试或两阶段兜底后得到可用文字；
- 第 2 页遇到连接中断时只补一次短退避重试，仍失败则明确标记该页失败；
- 整卷停留在「等待校对」，不会自动开始切题。

### 1.2 坐标错误样本

模型把某一行的坐标写成字符串。系统应：

- 第一次失败不返回泛化「请稍后重试」；
- 下一次请求带上「哪一行坐标的哪个位置、期望数字、收到什么」的纠正说明；
- 纠错后再失败，自动用「先文字、后图形坐标」的方式保住文字；
- 如果页面确实有图但拿不到可用图形坐标，标记该页失败，并给出可读原因，而不是伪造坐标。

### 1.3 未确认不切题

用户上传后超过 10 分钟还没点「确认切题」。系统应：

- 页面识别状态仍停在「等待校对」；
- 后台恢复器不会把该卷当切题卡住任务补投；
- 分析状态不会因为补投失败而变成「失败」。

## 2. 背景与证据

`paperId=38` 本次真实状态：

- 第 1、3、4、5、6、7 页识别完成；
- 第 2 页失败：约 60 秒后连接中断；后续固定样本直连 Provider 实测完整识别约 109 秒，
  因此实际是 Spring AI 默认 60 秒请求超时覆盖了应用配置，而不是 Provider 的 60 秒边界；
- 第 8 页失败：模型连续三次返回结构不合法的坐标；
- 整卷识别状态为「等待校对」，但 13:38:08 被切题恢复器误补投，最终整卷分析状态变成「失败」。

第 8 页错误路径：

```text
lines[8].bbox[3]
invalidValue="bbox"
targetType=double
```

第三次变为：

```text
lines[2].bbox[3]
invalidValue="text"
targetType=double
```

含义是模型把坐标数组写成了字符串，而不是四个数字。当前程序在反序列化阶段直接失败，重试提示也只是
泛泛地要求「返回合法 JSON」，模型不知道具体错在哪一行，于是连续重复同类错误。

第 2 页错误链：

```text
OpenAIIoException
  <- InterruptedIOException
  <- IOException
```

当前传输类失败默认不原地重试，所以第 2 页只调用一次就失败。此前同一份文件的第 2 页曾经成功，因此
不能认定是页面损坏，更像网络、代理或服务端响应边界。

第 3 页在本次任务实际已成功，数据库状态为「已完成」。若界面仍显示第 3 页失败，属于上一次任务的旧状态
或前端未刷新，不是本次后端新缺陷；本轮不给第 3 页单独写修复代码。

## 3. 目标与非目标

### 3.1 目标

- 识别前约束坐标格式，降低结构错误出现概率；
- 结构错误重试时携带具体位置与期望类型，不再只提示「返回合法 JSON」；
- 多次纠错仍失败时，用两阶段兜底保住文字，并保持页面失败原因可读；
- 传输超时只做一次有界重试，且不绕过现有并发保护；
- 识别流程与切题流程状态分离，未确认的试卷不会被恢复器误切；
- 视觉链路关键日志可持久化，跨重启仍能查到失败页。

### 3.2 非目标

- 不引入新的视觉模型或备用模型；
- 不改上传、切题、作答、批改、报告的对外契约；
- 不改 Redis Stream 生产消费协议；
- 不修改 `paper_assets` 表结构和存量图片；
- 不把非法坐标字符串静默转换成合法坐标；
- 不为第 3 页编写没有复现依据的前端修复。

## 4. 业务设计

### 4.1 识别前把坐标契约说死

识别提示中新增明确约束：

- 每一行坐标必须是恰好 4 个数字组成的数组，数字范围 0 到 1；
- 坐标数组内不能出现字段名、字符串、对象或空值；
- 给出正确示例和错误示例，点名当前最常出现的两类错误：
  - 把坐标写成 `["bbox", "text"]`；
  - 把「文字」和「坐标」两个字段位置写反。

该规则同时适用于每一行的坐标和图形、表格、选项行等资源的坐标。

### 4.2 带具体原因的重试

结构解析失败后，把解析错误转成一条可执行的纠正指令，而不是泛化提示。例如：

> 上一次输出的第 9 行文字坐标的第 4 个位置期望是一个 0 到 1 的数字，但收到字符串
> `"bbox"`。请把该行坐标改成 4 个数字组成的数组，并保持该行文字是字符串。

规则：

- 只把「位置、期望类型、收到的短值」放入下一次提示；
- 不把整段模型原始输出、异常堆栈或图片识别出的长文本放回提示；
- 原始输出仍然只进诊断日志，不进模型提示。

### 4.3 两阶段兜底

带原因重试后如果结构仍然错，不再继续整页重抽，改用「先文字、后图形坐标」：

1. 先做一次纯文字识别，不要求任何坐标；
2. 如果识别结果不需要图形资源，直接完成该页；
3. 如果结果表示页面有图，再做一次图形坐标定位；
4. 图形坐标仍失败时，标记该页失败，并给出可读原因。

这样即使模型总在坐标字段上出错，文字内容也能被保住。该兜底默认开启，但只针对结构错误触发；
普通识别仍走原有路径。

### 4.4 传输超时的单次有界重试

连接中断或响应超时属于传输问题，不代表模型输出有错。规则：

- 每个失败页最多补一次重试，重试前做短退避和随机抖动；
- 重试仍失败则标记该页失败，不继续消耗预算；
- 重试仍受单页调用预算和全局视觉并发保护约束，不绕过限流。

这样比「一断就失败」更稳健，也比「无限重试」更可控。

### 4.5 识别与切题状态分离

识别完成后、用户确认前，系统只应处于「等待校对」。只有用户确认切题后，才允许进入「切题处理中」。

后台恢复器判断「切题卡住」时必须同时满足：

- 任务已经进入切题状态（识别状态为 `EXTRACTING`，或纯文字卷保持 `NONE`）；
- 切题所需的正文已经准备好（`resumeText` 非空）。

仅凭「分析任务处于待处理」不能补投切题。

### 4.6 诊断日志可持久化

视觉链路日志目前只写控制台，应用重启后失败页的原始信息会丢失。调整为：

- 保留完整、不做脱敏的本地诊断日志，包括模型原始回包、解析路径、页状态和异常链；
- 日志同时写文件，并做大小和数量限制；
- 失败记录补充「耗时、实际超时值、失败类别、页码、尝试次数」，但不记录密钥和令牌。

## 5. 边界与异常

| 场景 | 行为 | 是否重试 |
| --- | --- | --- |
| 坐标结构第一次错误 | 记录结构错误与反馈，进入带原因重试 | 是，单阶段预算内 |
| 连续两次单阶段结构错误 | 进入两阶段兜底 | 兜底独立计预算 |
| 两阶段兜底后仍失败 | 该页失败，给出可读原因 | 用户可手动重试该页 |
| 页面无图但坐标错误 | 两阶段兜底可只做文字识别，不算失败 | 按兜底规则 |
| 页面有图且图形坐标拿不到 | 不伪造坐标，该页失败 | 用户可手动重试 |
| 连接中断 / 响应超时 | 短退避后补一次 | 是，每页最多 1 次 |
| 限流 | 按现有退避规则重试 | 按现有规则 |
| 未确认的识别卷 | 恢复器不得补投切题 | 否 |
| 已确认且正文就绪 | 恢复器可补投，正常切题 | 按现有恢复规则 |
| 密钥 / 额度 / 模型不存在 | 立即失败 | 否 |

## 6. 可改点

- 想调整「带原因重试」次数：改结构错误连续触发兜底的阈值；
- 想控制两阶段兜底成本：改兜底是否开启、兜底最多调用次数；
- 想调整传输超时重试：改传输重试是否开启、重试次数与退避时长；
- 想调整恢复器误判边界：改「何时才算切题卡住」的判断条件；
- 想调整诊断日志量：改日志文件大小、保留数量和最低级别；
- 想调整坐标范围：改坐标是否允许数字字符串，以及坐标最大允许偏差。

### 7.2 精确调用预算与状态机

先消除矛盾：**「现有单页视觉调用总预算保持不变」只指单阶段预算不变（`maxVisionCallsPerPage`，
默认 3）。两阶段兜底是额外预算（`invalidOutputFallbackMaxCalls`，默认 2）。单页 provider 调用
硬上限 = 3 + 2 = 5。** 这个硬上限是显式允许的，不再与「总预算不变」冲突。

单阶段循环局部状态（每个页独立、不跨页累积）：

```text
int calls = 0;                    // 单阶段 provider 调用次数
int invalidStreak = 0;            // 连续 INVALID_OUTPUT 次数
boolean transportRetried = false; // 本页是否已做过传输重试
JsonFailureFeedback lastFeedback = null;
```

单阶段循环，条件 `calls < maxVisionCallsPerPage`：

```text
1. calls++
2. 调一次单阶段识别（invokeVisionOnceWithoutSchemaValidation）
3. 成功且内容校验通过 -> 返回结果
4. 失败，classify(e)：
   a. INVALID_OUTPUT:
      invalidStreak++
      lastFeedback = JsonFailureFeedbackFormatter.extract(e)
      if invalidStreak >= invalidOutputRetryThreshold -> 跳出，进入两阶段兜底
      else -> 继续循环（下一次带 lastFeedback）
   b. TRANSIENT_TIMEOUT:
      if transportRetryEnabled && !transportRetried && calls < maxVisionCallsPerPage
          -> transportRetried = true; 退避(transportRetryBackoffBase + 随机抖动 0..500ms); 继续循环
      else -> 抛异常，页 FAILED
   c. RATE_LIMITED -> rateLimitBackoff(attempt); 继续循环（现有行为）
   d. INCOMPLETE_CONTENT -> 继续循环（现有定向重抽）
   e. TERMINAL -> 抛异常，页 FAILED
5. 任何非 INVALID_OUTPUT 的失败 -> invalidStreak = 0
```

补充：`UnexpectedEndOfInputException` 现归为 `OUTPUT_TRUNCATED`，单阶段最多做一次减少输出的定向重试；
超过后按现有配置进入两阶段兜底或直接失败。

边界：若 `invalidOutputRetryThreshold` 被配置得大于单页单阶段预算，则在最后一次
单阶段调用仍是 INVALID_OUTPUT 时也直接进入兜底，避免预算耗尽后没有可执行的下一步。

两阶段兜底（仅当 `invalidStreak >= invalidOutputRetryThreshold` 且
`invalidOutputFallbackEnabled == true` 且 `twoStageRecognitionEnabled == false`）：

```text
fallbackCalls = 0
1. ocrBudget = invalidOutputFallbackMaxCalls > 1
       ? invalidOutputFallbackMaxCalls - 1 : 1
   requestPageOcr(..., maxCalls = ocrBudget)
   该内部循环沿用同一套反馈重试 / 传输重试规则，并始终为几何阶段预留 1 次调用
2. OCR 无视觉内容 -> 用纯文字组装 PageRecognition，返回（页 READY）
3. OCR 有视觉内容:
   remaining = invalidOutputFallbackMaxCalls - ocrCalls
   if remaining < 1 -> 页 FAILED（"OCR 后没有足够预算定位图片"）
   else requestPageGeometry(..., maxCalls = remaining)
      成功 -> 组装结果返回
      失败 -> 页 FAILED，错误文案说明"文字已保留，但图形坐标定位失败，请重试该页"
```

当 `twoStageRecognitionEnabled == true` 时，页面本来就整体走 `recognizeInTwoStages`，
不经过单阶段循环，因此「INVALID_OUTPUT → 兜底」不适用；但反馈重试与传输重试同样应用于
`requestPageOcr` / `requestPageGeometry` 两个内部循环。

### 7.3 两阶段开关真值表

保留现有 `twoStageRecognitionEnabled`（默认 `false`），新增 `invalidOutputFallbackEnabled`
（默认 `true`）。两者独立：

| twoStageRecognitionEnabled | invalidOutputFallbackEnabled | 行为 |
| --- | --- | --- |
| false | false | 只跑单阶段；INVALID_OUTPUT 仅在单阶段预算内带反馈重试，不兜底 |
| false | true（默认） | 单阶段为主；连续 INVALID_OUTPUT 达到阈值后进入兜底 |
| true | false | 整页走两阶段；兜底开关无效 |
| true | true | 整页走两阶段；兜底开关无效 |

### 7.4 恢复器精确查询条件

现状：`findStaleByAnalysisStatus` 只按 `analysisStatus + analysisUpdatedAt` 扫描，
不区分「未确认识别卷」与「已确认切题卷」；`touchQueuedAnalyzeForRecovery` 只判断
`analysisStatus='PENDING'`。这是 13:38 误补投的根因。

修复：新增专用查询 `findStaleExtractableByAnalysisStatus`，并让恢复器改用它；同时给
`touchQueuedAnalyzeForRecovery` 与 `resetStaleAnalyzeProcessing` 加上相同守卫（原子一致性）。

统一守卫条件：

```text
resumeText IS NOT NULL AND TRIM(resumeText) <> ''
AND recognitionStatus IN ('NONE', 'EXTRACTING')
```

新增查询方法（`ResumeRepository`）：

```java
@Query("""
    SELECT r FROM PracticePaperEntity r
    WHERE r.analysisStatus = :status
      AND r.resumeText IS NOT NULL AND TRIM(r.resumeText) <> ''
      AND r.recognitionStatus IN ('NONE', 'EXTRACTING')
      AND r.analysisUpdatedAt < :threshold
    ORDER BY r.analysisUpdatedAt ASC
""")
List<PracticePaperEntity> findStaleExtractableByAnalysisStatus(
    @Param("status") AsyncTaskStatus status,
    @Param("threshold") LocalDateTime threshold,
    Pageable pageable);
```

说明：

- `recognitionStatus IN ('NONE', 'EXTRACTING')` 用字符串字面量，Hibernate 会与枚举列比较；
  覆盖「纯文字直接切题（NONE）」与「扫描卷已确认切题（EXTRACTING）」两条合法路径。
- 未确认的扫描卷 `recognitionStatus ∈ {PENDING, PROCESSING, NEEDS_REVIEW}` 且 `resumeText=null`，
  被上述条件自然排除。
- `TRIM(r.resumeText) <> ''` 排除正文为空串的边界（确认流程本就会拒绝空文本，此处是双保险）。

`touchQueuedAnalyzeForRecovery` 追加：

```java
+ "AND r.resumeText IS NOT NULL AND TRIM(r.resumeText) <> '' "
+ "AND r.recognitionStatus IN ('NONE','EXTRACTING')"
```

`resetStaleAnalyzeProcessing` 追加同样的两行条件（在 `analysisStatus='PROCESSING'` 后）。

恢复器 `PaperExtractionRecoveryScheduler.recoverStuckTasks` 两处
`findStaleByAnalysisStatus` 调用均替换为 `findStaleExtractableByAnalysisStatus`，其余逻辑不动。

### 7.5 错误反馈格式化组件

新文件 `app/src/main/java/interview/guide/common/ai/JsonFailureFeedback.java`：

```java
package interview.guide.common.ai;

/** 从 Jackson 解析异常提取的、可写进下次 Prompt 的最小纠正信息。 */
public record JsonFailureFeedback(
    String location,  // 例如 "lines[8].bbox[3]"
    String expected,  // 例如 "数字（double）"
    String actual     // 例如 "\"bbox\""（已截断）
) {}
```

新文件 `app/src/main/java/interview/guide/common/ai/JsonFailureFeedbackFormatter.java`：

```java
public final class JsonFailureFeedbackFormatter {
  public static JsonFailureFeedback extract(Throwable error) { /* 见下 */ }
  public static String toInstruction(JsonFailureFeedback f, int maxChars) { /* 见下 */ }
}
```

`extract` 规则：

1. 沿 `getCause()` 链找第一个 `tools.jackson.databind.JsonMappingException`；
   找不到返回 `null`。
2. `location`：取 `ex.getPath()`（`List<JsonMappingException.Reference>`），
   按顺序渲染：字段名 → `.<name>`，索引 → `[<index>]`，拼接成 `lines[8].bbox[3]`；
   若 path 为空则用 `"<unknown>"`。
3. `expected`：若 `ex instanceof InvalidFormatException`，用
   `((InvalidFormatException) ex).getTargetType().getTypeName()`，`double` 渲染为
   `"数字（double）"`，`int` 渲染为 `"整数（int）"`，其他类型直接 `getTypeName()`；
   非 `InvalidFormatException` 则用 `"可解析的 JSON 值"`。
4. `actual`：`InvalidFormatException` 用 `((InvalidFormatException) ex).getValue()`，
   `String.valueOf(value)` 后首尾截断到 40 字符，字符串值保留双引号；
   非 `InvalidFormatException` 用 `""`。
5. 任何步骤抛异常或字段为 `null`，回退为「保守默认值」，不抛新异常。

`toInstruction` 规则：

```text
"上一次输出的 " + location + " 期望是 " + expected + "，但收到 " + actual
 + "。请把该字段改成正确类型；text 必须是字符串，bbox 必须是恰好 4 个数字组成的数组。"
```

先截断 `actual`（40 字符），再截断整句到 `maxChars`（默认 200），超长在字符边界截断并加 `…`。
完整原始回包、堆栈、长文本不得进入该方法输出。

`VisionFailureClassifier` 保留现有 `JacksonException -> INVALID_OUTPUT` 映射，并优先把
`UnexpectedEndOfInputException` 映射为 `OUTPUT_TRUNCATED`。

### 7.6 重试提示接口改造

`PaperPageVisionRecognizer` 当前 `retryInstruction(VisionFailureClass)` 只接收失败类别，
异常对象在 catch 后被丢弃（`PaperPageVisionRecognizer.java` 约 399-409）。

改为：

```java
private String retryInstruction(VisionFailureClass failureClass, JsonFailureFeedback feedback)
```

规则：

- `failureClass == null` → 返回 `""`。
- `INVALID_OUTPUT`：
  - `feedback != null` → `"\n上一次输出解析失败：" + JsonFailureFeedbackFormatter.toInstruction(feedback, feedbackMaxChars) + " 请严格按格式要求重新返回 JSON。"`
  - `feedback == null` → 退回固定文案，但仍点名坐标（不再只写「返回合法 JSON」）：
    `"\n上一次输出无法解析。请只返回严格 JSON，并确保 text 是字符串、bbox 是恰好 4 个数字组成的数组。"`
- `INCOMPLETE_CONTENT` → 现有定向重抽文案不变。
- `OUTPUT_TRUNCATED` → 提示“上一次输出在 JSON 完整闭合前被截断”，要求减少非必要内容、只返回
  `lines` 和必要字段、不要重复整页 `text`，并确保 JSON 完整结束。
- 其余 → `""`。

三个循环（单阶段 / OCR / 几何）各自维护局部 `JsonFailureFeedback lastFeedback`：

- 每次 `INVALID_OUTPUT` 失败时用 `extract(e)` 覆盖；
- 每次非 `INVALID_OUTPUT` 失败或成功返回时置 `null`；
- 下一次调用构造 `userPrompt` 时传入当前 `lastFeedback`。

### 7.11 调用链

结构错误反馈路径：

```text
PaperPageVisionRecognizer.recognizeInOneStage
  -> StructuredOutputInvoker.invokeVisionOnceWithoutSchemaValidation
      -> convertWithRepair 抛 Jackson 异常 -> invoke 抛 BusinessException(..., lastError)
  -> VisionFailureClassifier.classify -> INVALID_OUTPUT
  -> JsonFailureFeedbackFormatter.extract(lastError)
  -> retryInstruction(INVALID_OUTPUT, feedback)
  -> 下一次视觉调用带上具体纠正指令
```

两阶段兜底路径（结构错误连续达到阈值后）：

```text
invalidStreak >= invalidOutputRetryThreshold
  && invalidOutputFallbackEnabled
  && !twoStageRecognitionEnabled
  -> requestPageOcr(maxCalls=invalidOutputFallbackMaxCalls)
      -> 无视觉内容 -> 组装 PageRecognition，完成
      -> 有视觉内容 -> requestPageGeometry(maxCalls=remaining)
          -> 成功 -> 组装结果
          -> 失败 -> 该页 FAILED + 诊断
```

传输超时重试路径：

```text
BusinessException -> classify -> TRANSIENT_TIMEOUT
  -> !transportRetried && transportRetryEnabled -> 退避 + 抖动 -> 继续
  -> 已重试过 / 开关关闭 -> 该页 FAILED
```

恢复器路径：

```text
PaperExtractionRecoveryScheduler.recoverStuckTasks
  -> findStaleExtractableByAnalysisStatus(仅「正文就绪 + NONE/EXTRACTING」)
  -> touchQueuedAnalyzeForRecovery / resetStaleAnalyzeProcessing(同守卫)
  -> producer.sendExtractTask(paperId)
```
