# 视觉调用稳定性改造 - 设计稿

> 用途：审批用设计稿。针对「视觉识别超时 / 重复请求 / 无 provider 隔离」的稳定性改造。
> 状态：P1 / P2 / P3A 已在当前工作区实施；两阶段识别默认关闭（2026-10-29）。
> 前置事实：以当前工作区代码为准；`paperId=34` 第 3 页真实样本验收仍待执行。

当前实现边界：

- 失败分类、单次视觉入口、总调用预算、有界准入与熔断已接入三条视觉链路；
- OCR / 资源几何两阶段由 `PaperPageVisionRecognizer` 编排，几何失败不会重新 OCR；
- 页级并行只发生在单卷内部，Redis 仍是一份试卷一条 `paper:recognition` 消息；
- 继续使用单一默认 vision provider，不引入备用 provider 或 fallback；
- `app.paper.recognition.two-stage-recognition-enabled` 默认 `false`，需固定样本验收后再开启。

---

## 0. 结论摘要

当前视觉识别问题不是裁图、数据库或资源保存失败，而是**Spring AI 每个请求的 60 秒默认超时覆盖了
应用配置的视觉请求超时**；同一固定样本直连 Provider 可正常完成，耗时约 109 秒，但本地客户端在 60 秒
就取消了请求。超时后原样重试又会放大等待，并最终触发熔断。再叠加**单 provider 缺少并发隔离与背压**。
所以修复顺序是：

1. 先建立失败分类与总重试预算，停止乘法重试；
2. 再把视觉识别拆成「OCR 文本」与「资源几何」两阶段，降低单次输出；
3. 然后给单一 vision provider 加并发上限、有界队列与熔断（本轮不引入新 provider、不做 fallback）；
4. 最后才把整卷串行处理拆成页级并行，为高并发做准备；第一步只做「单卷内页级并行」（3.5A），
   不改变 Redis 生产消费协议。

本设计不改动前端识别预览、确认切题、作答批改等既有契约；页面失败仍通过 `page.error` 给安全文案。

## 1. 背景与问题定位

### 1.1 触发案例

- 2026-10-29 实测 `paperId=34`，文件 `四年级（上）语文第五单元情景测试卷-_.pdf`。
- 第 3 页最终 `FAILED`、`attempt=2`，无文本、无 `paper_assets`；其余 7 页 `READY`。
- 日志显示该页视觉调用两次都在约 60 秒返回 `OpenAIIoException`，原页图清晰。
- 用同一固定样本直连 Provider 可正常返回 HTTP 200，完整识别约 109 秒；因此不是 Provider 在 60 秒
  边界失败，而是 Spring AI 的 `OpenAiChatOptions` 默认超时覆盖了本地 Client 超时。
- 已确认不是渲染、OCR 输出为空、资源裁切或落库失败；是本地视觉请求过早取消，连续取消再触发熔断。

### 1.2 当前调用链

```text
PaperRecognitionStreamConsumer（AbstractStreamConsumer，单线程）
  └─> PaperRecognitionService.processPaper（按页串行）
        └─> recognizePage
              └─> for attempt in 1..MAX_RECOGNITION_ATTEMPTS(=2)
                    └─> StructuredOutputInvoker.invokeWithoutSchemaValidation
                          └─> for attempt in 1..structuredMaxAttempts(默认=2)
                                └─> ChatClient.prompt().system().user(media).call()
```

### 1.3 根因

1. **重试乘法**：`PaperRecognitionService` 页级最多 2 次，`StructuredOutputInvoker` 默认再乘 2 次；
   运输超时和 JSON 格式错误没有区分，都在原地重试。
2. **单次输出过重**：一页请求同时要求整页文本、每一行 bbox、图形/表格资源、锚点与备注，
   长输出更容易超时或被截断。
3. **配置超时曾经没有真正生效**：Spring AI 每次请求都会用 `OpenAiChatOptions.getTimeout()` 覆盖
   底层 `OpenAIClient` 的超时，而该选项自带 60 秒默认值。只配置 `ApiPathResolver` / `ClientOptions`
   的 `app.ai.vision-request-timeout` 不够，必须在构建 `OpenAiChatOptions` 时显式同步同一超时值。
   固定样本完整识别约 109 秒，默认值设为 3 分钟，避免 2 分钟边界只剩约 11 秒余量。
4. **超时不能靠重复请求解决**：只有一个默认 vision provider，本轮也不引入备用 provider；
   修复本地超时后仍应保留失败分类与熔断，避免 Provider 真正不可用时重复放大等待。
5. **缺少背压**：`PaperRecognitionStreamConsumer` 只有一个工作线程，整卷按页串行；
   未来提高并发前如果没有 provider 并发上限，会把单页慢放大成整批同时慢。

## 2. 目标与非目标

### 目标

- 视觉调用失败后产生可读、安全的原因，内部保留失败分类与 provider 信息。
- 单页遇到运输超时时，不重复同一请求；按失败类别走一次修复 / 退避重试，不切换 provider。
- 通过两阶段识别降低单次输出长度，降低超时与截断概率。
- 为高并发建立页级幂等任务、有界并发与背压。

### 非目标

- 不改上传合并入口、切题、作答、批改、报告契约。
- 不引入新的 OCR / 图像处理框架；几何仍复用现有 `PageGeometry`、`PageRecognitionValidator` 与
  各 `Paper*Resolver`。
- 不做 provider 降级 / fallback；本轮保持单一默认 vision provider，失败时直接返回可读原因。
- 不改变 `paper_assets` 的归属语义与 fail-fast 原则。

## 3. 详细设计

### 3.1 失败分类

新增内部枚举（建议放 `common/ai` 或 `resume` 模块，取决于是否被文本链路复用）：

```java
enum VisionFailureClass {
  TRANSIENT_TIMEOUT,
  RATE_LIMITED,
  INVALID_OUTPUT,
  OUTPUT_TRUNCATED,
  INCOMPLETE_CONTENT,
  TERMINAL
}
```

分类依据：

| 类别 | 判定 | 行为 |
| --- | --- | --- |
| `TRANSIENT_TIMEOUT` | 异常类型链命中 `OpenAIIoException / SocketTimeoutException / HttpTimeoutException / TimeoutException / ResourceAccessException` | 不切换 provider，也不原地重发同一请求；直接安全失败该页（见 §3.2） |
| `RATE_LIMITED` | HTTP 429 或 SDK 限流状态码 | 有限次退避 + 抖动，不再换同一请求重试 |
| `INVALID_OUTPUT` | JSON / schema 解析失败 | 使用修复提示重试，带上限 |
| `OUTPUT_TRUNCATED` | `UnexpectedEndOfInputException`，JSON 在结束前被截断 | 只做一次减少输出的定向重试 |
| `INCOMPLETE_CONTENT` | `PageRecognitionValidator` 判为缺内容 / 缺资源 / 缺布局 | 页级定向重抽，禁止重复同一 prompt |
| `TERMINAL` | 密钥、额度、模型不存在、未配置 | 立即失败，不重试 |

规则：**分类基于异常类型、HTTP 状态码和本地校验结果，不从上游原始 message 做字符串猜测**。
原始 message 只作为 `BusinessException` cause 保存，不进入日志和页面文案；
日志只记录可结构化的安全诊断字段，例如 Jackson 的 `path / invalidValue / targetType`。

### 3.2 重试预算

把「页级重试」和「调用器重试」合并成一个显式预算，避免乘法：

- 已实现每页视觉 provider 调用总预算 `app.paper.recognition.max-vision-calls-per-page`，默认 3；
- 两阶段模式下 OCR 最多使用「总预算 - 1」，始终为资源几何保留至少 1 次调用；
- 每类失败单独设置上限（同一 provider）：
  `INVALID_OUTPUT` 最多 1 次修复重试，`INCOMPLETE_CONTENT` 最多 1 次定向重抽，
  `OUTPUT_TRUNCATED` 最多 1 次减少输出的定向重试，
  `RATE_LIMITED` 带抖动退避重试，`TRANSIENT_TIMEOUT` 不原地重试、直接安全失败；
- `StructuredOutputInvoker` 为视觉链路提供「单次、不重试」入口，由调用方控制 fallback 与预算；
  文本链路继续沿用现有重试语义，减少对其它模块的回归面。

关键行为：**运输超时绝不允许连续两次发出完全相同的请求**。

### 3.3 两阶段识别

拆成两次更小、更专一的视觉请求：

1. **Pass A：整页 OCR**
   - 输入：页图 + 系统提示。
   - 输出：整页文本、`hasFigure`、题号 / 材料锚点；**不输出每一行的 bbox**。
   - 输出长度设置明确上限（如 8000 字符），超出视为 `INCOMPLETE_CONTENT`。
2. **Pass B：资源几何**
   - 仅在 `hasFigure=true` 或文本引用图 / 表 / 选项行时执行。
   - 输入：页图 + Pass A 文本 + 已识别锚点。
   - 输出：`FIGURE / TABLE / OPTION_ROW` 的 bbox、role、锚点和归属，**不要求整页所有行坐标**。

编排：

```text
Pass A 成功 ──没有视觉内容──> 组装 PageRecognition ──> Validator ──> READY
     │
     └─有视觉内容─> Pass B 成功 ──> 组装 PageRecognition ──> Validator ──> READY
                 │
                 └─失败──> 仅重试 Pass B（复用 A 文本，预算内）──> 仍失败──> FAILED
```

约束：

- Pass B 失败时**不能重新 OCR**，也不能把「有图但无资源」的页面置为 `READY`。
- Pass A 成功但 Pass B 失败时，默认不把半成品直接作为可校对文本；是否保留 OCR 草稿见 §6 开放问题。
- `PageRecognition` 可由两个新 DTO 组装，保持现有持久化结构与前端读取兼容。

### 3.4 单 Provider 背压与熔断

本轮不引入新的 vision provider，也不做 provider fallback，继续使用
`llmProviderRegistry.getDefaultVisionChatClient()`。

- 已新增 `VisionRequestGuard`（轻量组件）：
  - `max-in-flight`：并发上限，建议 2~4，按供应商配额与机器内存定；
  - `max-queue`：有界队列，队满时整卷 / 页任务按退避重投，禁止无界排队；
  - 轻量熔断 CLOSED / OPEN / HALF_OPEN，仅对 `TRANSIENT_TIMEOUT / 5xx` 计数；
    `TERMINAL`（密钥 / 额度 / 模型不存在）不熔断；
  - 使用显式 `ThreadPoolExecutor` / 信号量 / 原子计数器，不引入新框架。
- 失败行为（单 provider）：
  - `TRANSIENT_TIMEOUT`：不做同一请求原地重试，直接安全失败该页；
  - `RATE_LIMITED`：允许带抖动退避重试同一 provider；
  - `INVALID_OUTPUT`：允许 JSON 修复重试；
  - `INCOMPLETE_CONTENT`：页级定向重抽；
  - `TERMINAL`：立即失败。
- 若后续确需双 provider，再作为独立评审项引入 `VisionProviderRouter` 与 `fallback-vision-provider`，
  本轮明确不做。

### 3.5 高并发下的页级任务化

顺序仍是：先完成 §3.4 的 provider 背压，再并行。页级任务化分两种做法，决策如下。

#### 3.5A 单卷内页级并行（已实现，不改 Redis 协议）

保留现有「一份试卷一条 `paper:recognition` 消息」：

- `PaperRecognitionStreamProducer` 不改 payload；
- `PaperRecognitionStreamConsumer` 不改领取、ACK、重试逻辑；
- `AbstractStreamConsumer` 不改；
- `paper:recognition` 仍然是试卷级任务。

只在 `PaperRecognitionService.processPaper()` 内把页处理并行化：

1. 文本页（`PageSource.TEXT`）先同步 `markReady`，不占视觉并发；
2. 图片页提交到命名执行器 `paperRecognitionExecutor`（由 `BoundedExecutorFactory` 构建，底层仍是
   有界 `ThreadPoolExecutor`，禁止 `Executors.newXxxThreadPool()`），用其
   `submitBatch + poll(timeout, heartbeat)` 收页结果；
3. 主线程按心跳周期 `poll()`，同时调用现有 `heartbeat(paperId, attemptId)`，保持试卷级执行权；
4. 页开始前写 `PROCESSING`，按页级 attempt / fencing token 写终态；
5. `paper_pages` 增加可空 `recognition_attempt_id`；恢复时只把超阈值 `PROCESSING` 页重置为
   `PENDING`，`READY` 页绝不重跑；
6. 队满（拒绝策略默认 `abort`）时整卷退避 / 重试，不能把页误标 `FAILED`；
7. 单页失败只影响该页，全部失败仍走现有整卷失败路径；
8. 启动校验 `executor.pool-size <= VisionRequestGuard.max-in-flight`，默认都取 2；
9. 页级 `page-stale-threshold` 默认取 `vision-request-timeout × 单页预算 + 心跳间隔 + 余量`，
   并在启动校验它大于单页最坏时长；
10. 执行器默认传播 SecurityContext / MDC，保留 `propagate-security-context=false` 开关；
    纸卷识别不依赖 owner 上下文，后续可据压测结果决定是否关闭。

示例（8 页试卷：第 1-2 页有文字层、上传即 READY；第 3-8 页为扫描图；假设每页视觉调用约
110 秒）：

```text
串行（现状）：consumer 占住约 660 秒
0s    P3 ───────── 110s
110s  P4 ───────── 220s
...
550s  P8 ───────── 660s

3.5A（3 个页 worker）：consumer 占住约 220 秒
0s    P3/P4/P5 ───────── 110s
110s  P6/P7/P8 ───────── 220s
```

- 两种方式下 Redis 都只有 1 条 `paper:recognition` 消息，consumer 都一次只处理这一份卷；
- 区别只是「一页一页等」变成「3 页一起等」，单卷耗时 660s → 220s；
- 有积压时 consumer 提前 440s 空出来接下一份卷，整卷吞吐随之上升；
- 若 provider 只允许 2 路并发，则 6 页要 3 批、单卷约 330s——3.5A 只能逼近 provider 上限，
  不能超过。

页实体扩展（`recognition_stage` / `diagnostic_json` 仍为后续项）：

- `recognition_stage`（A / B）；
- `diagnostic_json`：只放 `failureClass / provider / model / attempt / durationMs / outputChars`，
  不含原文。

配置建议：

- `app.paper.recognition.executor.pool-size`（默认 2，≤ `VisionRequestGuard.max-in-flight`）
- `app.paper.recognition.executor.queue-capacity`
- `app.paper.recognition.executor.rejection-policy`（默认 `abort`）
- `app.paper.recognition.executor.propagate-security-context`（默认 `true`）
- `app.paper.recognition.page-stale-threshold`（页级恢复阈值）

边界：3.5A 提升的是「单卷墙钟时间」和「consumer 单位时间能消化的试卷数」——consumer 仍在同一
时刻只处理一份试卷，但它被每份试卷占用的时间变短，有积压时整体吞吐随之上升。它**不会带来
「多份试卷同时在途」**；当真正瓶颈是 provider 并发 / 配额时，3.5A 只是把单卷内的等待重叠起来
去逼近这个上限，不会超过它。要跨试卷并行，需要多 consumer 实例或 3.5B。若目标只是「单卷更快、
上限可预测」，做到 3.5A 即可，**不需要改 Redis 生产消费逻辑**。

#### 3.5B 真正页级 Redis 消息（仅在跨试卷吞吐不足时再做）

只有 3.5B 才需要改 Redis 生产消费逻辑：

- 每页一条消息，至少携带 `paperId + pageNo + pageAttemptId`；
- 页级领取、ACK、重试、恢复；所有页完成后聚合整卷为 `NEEDS_REVIEW` 或 `FAILED`；
- 同步修改 `AsyncTaskStreamConstants`、Producer、Consumer、恢复扫描与测试；
- 会引入页任务重复、聚合竞态与恢复复杂度，不能为了「看起来更并发」提前拆。

决策规则：先做 3.5A；当多份试卷并发上送、单个 consumer 吞吐成为瓶颈时，再评估 3.5B，
并把页级消息与 §3.4 的 `VisionRequestGuard` 上限对齐，避免 provider 被页级任务打满。

### 3.6 可观测性

建议指标（复用现有 Micrometer）：

| 指标 | 标签 | 用途 |
| --- | --- | --- |
| `app.ai.vision.pages` | `result=success/failed` | 页级成功率 |
| `app.ai.vision.attempts` | `failureClass` | 各类失败是否被误重试 |
| `app.ai.vision.latency` | `stage=A/B, provider` | 定位 OCR 慢还是几何慢 |
| `app.ai.vision.provider_inflight` | `provider` | 背压与熔断观察 |
| `app.ai.vision.output_chars` | `stage` | 输出长度是否接近上限 |

日志固定记录 `paperId / pageNo / attempt / stage / provider / model / durationMs / outputChars /
failureClass`；解析失败时额外记录 Jackson `path / invalidValue / targetType`。
Prompt、图片字节、模型原始输出与上游原始 message 一律不记录。

## 4. 分阶段实施

| 阶段 | 内容 | 风险 | 当前状态 |
| --- | --- | --- | --- |
| P1 | 失败分类 + 安全文案 + 总重试预算 | 低 | 已实现 |
| P2 | 两阶段识别 + 单 provider 并发上限 / 熔断（`VisionRequestGuard`） | 中 | 已实现，两阶段默认关闭 |
| P3A | 单卷内页级并行、页级 fencing、恢复 | 高 | 已实现 |
| P3B | 跨试卷页级 Redis 消息与聚合 | 高 | 未实现，按吞吐实测再评估 |

两阶段与页级并行均可由配置控制；迁移只增列，不做破坏性改动。

## 5. 测试与验收

- 单元测试：
  - 失败分类矩阵（超时 / 限流 / 非法输出 / 内容不完整 / 终态）；
  - 重试预算：同一异常不会触发超过总预算的 provider 调用；
  - 两阶段组装：无图页只调用 OCR；有图页调用 OCR + 几何；几何失败不重新 OCR；
    OCR 重试后仍为几何保留预算；Pass A 文本 + Pass B 资源仍通过 `PageRecognitionValidator`。
- 回归测试：
  - `PageRecognitionValidatorTest`、`PaperFigureCropResolverTest`、
    `PaperLayoutAssetResolverTest`、`PaperVisualBlockResolverTest` 等资源归属用例不回归；
  - `PaperRecognitionServiceErrorTest` 继续保证安全文案。
- 人工验收：
  - 重启后用同一固定样本确认单次视觉调用不再在 60 秒被本地取消，正常完成时长约 90～120 秒；
  - 确认 `app.ai.vision-request-timeout` 的配置值真实出现在 `OpenAiChatOptions.getTimeout()`；
    限流 / 非法输出 / 内容不全按预算重试，运输超时不原地重发；
  - 第 3 页成功时，文本、图形资源与题号归属正确；失败时页面文案可读且内部 `failureClass` 正确。
- 高并发验收：
  - 模拟多份扫描卷并发，provider 在途数不超过上限、队列不无限增长、数据库连接稳定；
  - 同一页并发 / 恢复任务不会互相覆盖终态。

## 6. 开放问题

1. Pass A 成功但 Pass B 失败时，是否需要新增 `PARTIAL` 页面状态保留 OCR 草稿，还是继续只有
   `READY / FAILED`？前者更省 token，但会扩展前端状态机。（未决）
