# 试卷上传统一与高并发改造 - 设计稿

> 用途：审批用设计稿。覆盖「试卷导入 → 切题 → 作答 → 交卷 → 批改 → 报告」全链路的架构审查结论、
> 需要优化 / 删除的点、以及为高并发改造预留的主要入口设计。
> 状态：已实施（2026-10-28；阶段 A/B/C 的核心改造已落地，阶段 D/E 待单独设计；
> `PaperRecognitionService` 的 upload / processor / review 进一步拆分列为后续结构优化）。
> 2026-10-29 补充视觉识别稳定性设计，待审批，尚未实现。
> 最后核对：2026-10-29，以当前工作区实际代码为准。

---

## 0. 结论摘要

本次改造有四个目标，按「正确性 / 上线可用」优先级排序：

1. **合并试卷分析页的两个上传入口为一个**：统一到 `POST /api/papers/upload`，一次可选多个文件，
   后端自动判定「纯文字直接切题」或「需要识图校对」，支持图片与文字文件混合、合并为一份试卷。
2. **删除旧切题双轨**：`PaperQuestionExtractionService` / `PaperStructureDetector` /
   `PaperExtractionProperties` 及配套 Prompt / 配置 / 测试，全部删除；只保留新链路
   `PaperStructureService` 与 `PaperExtractionResult`。
3. **请求线程瘦身（为高并发做准备）**：报告接口只读化、作答写路径加 per-session 锁；
   会话创建异步化、文件解析下沉作为后续阶段单独设计。
4. **结构优化**：统一「确定性判分资格」谓词；拆分超大类，提升可读性与可维护性。

本次不动「业务命名批量重命名」（`resume / interview / 试卷` 等旧语义）——那是另一个长期事项，
详见 `docs/待优化事项.md` 1.1。

## 1. 现状链路复盘

### 1.1 端到端流程

```text
上传                    切题（异步）                     作答
┌──────────────────┐    ┌─────────────────────────────┐   ┌────────────────────┐
│ POST /api/papers │──► │ paper:extract:stream         │   │ PaperAttemptService │
│ POST /api/resumes│    │  → bootstrapper 建 TEXT 页    │──►│  → startAttempt     │
│  (两个入口并行)   │    │  → PaperStructureService.build│   │  → createSession   │
└──────────────────┘    │  → AnswerKeyPreparation      │   └────────────────────┘
                        │  → createSessionFromQuestions│
                        └─────────────────────────────┘
                                                     │
交卷 / 批改（异步）                   报告（现状有两套）
┌──────────────────────────────┐      ┌──────────────────────────────────────┐
│ interview:evaluate:stream     │      │ A. GET .../details（前端实际使用）   │
│  → AnswerEvaluationService    │      │    = 读 DB，已落库报告，只读 ✓       │
│  → saveReport + 错题回写      │      │ B. GET .../report（前端未使用）      │
└──────────────────────────────┘      │    = 请求线程重跑 LLM + 写库 ✗       │
                                      └──────────────────────────────────────┘
```

### 1.2 两个上传入口（需要合并）

| 入口 | Controller | Service | 行为 |
| --- | --- | --- | --- |
| `POST /api/papers/upload` | `PaperRecognitionController` | `PaperRecognitionService.upload` | 1~10 个文件合并为一份试卷；`DocumentParser` 解析为「页 + 行 + 资源」；有 `IMAGE` 页走识别 Stream，全文字页直接切题 |
| `POST /api/resumes/upload` | `ResumeController` | `ResumeUploadService.uploadAndAnalyze` | 单文件；纯文字直接切题，无文字层 PDF 转给识别链路 |

前端 `frontend/src/pages/UploadPage.tsx` 同时渲染：

- `ScanPaperUpload`（多选 PDF/JPG/PNG，提交到 `/api/papers/upload`，可合并为一份试卷）；
- `BatchUploadPage`（批量队列，`paperUploadAdapter` 每次只上传一个文件到 `/api/resumes/upload`）。

问题：两个入口、两套文件白名单、两种交互语义；且批量队列「一次一个文件」满足不了
「多张照片 / 图片 + 文字文件合并成一份试卷」的需求。

### 1.3 报告读取的双轨（需要收口）

- 前端报告页实际读 `GET /api/interview/sessions/{sessionId}/details`（DB 已落库的报告，只读，正确）。
- `GET /api/interview/sessions/{sessionId}/report` 目前 `InterviewSessionService.generateReport()`
  会在**请求线程**重新调用 `AnswerEvaluationService.evaluateInterview()`（LLM）并 `saveReport()` 写库。
  已核对前端无任何调用方，属于「同步重任务 + 重复批改」的遗留路径，是高并发下最危险的一处。

## 2. 问题清单（分级）

### P0 —— 高并发下会破坏正确性 / 可用性

1. **报告接口同步重跑 LLM**：`GET .../report` → `generateReport()` 在请求线程调 LLM 并写库。
   应改为只读；报告只由 `EvaluateStreamConsumer` 异步生成。
2. **作答写路径无锁读改写**：`submitAnswer` / `saveAnswer` / `submitWholePaper` 都是
   `getOrRestoreSession()` → 修改 `questions` → `sessionCache.updateQuestions()`。并发请求
   读同一份 `CachedSession` 时会互相覆盖答案。需要 per-session 锁或版本号。
3. **会话创建在请求线程同步生成题目**：`createSessionInternal()` 调
   `questionService.generateQuestionsBySkill()`（LLM），几十秒到分钟级，占用请求线程。

### P1 —— 一致性 / 业务正确性 / 明确收益

4. **上传双入口 + 前端双 UI**（见 1.2）。
5. **旧切题双轨死代码**：`PaperQuestionExtractionService`、`PaperStructureDetector`、
   `PaperExtractionProperties`、`paper-question-extraction-*.st`、`app.paper.extraction` 配置，
   及 `PaperQuestionExtractionServiceTest` / `PaperQuestionNumberingTest`。`main` 已无生产引用。
6. **确定性判分谓词散落**：`AnswerEvaluationService.isDeterministicQuestion()` 与
   `PaperAttemptService.hasUnusableDeterministicAnswerKeys()` 是同一语义的两份拷贝。
7. **纯文字直切路径未对齐**（当前 WIP 缺口，见 3.2）：
   - `validateFiles()` 未放行 TXT / MD；
   - 纯文字逻辑页被 `MAX_PAGES=10` 误伤；
   - `chargePageQuota()` 对纯文字页也扣「识别页数」配额；
   - `enqueueDirectExtraction()` 直接拼 `page.lines()`，未复用 `PageTextMerger`；
   - 直接切题返回 `RecognitionStatus.READY` 语义含混。

### P2 —— 工程质量 / 可维护性

8. **`AnswerEvaluationService` 是上帝类（631 行）**：入口路由、确定性判分编排、视觉批改、
   报告合并、分值折算、文案生成、上下文拼装、置信度谓词全塞在一个类里；还有一个全仓库
   无调用的死方法 `toInterviewReportDTO()`。
9. **`PaperRecognitionService`（1353 行）**：除业务编排外还混入大量 bbox / 几何纯函数
   （`pixelRect` / `normalizedRect` / `union` / `inSameColumn` / `anchorDistance` /
   `nearestSeed` / `assetKind` / `uniqueKey` / `truncate` / `appendNote`），可下沉。
10. `PaperAnalysisPage.tsx` 约 1000 行，职责过重。
11. 文件解析（PDF 渲染、DOCX 解析、Tika 抽文本）目前仍在请求线程执行，进一步高并发需下沉。
12. 遗留无用错误码、未闭合注释等（`docs/待优化事项.md` 3.3 / 3.5），可顺带清理。

## 3. 改造设计

### 3.1 上传统一入口（核心交付）

**目标**：只保留一个入口 `POST /api/papers/upload`，`/api/resumes/upload` 保留为兼容别名
（内部委托），前端试卷分析页只渲染一个上传组件。

#### 3.1.1 后端：`PaperRecognitionService.upload` 收敛为唯一编排

1. **文件白名单扩展**：在 `validateFiles()` 增加 `text/plain`、`text/markdown`、`.txt`、`.md`
   （Tika 对 `.md` 可能报 `text/plain` 或 `text/markdown`，按 MIME 与扩展名双兜底）。
2. **页数上限分离**：
   - 视觉识别物理页（`PageSource.IMAGE`）继续限 `MAX_PAGES=10`；
   - 纯文字逻辑页（DOCX / TXT / MD 的 40 行逻辑页）不再按页数限，改按字符总量限
     （复用 `app.paper.extraction.max-paper-chars` 语义，新增独立配置
     `app.paper.upload.max-text-chars`，避免与切题上限耦合）。
3. **配额只对视觉页计费**：`chargePageQuota()` 只统计 `needsVision` 的页数；
   纯文字直切不扣「识别页数」配额。
4. **正文合并复用 `PageTextMerger.mergePlain`**：纯文字路径先按 `createPages()` 落 `textContent`，
   再用 `pageTextMerger.mergePlain(readyPages)` 得到清洗后的正文，去掉页眉页脚噪声，
   与 `confirm()` 路径保持一致。
5. **处理路径显式化**：`PaperUploadResult` 增加 `processingPath`（`DIRECT_EXTRACTION` /
   `VISION_RECOGNITION`）。纯文字直切返回 `processingPath=DIRECT_EXTRACTION`，
   `recognitionStatus=NONE`（「未走页级识别」）而非 `READY`；`analysisStatus=PENDING`
   表示切题异步进行中。前端据此决定跳「进度页」还是「识别校对页」。
6. **混合文件合并**：任意一页 `IMAGE` 即整份走识别链路；文字页 `createPages()` 直接
   落 `READY`，图片页落 `PENDING`，合并为同一份试卷。该行为当前实现已具备，保留。

#### 3.1.2 前端：单个「试卷上传组」替换双入口

1. 改造 `ScanPaperUpload`（或新建 `PaperUploadGroup`）为统一入口：
   - 多选文件，支持 PDF / DOC / DOCX / TXT / MD / JPG / JPEG / PNG；
   - 一次 `FormData` 提交到 `/api/papers/upload`；
   - 上传后按 `processingPath` 跳转：`DIRECT_EXTRACTION` → `/papers?paper=id`（进度轮询），
     `VISION_RECOGNITION` → 识别校对面板。
2. `UploadPage` 不再同时渲染两个入口；`ScanPaperUpload` 的双入口用法删除。
3. **决策点**：「批量上传多份试卷」（每份一个文件）的旧能力是否保留？
   - 推荐：试卷分析页只保留「单份试卷上传组」；批量导入多份试卷的能力在试卷管理页单独保留
     （知识库已有同类批量组件，复用 `BatchUploadPage` 与 `/api/resumes/upload` 兼容别名即可）。
   - 如你希望彻底下线 `/api/resumes/upload` 批量语义，则批量能力整体移除。

### 3.2 纯文字直切路径修正（承接当前 WIP）

当前工作区已有 `TextDocumentParser.java`（新增）与 `PaperRecognitionService.java`（已改）。
补齐以下缺口后这条路径才算闭环：

1. `validateFiles()` 放行 TXT / MD（同 3.1.1-1）；
2. 纯文字逻辑页不受 `MAX_PAGES=10` 限制（同 3.1.1-2）；
3. 纯文字页不扣识别配额（同 3.1.1-3）；
4. 用 `PageTextMerger.mergePlain` 合并正文（同 3.1.1-4）；
5. `PaperUploadResult` 增加 `processingPath`（同 3.1.1-5）。

### 3.3 删除旧切题双轨

删除文件（`main` 已无生产引用）：

- `app/src/main/java/interview/guide/modules/resume/service/PaperQuestionExtractionService.java`
- `app/src/main/java/interview/guide/modules/resume/service/PaperStructureDetector.java`
- `app/src/main/java/interview/guide/modules/resume/service/PaperExtractionProperties.java`
- `app/src/main/resources/prompts/paper-question-extraction-system.st`
- `app/src/main/resources/prompts/paper-question-extraction-user.st`
- `app/src/main/resources/application.yml` 中的 `app.paper.extraction` 配置块
- `app/src/test/java/interview/guide/modules/resume/service/PaperQuestionExtractionServiceTest.java`
- `app/src/test/java/interview/guide/modules/resume/service/PaperQuestionNumberingTest.java`

保留 `PaperExtractionResult`（新链路 `PaperExtractionStreamConsumer` / `ResumePersistenceService`
仍在使用）。

### 3.4 请求线程瘦身（高并发）

#### 3.4.1 本轮：报告只读化

`GET /api/interview/sessions/{sessionId}/report` 改为只读：

- 报告唯一生成方是 `EvaluateStreamConsumer`（已 `saveReport`）。
- `generateReport()` 改为 `getReport()`：读会话 + 已落库报告；`evaluate_status=COMPLETED`
  返回报告，`PENDING/PROCESSING` 返回「批改中」，`FAILED` 返回失败原因。
- 若确认 `/report` 无外部调用方，可考虑直接删除该端点；否则做只读兼容。
- 前端报告页保持不变（继续读 `/details`）。

#### 3.4.2 本轮：per-session 锁

`submitAnswer` / `saveAnswer` / `submitWholePaper` 用 Redis 锁包住「读 → 改 → 写」，
复用现有 `RedisService.executeWithLock`（`PaperAttemptService.startAttempt` 已有同款写法）：

```text
submitAnswer(sessionId, request):
  lock("interview:session:write:" + sessionId, 3s)
     getOrRestoreSession → 改 questions → 落库 → updateQuestions → 返回
  unlock
```

不引入版本号乐观锁，锁方案简单且与现有骨架一致；会话级写锁互不阻塞。

#### 3.4.3 后续阶段：会话创建异步化

`createSessionInternal()` 拆成「同步建壳 + 异步生成题目」：

1. 同步：生成 `sessionId`，落一条 `status=CREATED` 的壳会话，返回会话与「题目生成中」状态；
2. 异步：投递题目生成任务到新 Stream（或复用现有抽象），生成后回填 `paper_json` 并置可用。

**为何本轮不并入**：它影响面试主链路入口与前端交互，风险高，需要独立的幂等 / 重试 /
进度协议设计；单独一份设计稿更清晰。

#### 3.4.4 后续阶段：文件解析下沉

`PaperRecognitionService.upload` 的 PDF 渲染 / DOCX 解析 / Tika 抽文本当前在请求线程执行。
下沉方案：请求线程只做「校验 + 存原始件 + 建记录 + 投递输入处理任务」，解析与页面分类在
异步 Stream 完成。单列设计稿，避免本轮动作过大。

### 3.5 结构优化（本轮）

1. **统一确定性判分谓词**：抽一个共享谓词（如 `InterviewQuestionDTO.isDeterministicGrading()`，
   覆盖单选 / 多选 / 填空 / 判断），`AnswerEvaluationService` 与 `PaperAttemptService` 复用。
2. **拆分 `AnswerEvaluationService`（631 行）**，行为保持不变：
   - `AnswerEvaluationFacade`：保留 `evaluateInterview()` 入口，只做「题型路由 →
     委托判分 → 交给组装器」，不写具体判分 / 文案 / 折算细节；
   - `ReportAssembler`：`mergeReports` / `buildReferenceAnswers` / `buildCategoryScores` /
     `weightedScoreRate` / `buildObjectiveFeedback` / `buildCategoryHighlights` /
     `withQuestionReferences` / `sumFullScore` / `sumPaperScore` / `withFullScores` /
     `paperScoreOf` / `limitFeedback`；
   - `EvaluationContextBuilder`：`buildQuestionReferenceContext` / `collectQuestionAssetIds` /
     `hasQuestionReference` / `appendIfPresent`；
   - 删除死方法 `toInterviewReportDTO()`；置信度谓词（`isLowConfidence` /
     `hasUsableAnswerKey` / `confidenceOf` / `lowConfidenceMessage`）随共享谓词一起收口。

   说明：`ObjectiveAnswerGrader`（客观题）、`VisualQuestionEvaluationService`（视觉题）、
   `UnifiedEvaluationService`（文本题）已经是独立判分单元，本次只做 facade / 组装 / 上下文的
   职责切分，不重写判分逻辑。
3. **拆分 `PaperRecognitionService`（1353 行）**：本轮先完成 bbox / 几何纯函数下沉；
   上传编排、识别执行与人工校对三段服务化继续作为后续结构优化，优先保证本轮链路稳定：
   - `PaperUploadOrchestrator`：上传编排、去重、页上限 / 配额、创建实体与投递；
   - `PaperRecognitionProcessor`：逐页识别 / 重试 / 心跳（Stream 消费者调用）；
   - `PaperReviewService`：预览校对、改页、删页、确认切题、重识别。
   - bbox / 几何纯函数下沉到独立工具类（如 `PageGeometry` / `RecognitionGeometry`），
     与识别编排解耦，便于单测。
4. **拆分 `PaperAnalysisPage.tsx`**（约 1000 行）：按 `Stage` 拆上传 / 识别校对 / 作答 / 报告
   子组件，状态机与轮询逻辑收敛到 hook。
5. 顺带清理 `docs/待优化事项.md` 3.3 / 3.5 的无用错误码与未闭合注释。

### 3.6 视觉识别稳定性（后续，未实施）

详细设计见 [视觉调用稳定性改造-设计稿.md](视觉调用稳定性改造-设计稿.md)。

摘要：按 `TIMEOUT / RATE_LIMIT / INVALID_OUTPUT / INCOMPLETE_CONTENT / TERMINAL` 分类并合并总
重试预算；视觉识别拆成 OCR 与资源几何两阶段；本轮不引入新的 vision provider，只给单一 provider
加并发上限 / 有界队列 / 熔断；页级并行先做「单卷内并行」（3.5A，不改 Redis 协议），确需跨试卷
吞吐时再升级为页级 Redis 消息（3.5B）。

| 阶段 | 内容 | 风险 | 本轮 |

## 6. 影响面与风险
