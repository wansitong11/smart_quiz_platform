# 试卷分析全流程说明（上传 → 切题 → 作答 → 批改报告）

> 用途：读完这份文档，你应该能自己把整条链路讲清楚——**每步做什么、为什么这么做、好处是什么**，
> 并且经得起面试官追问（文末有「追问与回答」和「30 秒 / 2 分钟自述版」）。
>
> 所有结论都对着代码核实过（文末有代码地图），标 ⚠️ 的是已知问题，别当成设计亮点讲。

---

## 0. 一句话总览

用户上传一份试卷 → 系统**同步**存文件与记录、**异步**用「规则 + 大模型」把整卷切成结构化题目并组装成
**试卷层级树** → 用户在同一棵树上**整卷一次作答** → 交卷后**客观题确定性判分、主观题交大模型批改** →
产出逐题解析 + 小节得分 + 薄弱知识点的**报告**，错题自动进**错题本**。

```
                     ┌──────────── 同步（毫秒级）────────────┐
上传 PDF/DOCX/TXT ──► 校验(10MB/类型) → 按归属人去重 → 解析正文(Tika)
                     → 存对象存储(RustFS) → 落库(PENDING) → 投递切题任务
                                                          │
                     ┌──── 异步（Redis Stream）────────────▼────────────────────┐
                     │ 切题：结构识别(规则) → 按题号切块 + 按字符分批(3000字)      │
                     │      → 每批调模型（题号范围约束 + 结构化输出）             │
                     │      → 题号去重排序 → 组装 PaperTree（层级树）             │
                     │      → 写解析摘要 + 建「练习会话」(source_type=PAPER)      │
                     └─────────────────────────────────────────────────────────┘
                                                          │
试卷分析页(?paper=) 恢复现场 → 开始作答 ──► 整卷一次作答 ──► 交卷
   ▲                                             │
   └─ 报告页（逐题解析 / 小节得分 / 薄弱知识点）◄── 异步批改：客观题确定性判分
                                                    + 主观题大模型按要点批改
```

## 1. 先讲清数据模型（后面所有设计都围绕它们）

| 表 / 关键字段 | 存什么 | 为什么这么设计 |
| --- | --- | --- |
| `practice_papers`（试卷/材料） | 原始件信息、`resume_text`（解析出的正文）、`file_hash`、`analysis_status`、`analysis_attempt_id` | 正文落库，**切题/重新切题都不必再下载解析**；`file_hash` 支撑去重；状态 + 代次支撑异步状态机与并发防护 |
| `paper_analyses`（切题摘要） | 题数、卷面总分、摘要、知识点、`warnings`、关联会话 id | 列表页/详情页只要"摘要"，不必每次反序列化整棵树 |
| `practice_sessions`（作答会话） | `session_id`、`source_type`、`paper_json`（**试卷层级树**）、`status`、`evaluate_status`、`overall_score`、`owner_id` | **切题结果挂在会话上**（见 §3.1 的取舍说明）；一次作答 = 一条会话，状态在这里收敛 |
| `practice_answers`（逐题作答） | `question_index`、`answer_json`（结构化作答）、`score`（**得分率 0~100**）、`feedback`、`reference_answer` | 逐题一行，便于报告逐题渲染与错题本展平聚合；按题存分数与反馈，支持「未交卷也已落库」的断点续答 |

两个口径必须记住（面试常被追问）：

- **`score` 是得分率（0~100），不是卷面分**；要展示卷面分时用 `round(得分率 × 该题满分 / 100)` 现算。
- **总分按分值加权**：`Σ(得分率 × 满分) / Σ满分`，而不是各题得分率简单平均——
  否则 60 分作文和 3 分选择题权重一样，分数就没有意义了。

## 2. 阶段一：上传（同步做「轻活」，把「重活」扔给异步）

入口：`POST /api/resumes/upload` → `ResumeUploadService.uploadAndAnalyze`，顺序是：

1. **校验**：大小 ≤ 10MB、按类型白名单校验（PDF / DOCX / DOC / TXT）；
2. **去重**：算 `file_hash`，按**归属人**查是否已存在；命中直接返回已有记录（`duplicate=true`，访问计数 +1）；
3. **解析正文**：Tika 抽文本，抽不到（如扫描件）直接报错；
4. **存对象存储**：原始件上传 RustFS，拿到 `fileKey`；
5. **落库**：写试卷记录，状态 `PENDING`；
6. **投递切题任务**：往 Redis Stream 投 `paperId`，返回前端。

**为什么这么排、好处是什么**

- **先解析、再存对象存储**：解析失败就直接失败，不会先留下一个没用的文件；
  反过来「先存后解析」会出现「文件在、正文没有」的半成品状态。
- **落库失败要补偿删对象**：代码里 catch 住 DB 异常后主动删除刚上传的对象，
  避免「对象存储有文件、数据库没记录」的孤儿数据——生产里这类脏数据最难清。
- **投递失败不伪装成 PENDING**：接口如实返回 `enqueueAccepted=false` + `analysisStatus=FAILED`，
  前端提示「文件已保存，可稍后重试」。**返回状态永远等于数据库真实状态**，这是异步系统的第一条纪律。
- **接口只做入库 + 投递**：LLM 切题要几十秒到几分钟，放请求线程里既会超时又占并发；
  现在接口只做毫秒级的活，用户体验是「秒传 → 进度页轮询」。

## 3. 阶段二：切题（整条链路最核心的一段）

消费者：`PaperExtractionStreamConsumer`（继承 `AbstractStreamConsumer`）；
抽取服务：`PaperQuestionExtractionService`（结构识别用 `PaperStructureDetector`）。

### 3.1 任务骨架：状态机 + 心跳 + 执行代次（fencing）

`AbstractStreamConsumer` 统一提供：**Redis Stream 消费组**（多实例不重复消费）、**ACK 与重试计数**、
**心跳**；业务侧只写 `processBusiness`。

试卷侧再加一层**执行代次**（`analysis_attempt_id`）：投递任务时生成 `attemptId` 写进消息；
落库用「锁行 + 校验状态仍是 PROCESSING + attemptId 一致」的条件更新；代次不匹配的消费者**直接丢弃结果**。

**为什么**：异步系统最常见的事故是「旧执行和重试执行同时写库，把新结果覆盖掉」。
用代次（fencing token）做条件更新，比加分布式锁简单、也没有死锁风险。

**卡死怎么办**：恢复调度器扫描「超过阈值没有进展」的任务重新投递，**最多恢复 3 次**；
超限直接把状态置为 `FAILED` 并把原因给用户看（可手动重新切题）。既自愈，又不会无限重试烧钱。

### 3.2 结构识别：能用规则的地方不用大模型

`PaperStructureDetector` 用一组正则识别卷面骨架：

- 大题：`一、现代文阅读（35分）`（`^一、/二、…`）
- 小节：`（一）现代文阅读I（本题共5小题，19分）`
- 题号：行首 `1. / 1．/ 1、/ 1)`
- 材料标记：`材料一：`、`阅读下面的文字…`

输出「大题 → 小节 →（材料正文 + 题号列表）」的骨架。
**好处**：层级、题号、材料归属都是**确定性信息**，正则识别零成本、可解释、可单测；
只有「这题问什么、答案是什么、怎么评分」这种**语义信息**才交给大模型。
这是整条链路最重要的一条取舍（面试必问，见文末 Q1）。

### 3.3 分批切题：把「长卷 + 大模型」变成可控问题

1. **按题号切块**：整卷正文切成「一道题一块」；
2. **按字符预算分批**：每批 ≤ 3000 字（`app.paper.extraction.batch-char-limit`）；
   整卷超过 30000 字会截断，防止极端输入打爆上下文；
3. **每批带三样东西进 Prompt**：
   - 本批原文，且**向前多带 300 字上下文**（阅读题材料通常写在题号之前，不带就会「看不到原文」）；
   - **题号范围约束**：「本次只处理题号 6 到 9（共 4 道），不要重复抽取范围之外的题」；
   - 结构化输出格式（`BeanOutputConverter` 生成 JSON Schema 提示）；
4. **结构化输出统一走 `StructuredOutputInvoker`**：模型返回非法 JSON 自动重试，
   最终失败映射成业务错误码（`PAPER_EXTRACTION_FAILED`）；业务代码里不写重试逻辑。

**好处**：① 大卷不超上下文；② 明确题号范围显著降低漏题/串题；③ 单批失败会写进 `warnings`，
一份卷子不会因为某一批而整体崩掉。

### 3.4 结果收口：题号去重 → 组装层级树

- **题号去重（保留首个）+ 按题号升序**：分批边界处模型可能重复抽同一题，按题号去重最稳；
- **组装层级树**：按题号把每道题挂回 §3.2 的骨架节点，形成 `PaperTree`：
  - 父节点（大题/小节）的**分值、题数由子节点汇总**（`PaperTree.recalculate`）——模型给的分值只当建议，
    避免「小节写 16 分、题目加起来只有 10 分」这种自相矛盾；
  - 没归属到任何小节的题会挂到「其他题目」并告警，**不静默丢题**；
  - 树的叶子顺序决定 `questionIndex`（0 起）。**前端渲染、提交答案、批改、报告共用这一套索引**，
    所以不会错位——这就是「一份真相」；
- **落库 + 建会话**：写 `paper_analyses` 摘要（带代次校验），同时用切题结果建一条
  `source_type=PAPER` 的练习会话（题数、树 JSON、缓存），供后续作答复用。

### 3.5 这一段的设计亮点

1. **规则 + 大模型混合**：确定性信息用规则（省 token、可解释），语义信息用模型（覆盖长尾题型）；
2. **分批 + 范围约束 + 上下文回带**：把「整卷丢给模型」变成「小块 + 明确边界」；
3. **结构化输出 + 统一重试**：模型的不稳定被收敛到一层基础设施里；
4. **层级树作为唯一真相**：切题、作答、批改、报告、错题本全部基于它；
5. **执行代次 + 心跳 + 恢复上限**：不重复写、卡死能自愈、自愈有上限；
6. **不静默丢数据**：孤儿题、超限题、分批失败全部进 `warnings` 且前端可见。

## 4. 阶段三：作答（整卷一次作答 + 断点续答）

### 4.1 进入作答

- 页面：试卷分析页（`/papers`），**URL 参数即状态机现场**：
  `?paper=123` = 已上传、展示切题进度；`?session=xxx` = 已建会话、恢复作答或看报告；
- 「开始作答」→ `POST /api/resumes/{id}/attempts` → `PaperAttemptService`：
  - 用 Redis 锁 `paper:attempt:lock:{paperId}` **串行化「继续还是新开」的判定**（防连点建出两个会话）；
  - **上一次没交卷 → 直接返回那一条会话（继续作答）**；上次已交卷 → **基于同一份 `paperTree` 新开一次**
    （题不变，便于两次对比）。

**为什么**：用户误关页面、刷新、换设备都会回到同一份答卷，不丢进度，也不重复消耗切题成本。

### 4.2 作答交互

- **一次作答整卷**（不是逐题问答）：一页里可跳题、可回改，符合「做卷子」的真实体验；
- 渲染完全由 `PaperTree` 驱动：大题/小节标题、**阅读题原文挂在题目上方**、选择题渲染选项框、
  主观题渲染输入框，另有答题卡与进度；
- **答案本地暂存**（`localStorage`，按 sessionId 存）：刷新不丢；
  与服务端已落库的答案合并时以服务端为准。

### 4.3 交卷

`POST /api/interview/sessions/{sessionId}/answers/batch` → `InterviewSessionService.submitWholePaper`：

1. **校验会话状态**：已完成/已评估的直接拒绝（防重复交卷）；
2. **校验题号索引**：越界、重复索引直接报错，**不做静默覆盖**（避免学生的作答被后一次请求覆盖）；
3. **结构化落库**：选择题存 `{"selectedKeys":["B"]}`、填空与主观题存 `{"text":"…"}`；
   选择题的文本答案由后端按 key 拼出，前端不必关心展示格式；
4. 会话置为 `COMPLETED`、刷新缓存，并统计空答案数返回给前端确认；
5. **投递批改任务**（Redis Stream），前端进入「批改中」轮询。

## 5. 阶段四：批改与报告（客观题不算模型，主观题才交给模型）

消费者：`EvaluateStreamConsumer` → `AnswerEvaluationService` + `ObjectiveAnswerGrader`。

### 5.1 判分分流（最大亮点）

先把每道题喂给 `ObjectiveAnswerGrader.grade()`，能确定性判分的就不进模型：

- **选择题（单选/多选）**：从作答里抽选项字母集合与参考答案比对
  （只认「纯选项字母」或「答案/故选 + 字母」两种形态，避免把主观文字里的字母误判成选项）；
  - 完全一致 → 得分率 100%；多选漏选 → 按配置给部分分（默认 50%）；错选 → 0；
  - 未作答 → 0 分，并直接给出正确答案；
- **填空题**：归一化（去空白、去标点、全角转半角、转小写）后比较；纯数字/字母答案没有等价改写空间，
  直接判对错；其余「可能是等价表述」的才交回模型判断。

剩下的题（主观题、需要等价性判断的填空）才进大模型，并且**带上这题的参考答案、要点与解析作为上下文**，
要求模型按点给分而不是自由发挥。

**好处**：① 客观题零 token、零幻觉、可复现（同一份答卷判多少次都一样）；
② 主观题判分有依据；③ 成本与耗时都明显下降（一份卷子里客观题往往过半）。

### 5.2 合并与总评

- 以 `questionIndex` 为键合并「确定性判分」与「模型批改」；**两条路都没覆盖到的题给 0 分并提示可重新批改**，
  保证报告不缺题；
- **总分按分值加权**（见 §1 的口径）；
- 若整卷**全是客观题**，直接跳过模型：总评、优势、改进项都由「按知识点聚合的得分」生成，
  既快又稳；
- 客观题评语不是冷冰冰的「错」，而是「判分结论 + 题目解析 + 考点」（解析来自切题阶段的 `analysis`）。

### 5.3 报告内容与前端表现

- `GET /api/interview/sessions/{id}/details` 返回：总分、逐题（你的答案 / 参考答案 / 得分 / 评语 / 解析）、
  **小节得分（题数、满分、实得、得分率）**、知识点薄弱项；
  小节得分是**用层级树把逐题得分聚合到最近的小节**算出来的，所以能看出「哪一大题丢分最多」；
- 批改是异步的：`evaluate_status` 走 `PENDING → PROCESSING → COMPLETED / FAILED`，
  前端每 2.5 秒轮询一次，失败可重试；
- `GET /export` 由服务端用 iText 生成 PDF（解析报告 / 答题报告），前端只触发下载。

### 5.4 错题本与重练

`GET /api/quiz/wrong-questions`：把**已完成/已评估的会话**展平，挑出没拿满分的题，
按「学科 + 题干归一化 key」聚合成一条记录并累计 `wrongCount`，按出错次数排序返回；
「错题重练」用错题重新组一次会话（`source_type=QUIZ_WRONG`），形成「测 → 错 → 练」的闭环。

> ⚠️ 已知问题（别当亮点讲）：这里判断「是否做错」用的是 `得分率 >= 满分`，
> 而 `score` 是 0~100 的得分率、`fullScore` 是卷面分（3、6 这类），两者口径不一致——
> 结果是**只保留 0 分的题，部分得分的题会被漏掉**。已记入 `docs/待优化事项.md`。

## 6. 设计亮点汇总（面试按这个顺序抛）

| # | 做法 | 为什么 | 好处 |
| --- | --- | --- | --- |
| 1 | 同步只做校验/去重/解析/入库/投递，切题与批改走 Redis Stream | LLM 调用分钟级，不能占请求线程 | 上传秒级返回；任务可重试、可观测、可扩展 |
| 2 | 结构识别用规则，语义抽取用模型 | 层级与题号是确定性信息 | 省 token、可解释、可单测；模型只做它擅长的 |
| 3 | 分批切题 + 题号范围约束 + 向前带材料上下文 | 长卷超上下文、阅读材料在题号之前 | 不漏材料、不串题，单批失败可告警 |
| 4 | 切题产物是层级树，父节点分值由子节点汇总 | 模型给的分值只是建议 | 结构自洽；前端/批改/报告共用一份真相 |
| 5 | `questionIndex` 由树的叶子顺序决定 | 前端提交、后端批改、报告展示要同一套索引 | 索引不会错位，问题好定位 |
| 6 | 客观题确定性判分 + 主观题模型批改 | 客观题判分不需要语义理解 | 零 token、零幻觉、可复现；主观题有要点约束 |
| 7 | 单题存得分率、总分按分值加权 | 3 分选择题和 60 分作文不能等权 | 分数口径科学，展示时按卷面分折算 |
| 8 | 执行代次 + 心跳 + 恢复上限 | 重试与旧执行会并发写库 | 不重复写、卡死能自愈、自愈不失控 |
| 9 | 按归属人去重 / requestId 幂等 / 防连点锁 / 题号去重 | 用户会重复点、重复传 | 不重复消耗成本，数据不重复 |
| 10 | DB 失败补偿删孤儿对象 + 状态如实返回 | 「对象在、记录无」最难清理 | 数据一致，前端提示准确 |
| 11 | 断点续答 + 本地暂存 | 用户会关页面、刷新 | 不丢进度、不重复切题 |
| 12 | 数据按 `owner_id` 归属、越权统一 404 | 多用户平台 | 只看自己的数据，且不泄露资源是否存在 |

## 7. 面试追问与回答（提前准备）

**Q1：为什么不用大模型一次把整卷切完？**
> 三点：① 长卷会超上下文，模型开始「偷工减料」甚至漏题；② 一次调用失败整卷重来，代价高；
> ③ 大小题层级、题号、材料归属本来就是确定性的，用正则零成本且可测。
> 所以我把任务拆成「规则识别结构 + 分批语义抽取」，模型只回答「这题问什么、答案是什么、怎么评分」。

**Q2：为什么切题结果挂在会话上，而不是建一张题库表？**
> 因为切题结果和「这次作答」强绑定：同一份试卷多次作答要基于**同一棵树**才谈得上对比成绩；
> 题库表适合「长期维护、反复出题」的场景（我们的知识库出题就是那样）。
> 这里把树存进会话的 `paper_json`，列表页另有 `paper_analyses` 摘要表，读列表不必反序列化整棵树。

**Q3：异步任务重复投递、或两个实例同时消费怎么办？**
> 三层防护：① Redis Stream 消费组保证同一条消息只被一个消费者领取；
> ② 每次投递带**执行代次**，落库是「校验状态 + 代次一致」的条件更新，过期执行的写被丢弃；
> ③ 「继续作答 / 新建会话」这类判定用 Redis 锁串行化，防连点。

**Q4：任务卡死了怎么办？**
> 消费者定期心跳更新进展时间；恢复调度器扫描「超过阈值没进展」的任务重新投递；
> **最多恢复 3 次**，超过就把状态置 `FAILED` 并把原因告诉用户（可手动重试）。
> 线上最怕「静默卡住」——我们让它要么自愈、要么明确失败。

**Q5：怎么保证判分公平、不会因为模型不同而分数不同？**
> 客观题完全不经过模型：选择题按选项集合比对、填空题归一化后比对，同一份答卷判多少次都一样；
> 只有主观题交模型，并且把参考答案、要点、评分标准一起给模型，要求按点给分；
> 总分算法固定（按分值加权），模型只影响主观题的分数。

**Q6：用户没交卷就退出了，会丢答案吗？**
> 不会。① 前端每次改动都写 `localStorage`（按 sessionId），刷新可恢复；
> ② 「开始作答」发现上一次没交卷时会**直接返回那一条会话**，不新开；
> ③ 交卷是整卷一次提交，提交时校验题号范围与重复索引，不静默覆盖。

**Q7：报告里的「小节得分」怎么算的？**
> 用层级树：每题得分先折算成卷面分（得分率 × 该题满分），再按「最近的祖先小节」聚合出题数、
> 满分、实得、得分率。这正是把切题结果做成层级树、而不是扁平数组的价值所在。

**Q8：模型返回的 JSON 不合法怎么办？**
> 结构化输出统一走 `StructuredOutputInvoker`：先按 Schema 约束模型，解析失败自动重试，
> 重试用尽才抛业务错误码。业务代码只有一行调用，换模型不用改业务。

**Q9：这套设计的成本控制点在哪？**
> ① 重复上传直接命中已有记录，不再切题；② 结构识别不花 token；
> ③ 分批只送必要文本；④ 客观题不调模型；⑤ 恢复重试有上限；⑥ 会话复用同一份切题结果。

**Q10：这套方案的薄弱点在哪、你会怎么继续改？**
> ① 主观题判分稳定性依赖模型，下一步加「评分标准结构化 + 抽检双评」来约束；
> ② 切题对版式怪异的试卷仍可能漏题，我在做「题号对账 + 定向补抽」（发现缺题只补那几题）；
> ③ 现在是单机 Redis Stream 队列，量再大要换成独立消息队列 + 任务表；
> ④ 错题本判错口径有个小 bug（得分率与卷面分混用），已在待优化清单里。

## 9. 自述版本（背下来就能讲）

**30 秒版**
> 试卷分析这条链路是「同步轻、异步重」：上传只做校验、去重、解析、入库、投递，秒级返回；
> 切题放 Redis Stream 异步做——先用正则识别大题/小节/题号骨架，再按题号分批交给模型抽取，
> 每批明确告诉它处理哪些题号、并把阅读材料上下文带上，最后按题号组装成一棵**试卷层级树**。
> 作答是整卷一次作答、一次交卷；批改时**客观题用规则确定性判分**（零 token、可复现），
> 只有主观题交给模型并按参考答案要点给分，最后产出逐题解析、小节得分和错题本。

**2 分钟版**（在上面基础上补四个「为什么」）
> 1）为什么拆同步/异步：LLM 调用分钟级，接口必须秒级，异步还能重试与观测；
> 2）为什么规则 + 模型混合：结构与题号是确定性信息，用规则省 token 又可解释；
> 3）为什么做成层级树：切题、作答渲染、批改上下文、报告小节聚合、错题本展平共用一份真相，
> 父节点分值由子节点汇总保证自洽，叶子顺序就是全链路统一的 `questionIndex`；
> 4）异步怎么保证不写脏：消费组 + 执行代次条件更新 + 心跳与恢复上限——
> 旧执行的结果会被丢弃，卡死的任务能自愈但不会无限重试。
