# 试卷导入与切题效率优化-设计稿

> 状态：已审核并实现（A0 / A1 / A2 / A2b / A3；另追加单阶段识别降噪与截断重试、解析批次与缺失语义修订）
> 日期：2026-11-04
> 实测依据：`app/logs/paper-flow.log`，`paperId=48`（`托福阅读1.pdf`，4 页扫描版，约 22.75 MB）
> 关联文档：`docs/改造说明.md`、`docs/待优化事项.md`、`.claude/rules/design-delivery.md`

## Problem Statement

老师导入一份 4 页的扫描版 PDF 试卷后，要等约 6 分钟才能开始校对切题结果：

- 页识别约 130 秒（其中第 3 页因模型返回 JSON 截断触发了一次 `INVALID_OUTPUT` 重试，单页耗到 97.6 秒）；
- 结构切题约 114.8 秒，三块完全串行；
- 答案键生成约 109.6 秒，其中 8 道题的解析逐题串行，合计约 69.3 秒。

除去「识别完成等用户点确认」这段人工等待，系统真正在跑的串行链路合计超过 6 分钟。对连续导入多份试卷的老师来说，这是「干等」级别的问题。

同时发现一个必须先修的隐性风险：AI 调用的归因上下文（谁在用、哪个功能、扣哪个预算）在页识别任务提交到线程池后会被丢掉，可能让识图调用被记成 `UNKNOWN`、不进用户预算、并发限制失效，甚至让用户绑定的识图模型失效。

## Solution

在不改变现有对外入口（上传接口、`PaperStructureService.build`、`AnswerKeyPreparationService.prepare`）的前提下，做四件事：

1. 先修「AI 调用上下文在异步线程里丢失」的问题——这是任何并行化的前置条件。
2. 把结构切题的「分块 → 逐块调用模型 → 合并」从串行改成小规模并行（并行度 2）。
3. 把答案键生成的「主求解、独立复核、冲突裁决、逐题解析」统一改成批次级并行：所有批次共享一个可配置大小的 `paper-answer` 线程池（默认 2，可设 1 回到串行），阶段依赖保持不变。
4. 页识别容量调优（页池、Stream worker）单独放一批，先确认预算与内存再动；本轮已把页池默认调到 3，并同步 `PAPER_IMPORT` 预算。

优化后，同一份 4 页扫描卷的预期结构切题约从 114.8 秒降到约 52 秒，主求解+独立复核约从 40.2 秒降到约 25 秒，答案解析约从 69.3 秒降到约 35 秒；页识别在容量允许时也可进一步压缩。总体验上，导入后「机器在跑」的时间明显缩短。

## User Stories

1. 作为老师，我想导入扫描版试卷后尽快看到可校对的切题结果，这样我不用干等几分钟。
2. 作为老师，我想连续导入多份试卷时后面几份不要一直排队，这样我能批量准备练习。
3. 作为老师，我想在识别结果出来后继续看到「请确认」的提示，这样我不会误以为系统卡住了。
4. 作为老师，我想切题结果仍然按原试卷的行序排列，这样校对时不乱。
5. 作为老师，我想某一块切题失败时其他块不受影响，这样我不会因为一处问题整卷重来。
6. 作为老师，我想每道题的解析仍然完整、按题号对齐，这样发布后学生看到的是正确解析。
7. 作为老师，我想单道题解析失败时仍有一个确定性的兜底答案，这样不会因为一道题卡住整卷。
8. 作为管理员，我想 AI 调用仍然正确归属到用户和功能（而不是 `UNKNOWN`），这样成本账和预算限流才准确。
9. 作为管理员，我想并发限制在异步线程里真实生效，这样不会出现「限了等于没限」的超卖。
10. 作为管理员，我想用户在「成本观测与控制」页面看到的识图调用仍然显示用户自己绑定的模型，这样计费和观测可信。
11. 作为开发维护者，我想并行化不破坏现有 `build` / `prepare` 的调用契约，这样下游（存储答案键、前端）不用改。
12. 作为开发维护者，我想并行逻辑可被单元测试覆盖（排序、合并、失败隔离、上下文不污染线程），这样以后改并发参数有回归保障。
13. 作为等待大卷结果的老师，我想主求解和独立复核同时跑、逐题解析也并行，这样多页/多批试卷不用一批一批等。

## Implementation Decisions

- 对外 seam 保持不变：`PaperStructureService.build(Long paperId)` 与 `AnswerKeyPreparationService.prepare(Long paperId, BuiltStructure structure)` 的签名、返回类型、副作用都不变。
- 修复上下文传播选在 `BoundedExecutor`：在提交任务时捕获 `AiCallContext`，worker 线程内恢复，`finally` 还原/清理，镜像现有 MDC 传播方式。新增开关默认开，不改变现有池的大小与拒绝策略。
- 结构切题内部拆成三个协作件：分块规划、分块执行、结果组装。并行度固定为 2（先小步），节点按 `startLine` 排序，warnings 按块序合并，`subjectKey` 取第一个非空值，单块失败只跳过该块。
- 答案键生成统一改为批次级并行：PRIMARY / VERIFY / TIE_BREAK / 解析的所有批次共享一个 `paper-answer` 有界线程池，池大小是唯一并发旋钮（默认 2，可设 1 回到串行，不超 `PAPER_EXTRACTION` 预算并发）；阶段依赖保持（PRIMARY 与 VERIFY 先并发，完成后才 TIE_BREAK，最后解析）。
- 每个批次只返回自己的答案键增量和 warning，主线程按批次顺序归位合并；PRIMARY 任一批失败取消其余并抛错，VERIFY / TIE_BREAK / 解析失败保留主答案并记 warning。
- 页识别容量调优（页池 `pool-size`、`paper-recognition` Stream worker）与上下文修复、结构并行分属不同批次，先确认 provider 配额、`vision-guard.max-in-flight` 与生产内存再调整。当前已按确认结果把页池与 `PAPER_IMPORT.concurrency` 都设为 3。
- 并行度先取 2，避免与 AI 预算默认并发（`PAPER_EXTRACTION` 默认 `concurrency=4`）叠加后瞬时打爆 provider。
- 单阶段识别不再要求模型重复输出整页 `text`，只输出 `lines`，由后端派生全文；输出被截断时单独归类并只做一次定向重试。

## Testing Decisions

- 只测外部行为，不测实现细节：测「并行后节点按 `startLine` 排序」「warnings 按块序合并」「单块失败隔离」「单题失败走兜底」，不测内部用了几个线程。
- 模块测试：`BoundedExecutorTest`、`PaperStructureChunkingTest` / `PaperStructureResourceOwnershipTest`、`AnswerKeyPreparationServiceTest`、`PaperPageRecognitionProcessorTest`。
- 先例：仓库已有对 `PaperPageRecognitionProcessor` 的并发测试与对 `BoundedExecutor` 的 MDC/SecurityContext 传播测试，新测试沿用同样的 `@Nested` + 中文 `@DisplayName` 风格。
- 本次属于 T3（公共/异步/AI/并发），交付前跑全量 `./gradlew :app:test --no-daemon`，Gradle 输出只看尾部 `Select-Object -Last 60`。

## Out of Scope

- 精简视觉 Prompt（只让模型输出 `lines`，后端派生 `text`）：已作为追加优化实现，单元回归通过；上线前仍建议用固定扫描样本复测。
- 扫描 PDF 直接复用整页单图、减少重复渲染：会改资源处理语义，不在本批。
- 提高 `paper-recognition` Stream worker 提升多卷吞吐：单独一批，需先评估配额与内存。
- 把 `paper-answer` 池大小默认调超过 2：本批默认 2，要更大需先压测预算与内存。
- 上传、PDF 解析、页图写对象存储这几段耗时（合计约 15 秒）：本期不动，后续可单独评估。
- 不新增并行分层框架、不绕过 `StructuredOutputInvoker` / `VisionRequestGuard` / `AiUsageGate` / `BoundedExecutor`。

## Further Notes

- 实测里「识别完成到确认切题」的约 17.2 秒是等用户在页面点确认，不是系统卡顿；`PAPER_CONFIRM_BEGIN` 到结束仅 27ms。本设计不改这段交互。
- 页识别消息实际携带的 `aiFeature` 是 `PAPER_IMPORT`，因此单独调 `PAPER_RECOGNIZE` 预算并发不会作用到页识别，容量调优时要注意。
- 所有并行任务仍走同一套 `StructuredOutputInvoker` 与 `AiUsageGate`，靠修复后的上下文传播保证计费、限流、模型绑定正确。

# 正文（业务视角）

## 改造点 0：AI 调用上下文在异步线程里丢了（必须先修）

- 目的：让每一次模型调用都知道「是哪个用户、哪个功能、哪次操作」在发起，从而正确计费、正确限流、正确选用户绑定的模型。否则并行化会让这些账全乱。
- 触发：页识别等异步流程在主流程（Stream worker 线程）里带着上下文，当它把「识别这一页」提交到 `BoundedExecutor` 线程池后，线程池线程默认不继承这个上下文。
- 规则与步骤：`BoundedExecutor` 现在提交任务时只传播 MDC 和安全上下文，不传播 `AiCallContext`。改造是：提交任务那一刻先 `AiCallContextHolder.get()` 取一份快照；任务在 worker 线程真正执行前，把这份快照放回线程（没有则清空），跑完任务后 `finally` 还原到执行前的值，保证不污染池里的线程。
- 结果：线程池里执行的识图调用能读到正确的 `userId / feature / operationId`，成本观测与预算扣减恢复正常，用户绑定的识图模型不再失效。
- 边界与异常：提交时本来就没有上下文（比如系统定时任务）就保持为空，按系统任务处理；任务抛异常时也必须还原上下文，不能让错误上下文漏到下一个任务。
- 可改点：想关闭这个传播，改新增开关 `propagate-ai-call-context`（默认 `true`）。

## 改造点 1：结构切题分块并行

- 目的：把三块串行、合计约 114.8 秒的结构化，压缩到「最长那块」左右（约 52 秒），让老师更快进入校对。
- 触发：试卷确认切题后，`PaperStructureService.build(paperId)` 开始按行数把试卷切成块（软上限 2800 字符、硬上限 5000 字符），每块调一次模型。
- 规则与步骤：保持 `build(paperId)` 对外不变。内部先做「分块规划」算出每块的行区间；再把各块提交到一个小线程池（并行度 2）里并行调用模型；最后「组装」——节点按 `startLine` 从小到大排序，warnings 按原块顺序拼接，`subjectKey` 取第一个非空块的值，试卷过长提示照旧。
- 结果：产出和现在完全相同的 `BuiltStructure`（科目、层级树、题目、总分、warnings），只是更快。
- 边界与异常：某一块调用失败只跳过该块并记一条 warning，不拖垮其他块；线程池满被拒绝时降级为串行跑完剩余块，不能直接丢任务。
- 可改点：并行度抽成配置（默认 2）；想调整「多大算一块」改 `SOFT_CHUNK_CHARS` / `HARD_CHUNK_CHARS`。

## 改造点 2：答案键解析并行

- 目的：把 8 道题逐题串行、合计约 69.3 秒的解析，压缩到约 35 秒（并行度 2）。
- 触发：结构切题完成后，`AnswerKeyPreparationService.prepare(paperId, structure)` 在生成主答案、独立复核、一致性裁决之后，进入逐题「解析生成」阶段。
- 规则与步骤：保持 `prepare(...)` 对外不变。当前逐题解析是串行循环且直接改写共享的 `keys` / `warnings`。改造为：每道题拆成独立任务，任务只读取已有答案键快照、返回「这题的新答案键 + 这条 warning」，不改共享对象；主线程等全部完成后按 `questionIndex` 归位合并。单题失败仍走现有兜底——生成失败就保留标准答案并记 warning。
- 结果：产出和现在完全相同的 `PreparedAnswerKeys`（答案键集合 + warnings），只是更快；并行不会覆盖已生成的正确答案键。
- 边界与异常：单题失败不影响其他题，也不会因为并发写同一个 Map 产生错序；线程池满时降级串行。
- 可改点：解析并行度由共享池 `APP_PAPER_ANSWER_POOL_SIZE` 控制；解析批次大小仍由 `ANALYSIS_BATCH_SIZE` 控制（当前 1）。

## 改造点 2b：答案键批次统一并行（PRIMARY / VERIFY / TIE_BREAK）

- 目的：把答案键生成里所有独立的「出答案」批次（主求解、独立复核、冲突裁决）统一交给一个共享有界线程池并行跑，用池大小这一个旋钮控制总并发，既不过载 provider，也能在小池/大池之间灵活切换。
- 触发：`prepare(...)` 按阶段产出批次任务：PRIMARY 与 VERIFY 的批次先一起提交；两者都完成后找冲突、再提交 TIE_BREAK 批次；最后才做解析。
- 规则与步骤：保持 `prepare(...)` 对外不变。所有「出答案」批次（文字每 10 题一批、图形按页和图片上限打包）都作为独立任务提交到 `paper-answer` 池；池大小 `APP_PAPER_ANSWER_POOL_SIZE` 默认 2，可调到 1（等价于现状串行）或不超过预算的更大值。PRIMARY 与 VERIFY 同时占用池；TIE_BREAK 在其后、解析在最后，阶段之间不重叠。每个批次任务都固定携带 `phase`（PRIMARY / VERIFY / TIE_BREAK），归位时按 `phase` 路由到对应的结果 Map，主答案与复核绝不会互相覆盖。
- 结果：出答案的结果与串行完全一致；并发度由池大小集中控制，不散落 if-else。
- 边界与异常：PRIMARY 任一批失败 → 取消其余在跑批次并抛错；VERIFY / TIE_BREAK 失败 → warning 保留主答案；`VisionRequestRejectedException` 致命；池满拒绝 → 降级串行。池大小上限不超过 `PAPER_EXTRACTION` 预算并发 4 与 `vision-guard.max-in-flight=4`。
- 可改点：并发度只改 `APP_PAPER_ANSWER_POOL_SIZE`；想完全串行设 1。

## 改造点 3：页识别容量调优（已实现）

- 目的：让单卷内的多页识别、以及多份试卷之间，都能更充分地利用已批准的视觉并发额度，进一步缩短等待。
- 触发：单卷页池原为 2、`paper-recognition` Stream worker 只有 1，多卷时后卷会排队。
- 规则与步骤：已确认页识别实际走 `PAPER_IMPORT` 预算，`vision-guard.max-in-flight=4`，生产内存约 1.6 GB；页池从 2 调到 3，并把 `PAPER_IMPORT.concurrency` 对齐到 3。`paper-recognition` Stream worker 暂保持 1，多卷吞吐另做压测。
- 结果：单卷识别更快、多卷吞吐更好，且不突破 provider 配额与内存。
- 边界与异常：无脑放大页池不会变快——真正的上限是 vision provider 并发与预算；内存不足会引发 GC 抖动。
- 可改点：页池大小 `app.paper.recognition.pool-size`、Stream worker `APP_STREAM_PAPER_RECOGNITION_WORKERS`。

## A0：BoundedExecutor 传播 AiCallContext

### 入口与签名

- 修改类：`app/src/main/java/interview/guide/common/async/BoundedExecutor.java`
- 修改方法：`private Runnable wrap(Runnable task)`、`private <T> Callable<T> wrap(Callable<T> task)`。
- 构造器新增一个布尔参数：`BoundedExecutor(String name, ThreadPoolExecutor pool, boolean propagateContext, boolean propagateAiCallContext)`，保存为字段。
- 工厂同步改：`app/src/main/java/interview/guide/common/async/BoundedExecutorFactory.java` 的 `create(...)` 在 `return new BoundedExecutor(...)` 时多传 `properties.isPropagateAiCallContext()`。

### 数据

- `AiCallContext` 是 `AiCallContextHolder.AiCallContext(Long userId, AiFeature feature, String operation, String requestId, String operationId, String source)`（`app/src/main/java/interview/guide/common/ai/AiCallContextHolder.java`）。
- `AiCallContextHolder` 提供 `get()`、`set(AiCallContext)`、`clear()`、`callWith(AiCallContext, ThrowingSupplier)`。
- 新增配置：`BoundedExecutorProperties` 增加 `propagate-ai-call-context`（布尔，默认 `true`），对应 getter `isPropagateAiCallContext()`；`application.yml` 里各执行器已有的 `propagate-security-context` 位置一并补默认 `propagate-ai-call-context: ${...:true}`（至少页识别执行器 `app.paper.recognition.propagate-ai-call-context`）。

### 步骤映射（wrap 的实现方式）

- `wrap(Runnable task)`：
  1. 若 `!propagateContext` 且 `!propagateAiCallContext`，直接返回 `task`。
  2. 提交线程捕获 `Map<String,String> mdc = MDC.getCopyOfContextMap()` 与 `AiCallContext ai = AiCallContextHolder.get()`。
  3. 返回新 `Runnable`：执行前保存 `Map previousMdc` 与 `AiCallContext previousAi`；`restoreMdc(mdc)`；`ai == null ? AiCallContextHolder.clear() : AiCallContextHolder.set(ai)`；`try { task.run(); } finally { 还原 previousAi 与 previousMdc }`。
  4. 还原规则：`previousAi == null ? clear() : set(previousAi)`；`previousMdc` 用现有 `restoreMdc`。
- `wrap(Callable<T>)` 同构，`try` 内 `return task.call()`。

### 状态与分支

- `ai == null`：worker 内清空上下文，等价于系统任务。
- `previousAi != null`：任务结束后恢复提交前的上下文（worker 线程通常为空，此分支保证幂等）。
- 任务抛异常：`finally` 必定还原，不污染池线程。
- 只传播上下文，不改变池大小、队列、拒绝策略、`completionService()` 行为。

### 可改点映射

- 关闭传播：`propagate-ai-call-context: false`。
- 想只对某类执行器开：只在该执行器的 `BoundedExecutorProperties` 配 `propagate-ai-call-context: true`。

### 测试（A0）

- `BoundedExecutorTest` 新增：提交任务前 `AiCallContextHolder.set(...)`，任务内断言 `AiCallContextHolder.get()` 等于提交时的值；任务结束后断言池线程上下文已还原为空；未设置上下文时任务内读到 `null`。

## A1：PaperStructureService 分块并行

### 入口与签名

- 修改类：`app/src/main/java/interview/guide/modules/resume/service/PaperStructureService.java`
- 对外方法保持不变：`public BuiltStructure build(Long paperId)`（现第 149 行）。
- 内部新增协作件（建议放在同包或 `.../resume/service/` 下）：
  - `PaperStructureChunkPlanner`：`List<ChunkPlan> plan(List<String> lines, List<int[]> pageRanges)`。
  - `PaperStructureChunkRunner`：`List<ChunkResult> run(List<ChunkPlan> plans, List<String> lines, List<AssetBinding> assets, List<MaterialBinding> bindings)`。
  - `PaperStructureAssembler`：`BlockTreeDTO assemble(List<ChunkResult> results, int chunkCount)`。

### 数据

- 文字切批：`TEXT_BATCH_SIZE = 10`（现第 57 行），沿用 `textAnswerBatches(...)`；TIE_BREAK 沿用逐题一批。
- 图形切批：沿用 `packVisualBatches(...)`（按页分组，受 `MAX_QUESTIONS_PER_CALL` / `MAX_IMAGES_PER_CALL` 限制）。
- 复核范围：`verificationSources = sources.filter(requiresConsistencyVote)`，只含选择题（现第 633–635 行）。
- 结果 Map：主求解写 `keys`、复核写 `verificationKeys`、裁决写 `tieBreakKeys`，本就分开；同一 `questionIndex` 在这几张 Map 里是彼此独立的记录，互不覆盖。
- 配置：`app.paper.answer.pool-size: ${APP_PAPER_ANSWER_POOL_SIZE:2}`；合法范围 1..4，不得超过 `app.ai.budget.features.PAPER_EXTRACTION.concurrency` 与 `app.ai.vision-guard.max-in-flight`。

### 步骤映射

1. `prepare(...)` 开头按 `needsVision` 把 `sources` 分成文字/图形两组，并算 `verificationSources` / `verificationSplit`。
2. 构造批次任务：
   - PRIMARY：`textAnswerBatches(text)` 每批一个任务 + 按页 `packVisualBatches(visual)` 每批一个任务；任务内部走 `requestTextAnswers` / `prepareVisualAnswerBatch` 的现有逻辑，但结果写进 `BatchOutcome` 而不是共享 Map。
   - VERIFY：同 PRIMARY，作用于 `verificationSplit`。
   - 把 PRIMARY + VERIFY 的任务一起 `AnswerBatchRunner.run(..., CANCEL_ON_FATAL)`。
   - `ExecutorRejectedException` → 降级为「先 PRIMARY 再 VERIFY」串行。
3. 归位（按 `phase` 路由，绝不能靠 `questionIndex` 猜）：
   - 先做防御校验：`outcome.phase()` 必须等于 `task.phase()`、`outcome.batchIndex()` 必须等于 `task.batchIndex()`，不一致直接抛 `IllegalStateException`（视为致命，`CancelPolicy` 不豁免）。
   - 任一 PRIMARY 批次 `fatal != null`（或任一 `VisionRequestRejectedException`）→ 取消其余任务、原样上抛。
   - 否则逐条处理 `BatchOutcome`：`phase == PRIMARY` 的 `keyDelta` 只写 `keys`，`phase == VERIFY` 只写 `verificationKeys`；warnings 按「PRIMARY 先、VERIFY 后」顺序合并。`source`（`SOURCE_TEXT` / `SOURCE_VISION`）只标记到 `AnswerKeyDTO` 自身，不参与路由。
4. `ensureAllAnswersPresent(sources, keys)` → `findConflicts` → 若有冲突，构造 TIE_BREAK 批次任务，`run(..., CANCEL_ON_FATAL)`（`VisionRequestRejectedException` 致命，其余非致命）→ 归位 `tieBreakKeys`。
5. `applyConsistency` → `enrichAnalyses`（A2 并行，同一 `paper-answer` 池；阶段间串行，不与前面重叠）。

### 状态与分支

- PRIMARY 批次失败：`CANCEL_ON_FATAL` 下取消其余并抛错。
- VERIFY / TIE_BREAK 批次失败（非 `VisionRequestRejectedException`）：非致命，warning + 保留主答案。
- `VisionRequestRejectedException`：致命，取消其余并上抛。
- 拒绝降级：`ExecutorRejectedException` → 该阶段串行执行。
- 路由隔离：`phase` 在构造任务时就固定并随 `BatchOutcome` 返回；PRIMARY 永不写 `verificationKeys`，VERIFY 永不写 `keys`。
- 防御校验：`outcome.phase` / `outcome.batchIndex` 与 `task` 声明不一致 → 抛 `IllegalStateException`，不静默归位。
- 并发上限：池大小 N（默认 2）；PRIMARY 与 VERIFY 共享池，峰值 N 个并发调用。
- 图片内存：同一时刻最多 N 批图片；生产内存约 1.6 GB，默认 N=2。

### 可改点映射

- 并发度：`APP_PAPER_ANSWER_POOL_SIZE`（默认 2；设 1 即完全串行）。
- 批次粒度：文字 `TEXT_BATCH_SIZE`、图形 `MAX_QUESTIONS_PER_CALL` / `MAX_IMAGES_PER_CALL`。

### 测试（A2b）

- `AnswerKeyPreparationServiceTest` 定向测试：
  - 批次并行后 `keys` / `verificationKeys` / `tieBreakKeys` / `warnings` 与串行结果一致。
  - PRIMARY 结果只进 `keys`、VERIFY 结果只进 `verificationKeys`，同一 `questionIndex` 在两 Map 各自独立、绝不交叉覆盖。
  - 任务返回的 `phase` / `batchIndex` 与声明不符 → 抛异常、不归位。
  - PRIMARY 任一批失败 → 其余取消并抛错。
  - VERIFY / TIE_BREAK 失败 → warning + 保留主答案。
  - `VisionRequestRejectedException` → 取消其余并上抛。
  - `ExecutorRejectedException` → 串行兜底。
  - 池大小设 1 时结果与串行完全一致（等价性回归）。

## 追加优化：单阶段识别降噪与截断重试

- 单阶段识别只要求模型输出 `lines`，整页 `text` 由后端从 `lines` 派生；同一份全文不再在 JSON 中出现两次，降低输出 token 和截断概率。

## 2026-11-05 追加修订：解析批次、RPM 等待与缺失语义

本修订覆盖正文中“逐题解析并行、单题失败生成确定性兜底”的旧描述，实际实现以本节为准：

- 解析批次默认从 `1` 调整为 `3`，通过 `app.paper.answer.analysis-batch-size`
  （`APP_PAPER_ANALYSIS_BATCH_SIZE`，范围 1~10）配置。8 题文字卷通常拆成 3 批，
  27 题大卷通常拆成 9 批，避免 27 次独立调用把同一分钟 RPM 打满，也避免一批塞入
  过多 500 字解析导致长 JSON 截断。
- 每批调用前由 `PaperAnalysisPacer` 检查 `PAPER_EXTRACTION` 当前用户的 RPM 窗口；
  已满时等待窗口剩余时间（带少量抖动），最长 `analysis-rate-limit-max-wait`
  （`APP_PAPER_ANALYSIS_RATE_LIMIT_MAX_WAIT`，默认 65 秒）。真正的计数与放行仍由
  `AiUsageGate` 负责，pacer 不重复计数。
- 只有 `AI_RATE_LIMIT_EXCEEDED` 做最多 2 次尝试；等待或调用被中断时按
  `PAPER_EXTRACTION_FAILED` 失败，不静默吞掉。
- 解析按 `questionIndex` 回填到本批结果，主线程按题号合并；缺失题目保留第一轮已确认答案，
  解析字段写入“解析未生成，请稍后重新生成。”并记录 warning，不再生成
  “本题正确答案为……”这类看起来像解析的兜底文案。
- 历史报告通过 `InterviewDetailDTO.AnswerDetailDTO.analysis` 返回真实解析，前端在逐题报告
  中显示“题目解析”；缺失时显示上述明确提示，便于用户识别并重新生成。
- 回归重点：`AnswerKeyPreparationServiceTest`（3/3/2 分批）、
  `AnswerKeyPreparationConcurrencyTest`（队列拒绝后当前线程完成剩余批次）、
  `AnswerKeyConsistencyIntegrationTest`（解析失败标记缺失而非伪造）、
  `PaperAnalysisPacerTest`（等待上限与 RPM 判断）。
