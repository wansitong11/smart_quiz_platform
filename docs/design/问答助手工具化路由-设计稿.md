# 问答助手工具化路由（Function Calling）· 设计稿

> 状态：P0 已实现（2026-09-24），含 trace 落库
> 需求：把「不是知识库该答的问题」从严格 RAG 里分流出去。典型症状——用户问「我第一个问题问了什么」，助手回「提供的知识库内容未包含当前对话的历史记录」。
> 前置：`kb_scope`（全部资料 / 按分类 / 指定资料）已落地，见 `知识库检索范围与分类-设计稿.md`。

---

## 一、结论先说

| 问题 | 判断 |
| --- | --- |
| 根因是什么？ | 不是记忆缺失。历史已经作为 messages 传给模型了，是 system prompt 写着「只使用知识库中检索到的相关信息」，模型于是不敢用对话记录。 |
| 用一个更强的 prompt 行不行？ | 只能缓解。元问题往往检索不到东西，而我们代码里「检索为空 → 直接拒答」，模型连调用机会都没有。**分流必须发生在检索之前**。 |
| 怎么分流？ | **把能力做成工具，让模型自己选**：`search_knowledge_base`（资料）与 `get_conversation_history`（会话记录）两个工具挂在同一个 ChatClient 上，模型按问题类型决定调哪个。 |
| 严格 grounding 要不要放弃？ | 不放弃，**改成绑定在工具上**：凡涉及资料事实，必须来自 `search_knowledge_base` 的结果；对话类问题依据 `get_conversation_history` 回答；两者都答不了才说信息不足。 |
| 需要新增多少东西？ | 一个 ChatClient 变体 + 两个 `@Tool` 方法 + 规则前置路由 + 无工具调用时的兜底 + 过程事件。P0 约 2 天。 |
| 检索范围（`kb_scope`）要不要给模型当参数？ | **不给**。通过 `ToolContext` 隐式注入会话范围，避免模型乱改检索范围；P1 再开放受限的 `categoryCode` 白名单。 |

## 二、现状盘点（可直接复用）

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| Tool calling 基建 | `LlmProviderRegistry.buildToolCallAdvisor(...)` | 已注入 `ToolCallingManager`，默认 ChatClient 带 `ToolCallingAdvisor`，语音客户端已是「工具 + 流式」形态 |
| 工具注册方式 | `AgentUtilsConfiguration` + `spring-ai-agent-utils` | 已有一个 `ToolCallback` bean（`SkillsTool`），说明这套机制在本项目跑通过 |
| 会话记忆 advisor | `LlmProviderRegistry.buildDefaultAdvisors(...)` | `MessageChatMemoryAdvisor` + `MessageWindowChatMemory`（窗口 ≥20）已是可配置项 |
| 安全兜底 | `SafeGuardAdvisor` | 敏感词直接拦，失败话术可配 |
| 资料检索 | `KnowledgeBaseQueryService.retrieveRelevantDocs(...)` | 已完成范围解析 + 跨库召回配额 + 出处信息（`kb_id` 在片段 metadata 里） |
| 范围解析 | `RagScopeService` / `ResolvedScope` | 检索层只认「一组 kbId 或空」，天然适合藏在工具内部 |
| 会话记录 | `rag_chat_messages` / `RagChatSessionService.loadHistoryMessages` | 消息已落库，字段有 role、content、message_order、created_at |
| 可观测 | `RagMetrics` | 已有 requests / refusals / stage duration，缺「工具调用」维度 |

**API 事实（Spring AI 2.0.0，已核对依赖 jar）**

- `ChatClient.prompt().tools(Object...)` / `.toolCallbacks(ToolCallback...)`：按请求挂工具
- `ChatClient.prompt().toolContext(Map)` + `org.springframework.ai.chat.model.ToolContext`：把「模型看不到、但工具需要」的上下文（会话 ID、资料范围）传进去
- `ToolCallingAdvisor.Builder`：`toolCallingManager` / `toolExecutionEligibilityChecker` / `conversationHistoryEnabled`
- `OpenAiChatOptions.getToolChoice()` / `getParallelToolCalls()`：可设置工具选择策略（**不同厂商兼容性需实测**）
- `MessageWindowChatMemory` 默认窗口 20；JDBC 仓储需另引 starter，官方没有「按相似度检索历史」的 advisor

**当前问答链路**（`KnowledgeBaseQueryService.answerQuestionStream`）

```
提问 → 空范围/空问题校验 → Query 改写 → 向量检索（配额均衡）
     → 无命中 ⇒ 直接返回标准拒答（模型根本没被调用）
     → 有命中 ⇒ 严格 grounding prompt（只依据资料）→ 流式生成 → 追加「出处」块
```

## 三、目标与非目标

**目标**

1. 「我们刚才聊了什么 / 我第一个问题问了什么 / 上一条回答是什么」能正确回答
2. 与资料无关的问题（闲聊、越界、平台操作类）不再套用「未检索到相关信息」，改为引导式回答
3. 资料类问题保持现在的严格 grounding 与出处，不因为引入工具而开始编造

**非目标（本期不做）**

- 不做多跳推理 / 复杂 agent 规划
- 不让模型直接执行写操作（导出、删除等），只做只读查询
- 不改动 `kb_scope` 的交互（沿用现有三态）

## 四、总体架构

```
用户提问（SSE）
  │
  ├─ 0. 规则前置路由（零成本、确定性）
  │      · 元问题关键词（我刚才问 / 上一个问题 / 总结这段对话 / 复述…）→ 直接调会话工具
  │      · 敏感词 → SafeGuardAdvisor（已有）
  │
  ├─ 1. Agent 轮（模型 tool calling）
  │      工具：search_knowledge_base(query)
  │            get_conversation_history(limit, order)
  │      首轮优先要求调用工具；之后 auto，最多 N 轮
  │
  ├─ 2. 兜底
  │      · 模型没调任何工具且问题不是对话类 → 后端补一次检索再生成
  │      · 检索无命中 → 分档话术（资料缺失 / 换个问法 / 引导提问示例）
  │      · 工具异常 → 降级为「无命中」，不向上抛 500
  │      · provider 不支持工具 → 配置开关回退到现有纯 RAG 链路
  │
  └─ 3. 输出
         流式回答 + 过程事件（tool_start/tool_end）+ 出处（来自工具结果，不由模型编）
```

## 五、工具设计

### 5.1 `search_knowledge_base`

```java
@Tool(description = """
    在用户自己的资料库里检索与问题相关的原文片段。
    适用于：学科知识、讲义/教材内容、用户上传资料里的事实性问题。
    不适用于：询问本次对话历史、平台功能操作、与资料无关的闲聊。
    同一轮里可以多次调用（换关键词再检索）。
    """)
ToolResult searchKnowledgeBase(
    @ToolParam(description = "检索用的关键词或问题，尽量保留学科术语") String query,
    ToolContext context);
```

- **范围不入参**：`context` 里带 `sessionId`，工具内部用 `RagScopeService.resolve(session)` 得到本次范围（`ALL` / `CATEGORY` / `SELECTED`），保证模型无法绕过用户在界面上选的范围
- 复用 `retrieveRelevantDocs` 的召回池放大 + 每份资料保底配额；命中后按 `kb_id` 归位提问计数（沿用现有逻辑）
- 返回内容分两部分：给模型看的片段正文（带《资料名》标注），给前端看的结构化出处（`kbId/name/score/片段序号`）
- 无命中时返回明确的「未命中」结构，而不是抛异常，让模型自己决定换关键词再试或说明信息不足

### 5.2 `get_conversation_history`

```java
@Tool(description = """
    读取本次会话的历史消息（用户提问与助手回答）。
    适用于：用户询问「我刚才问了什么」「第一个问题是什么」「总结一下我们聊的」
    「上一条回答是什么」等与对话记录本身有关的问题。
    不适用于：询问学科知识或资料内容（那要用 search_knowledge_base）。
    """)
ToolResult getConversationHistory(
    @ToolParam(description = "读取条数，默认 20，最多 100") Integer limit,
    @ToolParam(description = "排序：ASC 从最早开始（问「第一个问题」时用），DESC 从最新开始") String order,
    ToolContext context);
```

- 数据源：`rag_chat_messages`（按 `session_id` + `message_order`），只读、按需裁剪条数与长度
- `order` 是必须的：只给「最近 N 条」会答不出「第一个问题」，这是上个 bug 的直接教训
- P1 可把「总结对话」并入同一工具（返回全量摘要 + 条数），或另开 `summarize_conversation`

### 5.3 工具描述就是路由策略

两个工具的 `description` 里必须写清「什么时候用 / 什么时候不用」——模型只在 prompt 里看到这些描述，路由效果八成取决于它。上线后要按「未命中问题榜」迭代这段文案。

## 六、调用策略与兜底

| 场景 | 处理 |
| --- | --- |
| 明显元问题 | 规则前置直接注入会话记录（不进模型路由），保证 100% 命中 |
| 首轮 | 优先 `tool_choice = required`（强制选一个工具）；厂商不支持时退化为 prompt 引导 |
| 后续轮 | `auto`，允许「检索 → 换关键词再检索 → 生成」 |
| 最大工具轮次 | 3 轮（可配），超出直接基于已有结果生成 |
| 模型一轮都没调工具 | 后端补一次检索（把结果当作工具结果注入）再生成；避免知识问题靠模型记忆乱答 |
| 检索无命中 | 分档话术：资料里确实没有 / 建议换关键词 / 引导提问示例 |
| 工具抛异常 | 记 `tool_errors` 指标，按「无命中」处理，不打断流式响应 |
| provider 不支持工具 | 配置开关 `app.ai.rag.tools.enabled=false` → 回退现有纯 RAG 链路 |

## 七、Prompt 重构

`knowledgebase-query-system.st` 从「只使用知识库内容」改成「工具契约」：

```
1. 涉及资料事实（学科知识、讲义内容）→ 必须先调用 search_knowledge_base，回答只能引用工具返回的原文
2. 涉及本次对话（我问过什么、总结对话、上一条回答）→ 调用 get_conversation_history
3. 两者都覆盖不到 → 用 1-2 句说明信息不足，并给出可用的提问示例
4. 引用规范：资料类回答的出处由系统按工具结果追加，模型不要自己编出处
```

这样「严格 grounding」从一句笼统的约束，变成**绑定到具体工具**的规则，元问题不再被误伤。

## 九、流式与前端

后端：`ToolCallingAdvisor` 支持流式（`adviseStream`），但工具执行发生在流开始前/中途，用户会感觉「卡一下」。因此 SSE 增加过程事件：

| 事件 | 载荷 | 前端表现 |
| --- | --- | --- |
| `tool` | `{"name":"search_knowledge_base","status":"start"}` | 「正在检索你的资料…」 |
| `tool` | `{"name":"get_conversation_history","status":"start"}` | 「正在读取本次对话记录…」 |
| `sources` | `[{"kbId":3,"name":"数学知识点","segments":2}]` | 回答下方出处 chips（可点击定位资料） |
| `answer` | 文本分片 | 现有渲染不变 |

前端 `KnowledgeBaseQueryPage` 已有 `streamSse`（`parseMode: 'event'`），只需按事件名分支渲染；出处从「模型输出末尾的 Markdown 块」升级为结构化 chips（现在是 P1 遗留项，正好一起做）。

## 十、安全、限额与成本

| 项 | 做法 |
| --- | --- |
| 敏感词 / 越界 | `SafeGuardAdvisor`（已有）+ 越界话术模板 |
| 工具轮次上限 | 3 轮；单工具超时 10s |
| 并发与成本 | 沿用 `@RateLimit`；一次提问最多 2 次检索 + 1 次生成，token 与现在同量级 |
| 写操作 | 本期不暴露（导出/删除类工具必须走「用户确认 + 独立接口」，不做成模型工具） |
| 工具入参清洗 | 沿用 `PromptSanitizer`；工具只读，天然避免了越权写入 |

## 十一、可观测与运营闭环

**P0**：`RagMetrics` 增加 `rag_tool_calls_total{tool,result}`、`rag_tool_duration`，以及 `rag_no_tool_call`（模型没调工具的比例）。

**P1**：新增 `rag_query_traces` 表，每次提问落一行：

```
session_id, question, rewritten_query, intent(rule|tool|fallback),
tools_json(工具名+参数+耗时+命中数), top_score, outcome(answered|no_hit|tool_error),
latency_ms, created_at
```

用途：**未命中问题榜**（决定补什么资料）、**意图分布**（决定要不要加工具）、**拒答后追问率**（决定话术怎么改）。这一层是企业级和 demo 的分水岭，建议 P1 一定做。

## 十三、验收标准

1. 「我第一个问题问了什么」「总结一下我们聊了什么」→ 正确回答，不出现「知识库内容未包含」这类拒答
2. 「名词性从句有哪些例句」→ 仍走资料检索，回答带出处，且不编造资料里没有的内容
3. 「帮我写一首诗」「你们和别的产品比怎么样」→ 引导式回答，不检索、不硬答
4. 模型一轮没调工具时，后端补检索，答案仍基于资料（可观测里能看到 `fallback`）
5. 工具超时/异常时接口不 5xx，用户看到的是「信息不足 + 引导」
6. provider 关闭工具（配置开关）时，行为与当前版本完全一致
7. 前端能看到「正在检索资料…」这类过程提示，回答下方出处以结构化形式展示

## 十五、风险

| 风险 | 应对 |
| --- | --- |
| 厂商 `tool_choice` / 并行工具调用兼容性不一 | 配置开关 + 首轮失败自动降级；上线前用现有四家 provider 各跑一遍 |
| 引入工具后模型对知识问题不再严格依据资料 | 工具契约写进 system prompt + 保留「无工具调用则补检索」的兜底 + 用评测集回归 |
| 工具描述写不好导致路由错 | 靠 `rag_query_traces` 的意图分布迭代描述文案；P2 加入元问题/越界评测样本 |
| 流式体验出现停顿 | SSE 过程事件 + 前端骨架提示，把等待可视化 |

| 「帮我写一首诗吧」 | ✅ 引导式回答（说明只负责资料与学科问题 + 给出可问的示例），不硬答 |
| 榜单接口 | ✅ `total=4 / noHit=1 / refusalRate=0.25`，意图分布 RULE、PRERETRIEVAL、FALLBACK 各就各位 |

### 重要发现：Spring AI 2.0.0 的流式工具调用合并缺陷（已用官方补丁解决）

**根因（源码级）**：`OpenAiChatModel$ChunkMerger.mergeDeltas` 在 2.0.0 里用
「工具调用分片是否带 `id`」来判断这是**新的工具调用**还是**同一调用的续传分片**：

```java
if (toolCall.id().isPresent()) { /* 新工具调用 */ }
else { ToolCall last = tcs1.get(tcs1.size() - 1); Function f = last.function().get(); ... }
```

DashScope（以及官方注释里点名的 DeepSeek）的续传分片**不带 `id` 或带空字符串 id**，
于是被误判成续传，进而走到 `function().get()` / `name().get()` 上抛
`NoSuchElementException`（`Optional.get()` 空值）——这就是我们看到的崩溃。

**官方修复**：Spring AI **2.0.1** 把这段逻辑改成**按 tool call 的 `index` 合并**，并对缺失字段做容错：

```java
// 2.0.1 源码注释：Deltas of the same logical tool call share the required 'index' field.
// Some OpenAI-compatible providers (e.g. DeepSeek) send an empty-string id on continuation
// deltas instead of omitting it, so id presence cannot be used to detect the start of a new tool call.
Map<Long, ToolCall> mergedByIndex = new LinkedHashMap<>();
tcs1.forEach(tc -> mergedByIndex.merge(tc.index(), tc, ChunkMerger::mergeToolCalls));
```

同时 `chunkToChatCompletion` 也不再裸调 `Optional.get()`：缺 id/name 时抛带说明的
`IllegalStateException`，`arguments` 缺省为 `""`。

**采取的动作**：`gradle/libs.versions.toml` 的 `springAi` 从 `2.0.0` 升到 `2.0.1`（patch 版本，
全家桶统一；`spring-ai-agent-utils:0.10.0` 兼容，编译与全量测试通过）。

**验证结果**：

| 指标 | 升级前（2.0.0） | 升级后（2.0.1） |
| --- | --- | --- |
| 流式工具调用 | `NoSuchElementException`，触发降级 | 正常，无异常 |
| 「我第一个问题问了什么」耗时 | 17756ms（含约 3s 失败尝试） | **3506ms** |
| 日志「降级为无工具生成」告警 | 每次必现 | **0 次** |
| 全量后端测试 | 通过 | 通过 |

**保留降级链的理由**：它现在是纯粹的保险（厂商网络抖动、其它兼容性问题），不再是主路径。

**官方文档里另一条标准化做法（P1 备选）**：`tools.html` 的 *User-Controlled Tool Execution*——
用 `AdvisorParams.toolCallingAdvisorAutoRegister(false)` 关掉自动工具循环，自己用
`ToolCallingManager` 驱动迭代. 文档明确把「向 SSE/WebSocket 转发中间进度」列为该模式的适用场景，
正好对应我们 P1 想做的 `tool` 过程事件；将来要做工具调用之间的人工确认也用它。

### 与设计稿的差异

1. SSE 命名事件（`tool` / `sources`）未做，出处仍是回答末尾的 Markdown 块——留到 P1；
2. 首轮强制 `tool_choice=required` 未启用：升级后工具可用，但实测模型多数情况下直接用上下文
   （预检索片段 / 注入的对话记录）回答，轨迹多为 `RULE` / `PRERETRIEVAL`；要让工具成为主路径，
   P1 再开这个开关（`OpenAiChatOptions.getToolChoice()` 可用，但各厂商兼容性需逐个测）；
3. 意图枚举落库为 `RULE / PRERETRIEVAL / TOOL / FALLBACK`（比设计稿多一个 `PRERETRIEVAL`，代表「走预检索通道、模型没额外调工具」）。

## 十七、简化改造（2026-09-25）：去掉规则通道，记忆交给框架

**动机**：主流程里为「对话历史」单独写了一套规则路由（关键词表 + 预注入对话记录），
属于应用层的补丁而不是框架该有的写法。既然工具可用（2.0.1 修好流式工具调用），
就应当由 **function calling** 决定是否查历史，**对话上下文**交给 Spring AI 的 **ChatMemory**。

### 改了什么

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 意图判断 | `RagIntentRouter` 正则匹配 + 元问题走特殊分支 | **删除**，统一「改写 → 预检索 → 带工具调用模型」 |
| 对话记录注入 | 后端把最近 20 条渲染成 `{chatHistory}` 块拼进 prompt | **删除**，改由 ChatMemory 作为消息注入 |
| 历史查询 | 规则命中即预注入（模型不用调工具） | **`get_conversation_history` 工具**，模型自己判断（支持 ASC/DESC、可读全量） |
| 对话记忆 | 手写 `loadHistoryMessages` + `spec.messages(history)` | Spring AI `ChatMemory` + `MessageChatMemoryAdvisor` |
| 出处 | 预检索命中就追加 | 只在「没有只用历史工具」时追加（避免和会话类回答串味） |

### ChatMemory 的标准接法（官方自动配置源码）

`ChatMemoryAutoConfiguration` 两个 Bean 都是 `@ConditionalOnMissingBean`：

```java
@Bean @ConditionalOnMissingBean
ChatMemoryRepository chatMemoryRepository() { return new InMemoryChatMemoryRepository(); }

@Bean @ConditionalOnMissingBean
ChatMemory chatMemory(ChatMemoryRepository repo) {
    return MessageWindowChatMemory.builder().chatMemoryRepository(repo).build();
}
```

所以我们**只提供一个 `ChatMemoryRepository` Bean**，自动配置就会用你的仓储构建
`MessageWindowChatMemory`，内存版实现自动退让——不需要自己 new 记忆对象。

本项目的实现 `RagChatMemoryRepository`（`@Repository("ragChatMemoryRepository")`）：

- `findByConversationId` → 读 `rag_chat_messages`（conversationId 即会话 ID），只取已完成消息
- **剔除当前这一轮的 user 消息**（它已作为 prompt 发出，重复注入会让模型看到两遍）
- `saveAll` / `deleteByConversationId` 是**空实现**：消息落库与删除由 `RagChatSessionService`
  负责（它还要维护 SSE 占位消息），这里再写会同一轮落两份；因此该适配器是**只读**的

`LlmProviderRegistry.createAgentChatClient` 只注入自动配置出来的 `ChatMemory`，
用 `MessageChatMemoryAdvisor.builder(chatMemory)` 挂到 agent 客户端；调用时通过
`advisors(a -> a.param(ChatMemory.CONVERSATION_ID, sessionId))` 指定会话。

### 验证结果

| 提问 | 轨迹 | 说明 |
| --- | --- | --- |
| 「我第一个问题问了什么」 | `TOOL` + `tools_json=[{"name":"get_conversation_history","hits":5,"latencyMs":7}]` | **模型自己调用了历史工具**，规则通道已删除 |
| 「资料里有哪些写作技巧？」 | `PRERETRIEVAL` + 系统追加出处 | 资料链路不变 |
| 后端全量测试 | 通过 | 含 Spring AI 2.0.1 升级回归 |

### 这次简化的代价（如实记录）

1. **延迟**：历史类问题以前走规则通道约 3.5s（不检索、不调工具），现在要 做一次预检索 +
   一轮工具调用，实测 15～40s（DashScope 本身也慢）。若在意这个，可以让规则只做
   「跳过预检索」这一件小事，而不是整套预注入。
2. **提问计数**：历史类问题也会因为预检索命中而给资料 +1，语义变成「该资料参与过回答」。
3. **模型偶尔自写出处**：历史类回答里模型有时仍写一行「**出处**：本次对话历史记录」，
   系统侧已不再重复追加；彻底解决要么在流式尾部做一次清理，要么把出处改成结构化的
   SSE 事件（P1 一起做）。

## 十八、严格接地策略：暂不放开（2026-09-25 决策）

**现象**：用户问「能用这个句式帮我造一些其他句子示例吗」，助手回答
「知识库中未收录更多名词性从句的示例」——它其实会造句，但被提示词禁止使用自身知识。

**原因**（`knowledgebase-agent-system.st` 三条规则叠加）：

| 位置 | 原文 |
| --- | --- |
| 工具契约 | 资料类问题「必须先调用 `search_knowledge_base`，回答只能引用工具返回的原文片段」 |
| 补充规则 | 「不得凭记忆补充资料里没有的结论；资料里没有就说没有」 |
| 回答原则 | 「准确性优先：只依据检索结果，禁止编造」；「资料里没有的内容不展开」 |

**决策**：**保持现状不动**。严格接地的可信度收益大于"能多答一些"的体验收益，
尤其在学习场景下，把模型通用知识混进"资料事实"是更严重的问题。

**如果以后要放开，按下面的分级方案做（本次不实施）**：

| 级别 | 触发场景 | 行为 | 标注 |
| --- | --- | --- | --- |
| L1 严格接地 | 事实核对：资料写了什么、答案、考点、数据 | 只依据检索片段，没有就说没有 | 系统追加出处 |
| L2 允许通用知识补充 | 生成/讲解：造句、举例、改写、讲方法、概念解释 | 先说明资料里有什么，再用通用学科知识补充 | 补充内容前打标记 `> ※ 以下为通用知识补充，未出现在你的资料中` |
| L3 引导拒答 | 闲聊、越界、平台操作 | 说明能力范围 + 给可问示例 | — |

落地要点（当时梳理好的，可直接照做）：

1. **Prompt 分级**：把「资料里没有就说没有」改成按问题类型分流——
   事实核对类保持不变；生成/讲解类允许补充并强制标注；补充与资料冲突时以资料为准。
2. **配置开关**：`app.ai.rag.answer.beyond-materials: strict | supplement | off`
   （建议默认 `supplement`，便于答辩/演示时切换对比）。
3. **可观测 + 前端提示**：后端对回答做一次标记检测，往 `rag_query_traces` 加
   `has_supplement` 列 → 榜单可回答「多少比例的回答依赖通用知识」；
   前端用 Markdown 引用块自然区分，不必特殊渲染。
4. **评测配套**：往现有 RAG 评测集加三类样本（事实类必须接地 / 生成类允许补充 /
   越界走引导），否则容易"改好一类、坏另一类"。
5. 若"造句/举例/改写"成为正式功能，再考虑做成工具 `generate_examples(pattern, count)`，
   由 function calling 触发：来源清晰（工具产物 ≠ 资料）、格式可控、可单独限流。
