## 一、项目定位与核心链路

### 1.1 产品已转向个人备考，但业务命名仍是教育 / 面试语义 — P1

- **现状**：产品定位已经确定为“个人职业资格 / 考证备考”，支持用户导入自己的习题、试卷或资料，
  进行智能练习、批改、历史复习和知识库问答；但代码、数据库表、路由和页面仍大量使用
  `resume / interview`、学生、小学、高中、试卷等旧语义。
- **影响**：新用户和面试官容易把项目理解成 K12 刷题系统；后续继续开发会在错误概念上叠加改动。
- **建议做法**：先基于核心用户旅程建立领域词汇和迁移表，再按“数据结构 → API → 前端文案”分批改名。
  不要直接全局替换；历史表名、接口兼容和外部部署配置需要单独评估。
- **来源**：2026-10-25 产品方向讨论。用户明确决定先修完批改链路，再整体改造。

### 1.3 切题漏题没有校验 — P1

- **现状**：同一份《高三语文模拟试卷》两次切题，一次切出 23 题/150 分、一次只有 22 题/144 分——模型漏掉了第 9 题（6 分），而流水线里 `warnings_json` 是空的，界面照常显示 144 分，没有任何提示。
- **根因**：当前主链路是 `PaperStructureService.callModelChunked()`；分块失败会写 warning，
  但成功回包内没有做“原文题号集合 vs 结构节点题号集合”的对账，因此整题漏识别时仍可能静默通过。
- **建议做法**：① 每块在本地扫描可确认的行首题号，与模型返回的 QUESTION 做对账；
  ② 缺失题号定向补抽并合并；③ 无法确定题号时至少写 warning，前端在分析页明确展示卷面可能不完整。
- **来源**：用户反馈"解析出来是150分，但显示144"。

### 1.4 答案键可能形成“两个 non-thinking 错误答案一致”的假共识 — P0

- **现状**：`AnswerKeyPreparationService` 的主求解和独立复核都使用 non-thinking 普通客户端，
  只有两者冲突时才用 reasoning 单题裁决。2026-10-25 的数学测试卷第 2 题验证过：
  non-thinking 返回错误 `C`，单题 reasoning 约 11 秒可返回正确 `B`；如果主求解和复核同时答错为 `C`，
  当前会得到 `CONSENSUS=100`，不会触发 reasoning 裁决。
- **影响**：高风险数学、图形或推理题仍可能出现稳定但错误的答案键，后续客观题判分会把正确作答判错。
- **建议做法**：对选择题的复核采用 reasoning 单题或最多 2 题小批，禁止重新使用 8 题整批 thinking；
  或仅对低置信度、数值/图形/多步推理题触发 reasoning 审计。先用真实样本测单次耗时，并确认
  `OpenAiChatOptions.getTimeout()` 与配置一致，不用假想的上游 60 秒边界做决策。
- **来源**：2026-10-25 答案键日志跟踪与第 2 题差分验证。

### 1.5 阅读材料归组仍有边界 — P1

- **现状**：`PaperMaterialHierarchyNormalizer` 已能合并跨页续写材料，并用 88% 字符 n-gram 覆盖率
  识别题目旁重复展示的段落摘录；`PaperTreeView` 也已能渲染根级 MATERIAL 正文。
- **剩余风险**：如果模型没有输出完整文章 MATERIAL、摘录被大幅改写/OCR 差异超过阈值，或后续出现
  多篇材料交叉引用，后端仍无法可靠确定父子关系。
- **建议做法**：让结构协议显式输出 `materialRole`（PASSAGE / EXCERPT / NOTE）和稳定的 `groupKey/parentRef`，
  分块调用时携带当前阅读组上下文；文本相似度只作为后端校验和旧数据兜底。
- **来源**：2026-10-25 托福阅读 `paperId=31/33` 验证。

### 1.6 出题可选"覆盖"模式 + 保护手工题 — P2

- **现状**：生成题目已改为**追加**语义（不覆盖）。若用户想"清空重来"，目前只能自己去题库里删。
- **建议做法**：生成弹窗加「生成方式：追加（默认）/ 覆盖」；覆盖要二次确认，并**保护手工新增/编辑过的题**——需要给题目加 `source`（GENERATED / MANUAL）或 `edited_by_user` 标记（一条迁移），覆盖只删模型生成且未被编辑过的。
- **来源**：知识库出题改造时讨论（用户选"追加"，覆盖方案暂缓）。

### 1.7 阅读型板块靠关键词判定，且截断兜底是「整板块丢弃」— P2

- **现状**：2026-10-27 修复了模拟测验阅读材料被截断到 1200 字、题目却考到被截掉内容的问题
  （见 `docs/design/模拟测验考试科目化-设计稿.md` §10）。当前判定阅读型板块靠「考点/标题关键词
  （阅读 / 完形 / 文言文）+ READING 题型」，截断兜底用「宁缺毋错」整板块丢弃。
- **当前默认**：普通 1200 / 阅读 4000 / 整卷 6000 / 单卷 1 个长阅读板块；`application.yml`
  已同步这些配置项。托福阅读测试大纲见设计稿 §10.7。
- **边界**：自定义考点名不含关键词、且全用单选/多选/判断题考一段原文时，会漏判成普通板块而继续
  1200 截断；整板块丢弃在材料仅略超上限时会丢掉整个大题。
- **建议做法**：① 考点/科目配置加显式 `materialLength`（short/long）字段替代关键词判定，前端可配；
  ② 截断兜底改用一次 plain-client 自检，只剔除不可作答的题，保留可作答题。
- **来源**：2026-10-27 托福考试阅读题材料截断排查与修复。

### 1.8 混合来源错题重练时图片不能逐题回源 — P2

- **现状**：错题快照已经保存每道题的源 `paperId`，错题列表能正确展示图片；但一次重练混合多张源试卷时，
  练习会话只能保存一个会话级 `paperId`，重练作答页只能回看其中一张试卷的资源。
- **建议做法**：把源 `paperId` 下沉到 `PaperNode.PaperMeta`（题目与材料节点各自携带），前端优先使用
  节点级 `paperId`、缺失时回退会话级 `paperId`；同时保持旧试卷树 JSON 的反序列化兼容。
- **来源**：2026-10-28 错题本实现验收。

### 1.9 多实例部署时视觉 provider 仍缺全局配额 — P2

- **现状**：`VisionRequestGuard` 和单卷页执行器都在 JVM 内限流；多实例部署时每个实例仍可各自占满
  provider 配额。页资源保存与最终 fencing 写 `READY` 之间也还有极窄的孤儿资源窗口。
- **影响**：跨实例突发流量仍可能把单 provider 打满；极端竞态下 `paper_assets` 可能留下未被页面引用的对象。
- **建议做法**：接入 provider 侧配额或增加 Redis 全局令牌桶；补一个按 `paperId + attemptId` 清理孤儿资源的巡检。
  代次化后清理还必须排除当前页几何快照、进行中/历史会话和错题快照正在引用的资源；
  不要通过关闭页级 fencing 或放宽并发上限规避问题。
- **来源**：2026-10-29 视觉调用稳定性改造验收；实现与剩余风险见
  `docs/design/视觉调用稳定性改造-设计稿.md`。

### 1.10 `OPTION_ROW` 裁图下沿可能带入下一题题干 — P1

- **现状**：`paperId=35` 的 `p1a4` 现在能正确归属第 4 题，但裁图下沿仍可能包含第 5 题题干。
  这是视觉块边界问题，与“资源挂到哪道题”的确定性归属问题相互独立。
- **影响**：即使归属正确，学生端图片选项或视觉批改输入仍会带入相邻题文字，影响可读性和模型判断。
- **建议做法**：在 `PaperVisualBlockResolverTest` 增加 `OPTION_ROW` 下边界 fixture，断言最后一块
  tile 在下一题题号行之前结束；修复收紧逻辑时不要按整页全局缩短，只处理同一资源块内的下沿。
- **来源**：`docs/design/资源归属确定性改造-设计稿.md` §12 与 2026-10-30 实施验收。

### 1.11 历史识别代次资源暂不回收 — P2

- **现状**：页资源已按识别代次隔离，历史报告、历史会话和错题快照需要继续读取旧图，因此本轮明确不删除旧代次。
  同一页多次重试、整卷重识别和失败尝试会让 `paper_assets` 与对象存储持续累积。
- **影响**：长期使用后数据库资源行和 S3 对象会增长；仅按时间删除会破坏历史报告或错题图片回看。
- **建议做法**：后续单独设计 GC：先扫描当前页几何快照、`paper_json`、错题快照和进行中会话的引用，
  再按“未引用且超过保留期”删除；先 dry-run 统计，再分批清理数据库行和对象存储。
- **来源**：`docs/design/试卷资源版本化与作答快照隔离-设计稿.md` §10.3 与 2026-10-30 实施。

### 1.12 内容锁依赖 Redis 可用性，当前按失败关闭处理 — P2

- **现状**：开始作答和所有试卷内容变更都通过 Redis 获取单卷内容锁；Redis 不可用或锁等待超时时，
  请求会失败，不会在没有版本护栏的情况下继续执行。
- **影响**：逻辑上安全，但 Redis 抖动会暂时阻断作答开始和内容修改；多实例高并发时也缺少内容锁等待、
  获取失败和持有时长的独立观测指标。
- **建议做法**：保持失败关闭，不增加无锁降级；补内容锁等待时间 / 获取失败率 / 持有时长指标和告警，
  再按真实压测结果调整 `PaperContentGuard.LOCK_WAIT_SECONDS`。若未来锁竞争成为瓶颈，优先缩短锁内操作，
  不要把 LLM、S3 或长耗时识别包进锁内。
- **来源**：`docs/design/试卷资源版本化与作答快照隔离-设计稿.md` §G、§H 与 2026-10-30 实施复核。

## 三、工程质量与清理

### 3.2 实体注解与迁移不一致：`fileHash` 的列级唯一 — P2

- **现状**：`PracticePaperEntity` / `KnowledgeBaseEntity` 的 `fileHash` 仍是 `@Column(unique = true)`，而唯一约束已经改成 `(owner_id, file_hash)` 复合索引。
- **影响**：正式库由 Flyway 建表（`ddl-auto: validate`）所以线上没影响；但 H2 `create-drop` 跑测试时会多出一条列级唯一约束，与"同一文件多人各存一份"的语义冲突。
- **建议做法**：删掉这两个字段上的 `unique = true`。
- **来源**：`docs/design/用户数据隔离设计稿.md`「明确不做 / 遗留」。

### 3.3 `PaperRecognitionService` 仍同时承担上传、识别和校对职责 — P2

- **现状**：本轮已把 bbox / 几何纯函数下沉到 `PageGeometry`，但 `PaperRecognitionService` 仍约 1300 行，
  同时包含上传编排、视觉识别执行、页资源裁切、人工校对和确认切题。
- **影响**：后续给上传入口加背压、限流或异步化时，改动会继续集中在一个大类里；单测也只能围绕整个
  Service 构造大量依赖。
- **建议做法**：按设计稿继续拆成 `PaperUploadOrchestrator`（校验 / 去重 / 配额 / 建实体 / 投递）、
  `PaperRecognitionProcessor`（逐页识别与重试）和 `PaperReviewService`（校对 / 页操作 / 确认切题），
  拆分时保持现有 `PaperRecognitionController` 路由和 Stream payload 不变。
- **来源**：`docs/design/试卷上传统一与高并发改造-设计稿.md` §3.5。

### 3.6 本地库里的孤儿向量行 — P2

- **现状**：`vector_store` 里还留着 `kb_id = 5/6` 的向量（对应的资料记录早已不存在），是历史测试遗留。
- **建议做法**：清一次 `vector_store`（或写个"资料不存在就清理向量"的巡检任务）。
- **来源**：本轮核对向量清理时发现。

### 3.7 发版别在服务器上构建镜像（app 镜像在服务器上会构建失败）— P1

- **现状（2026-10-14 实测）**：前端构建上下文已收窄到 `frontend/`（约 6MB）✓，但
  · 服务器上 **BuildKit 不稳定**：`docker compose build frontend` 报过
  `NotFound: forwarding Ping: no such job …`（构建器被打断）；
  · `up -d --build frontend` 会**顺带尝试构建 app 镜像**并失败（1.6G 内存不足），
  报错里只露出 Dockerfile.app 的片段，容易误判成前端的问题；
  · app 镜像必须 `COPY app/build/libs/app.jar`，上下文是仓库根（约 235MB），现传现建要么很慢要么失败；
  · 服务器**导出镜像层也慢**（慢盘，`exporting layers` 要 2~3 分钟）。
- **已改用（推荐固化）**：**本机构建镜像 + 传镜像**：
  `docker build` → `docker save` → `scp` → 服务器 `docker load` → `up -d <svc>`；
  实测 66MB 前端镜像传输 1 分钟，完全不碰服务器的构建器（步骤见运维速查 §6）。
- **仍未做**：CI（`.github/workflows/deploy.yml`）已会构建并推 ACR，但那条链路（含 `context: frontend` 构建）
  还没实际跑通过；正式启用前先跑一次，并验证服务器侧 `deploy-remote.sh` 的拉取与回滚。
- **来源**：2026-10-13/14 两次上线实测。

### 3.8 后台任务缺内存边界与"真超时" — P2（事故归因已修正）

- **现状**：向量化的解析那一步有 2 分钟超时（`DocumentParseService.parseWithTimeout`），但 `future.cancel(true)`
  只是发中断信号——**PDFBox/Tika 不响应中断**，卡住的线程会继续占着 CPU 和内存；文本清洗/分块则完全不在超时保护内。
- **归因修正（重要）**：2026-10-14 那次事故最初怀疑是《数学知识点.pdf》解析卡死，后来用**项目自己的 Tika/PDFBox**
  （fat-jar 里的同一套依赖与相同配置）在本地复现：这份 89.5KB、4 页的 PDF **2.9 秒解析完、抽出 1583 字符、堆仅用 86MB**
  ——文件是无辜的，事故主因见 3.10。
- **仍然建议做**（隐患是真的，只是不是那次的主因）：给解析/清洗/分块统一设"真超时 + 中断"、限制单文件页数/字符数、
  把解析放进有独立内存预算的进程/容器、并让"长时间无进展"的任务自动判失败。
- **来源**：2026-10-14 事故排查（含本地复现）；复现工具 `scripts/inspect-pdf.py`、`scripts/TikaParseProbe.java` + `scripts/run-tika-probe.ps1`。

### 3.10 postgres 反复崩溃重建 + 机器内存余量不足（2026-10-14 卡顿的真因） — P0

- **现状**：postgres 日志里 **12 次** `all server processes terminated; reinitializing`
  （22:31、22:39、22:41、23:07、23:10、23:12、23:48、23:49、23:50、00:29 …）：每次都是一个后端进程异常退出
  （`could not send data to client: Broken pipe` / `Connection reset by peer` 之后 `exited with exit code 2` 或
  `terminated by signal 13`），postmaster 判定为崩溃 → **整个集群重建、所有连接断开**（恢复要 20~40 秒）。
  后果：应用连接池整片失效（app 侧出现一串 Hikari `Failed to validate connection`），用户请求随机失败/变慢；
  而每次重建又会把本来就吃紧的机器再推一把。
- **同时存在的结构性余量不足**：
  - app 容器的 JVM 上限之和 ≈ 容器上限：`-Xmx384m + MaxMetaspaceSize192m + MaxDirectMemorySize64m ≈ 640MB`，
    而 `mem_limit=700m`；实测**正常态就用 570~590MB**，几乎没有缓冲；
  - `-XX:+UseSerialGC -XX:ActiveProcessorCount=1`：内存压力下 GC 只有一个线程，缓不过来；
  - 1.6GB 的机器上跑 7 个容器（合计约 800MB），一旦有额外压力（docker 构建、批量解析等），
    宿主机 `/proc/pressure/memory` 直接到 **some 95%**、CPU 97% 花在内核态（回收）、load 38 → 整机卡死。
  - 注意：postgres 容器的 `memory.events` 里 `oom_kill=0` → **不是它的 256MB 上限被 OOM 打掉的**，
    崩溃是"客户端异常断连 → 后端死 → 集群重建"这条链造成的。
- **推测的触发环**：内存紧张 → JVM 长时间 GC 停顿 → 应用侧请求超时/取消、连接被硬断 →
  postgres 后端崩 → 集群重建 → 应用连接池雪崩 → 更紧张。**待查**：应用侧是谁在硬断连接
  （Hikari 默认 `maxLifetime=30m`、无 keepalive；是否存在查询超时/取消逻辑；pg 侧 `max_connections=30`、`work_mem=2MB` 是否偏紧）。
- **已处置（2026-10-14）**：
  1. app 资源余量：`mem_limit 700m → 900m`、`-Xmx384m → 512m`、`UseSerialGC → UseParallelGC`
     （`ActiveProcessorCount 1 → 2`），实测内存占用从 90%（630/700）降到 70%（630/900），余量 60MB → 268MB；
  2. 连接池加保活与超时：`keepaliveTime=120s`、`maxLifetime=15m`、`connectionTimeout=10s`、`validationTimeout=3s`
     （通过 compose 环境变量即时生效，同时写进 `application.yml` 作为仓库里的默认值）；
  3. 巡检告警已上线：`deploy/health-check.sh` + cron 每 5 分钟检查内存压力/容器内存/pg 重建次数/load，
     超阈值写日志并可推机器人 webhook（见运维速查 §3.1）。
- **第二次事故与收口（2026-10-15）**：12:10 内核 OOM 直接杀掉 app 的 java（`anon-rss:613008kB`，
  memcg 前缀对应 `smart-quiz-app`），随后内核内存回收进入死循环，13:14 起整机僵死，16:05 强制重启才恢复。
  **根因**：容器 `mem_limit` 之和 1700MB > 机器实际可用内存 1613MB（2GB 被 kdump 预留 256MB、固件再占约 130MB），
  于是每个容器都还离自己的上限很远，宿主机先没内存了。处置（均已落到 `/etc` 与 compose，重启后仍生效）：
  1. 关闭 kdump：`systemctl disable --now kdump-tools` + `/etc/default/grub` 加 `crashkernel=0`，
     `MemTotal` 1.58 GB → **1.87 GB**（需重启生效）；
  2. 上限之和重排到 **1440MB**：app `900m → 832m`（`-Xmx448m` + Metaspace192m + Direct48m）、
     postgres `256 → 224`、rustfs `256 → 176`、redis `96 → 80`、frontend/gateway `64 → 48`、certbot `64 → 32`；
  3. `vm.swappiness 0 → 60`（写 `/etc/sysctl.d/99-smart-quiz.conf`，覆盖 `/etc/sysctl.conf` 里的旧值）；
  4. `/etc/docker/daemon.json` 加 `"userland-proxy": false`，让注册接口记到**真实公网 IP**
     （此前一直记成 docker 网桥的 `172.19.0.1`，会把「每 IP 24 小时最多 3 个」退化成全站上限）。

  重启后复核：`available` 约 690MB、app 峰值 797MB/832MB、rustfs 峰值贴着 176MB（但 `memory.stat` 里
  `anon` 仅 50MB，是页缓存被计入 cgroup，内核按需回收）、各容器 `oom_kill=0`。
- **仍未做**：
  1. 查清"应用侧为什么硬断连接"（Hikari 默认 30 分钟 `maxLifetime` 之外，是否有查询超时/取消逻辑；
     是否与 JVM 长时间 GC 停顿有关）——现在加了保活只是降低概率，根因还没定位；
  2. 复核 postgres 参数（`max_connections=30`、`shared_buffers=64MB`、`work_mem=2MB`）与 pg 容器上限是否偏紧；
  3. 观察期：确认 postgres 不再出现新的 `all server processes terminated`（2026-10-14 基线为 12 次）。
     截至 2026-10-15 17:00 未再出现；注意容器在当日 16:2x 重建过，`docker logs` 只从新容器起算，
     跨重建的历史计数要看 `/opt/smart-quiz/logs/health-check.log`；
  4. app 内存余量只剩约 35MB（峰值 797MB / 上限 832MB）。撞上限时是**容器内被杀 + 自动重启**
     （宿主机不再陪葬，`docker inspect -f '{{.State.OOMKilled}}' smart-quiz-app` 可见），

### 3.13 批改失败后没有「一键重批」入口 — P2

- **现状**：批改是异步的，失败时会写 `evaluate_status=FAILED` + `evaluate_error`（界面上能看到原因），
  但会话 `status` 早已是 `COMPLETED`——`POST /api/interview/sessions/{id}/complete` 与再次交卷都会被
  `INTERVIEW_ALREADY_COMPLETED` 拒绝，**用户只能看到失败原因，没有任何途径重新批改**

- **建议做法**：新增 `POST /api/interview/sessions/{id}/evaluate`（归属校验；仅当 `status=COMPLETED` 且
  `evaluate_status ∈ {FAILED, COMPLETED}` 时允许），内部置 `PENDING` 后重新投递；前端在报告页给「重新批改」按钮。

### 3.14 填空题不做数值等价：`1/2` 与 `0.5` 会被判错 — P2

- **现状**：`ObjectiveAnswerGrader#gradeFillBlank` 在「归一化后不相等」且参考答案属于「纯数字/字母/运算符」
  （正则 `[0-9a-z/\-+.=]+`）时**直接判 0 分**，不再交回模型。于是数学/物理类填空题里
  `1/2` vs `0.5`、`0.50` vs `0.5`、`100` vs `100.0` 这类**等价写法会被判错**；
  去标点后不排序，所以**多值答案顺序不同也会判错**（如参考答案 `A、B`、学生写 `B，A` → `ab` vs `ba`）。
- **影响**：这类学科容易出现「答对了却 0 分」，用户体感差；换来的是零成本、可复现（不引入模型就没有幻觉）。
- **建议做法（任选其一）**：① 对纯数字答案先做数值规范化比较（分数转小数、去尾零，`BigDecimal` 即可，不需要表达式引擎）；
  ② 或把「纯数字但形式不同」的情况交回模型判等价（只在这类题上触发，成本很低）；
  ③ 或加配置开关（如 `app.interview.evaluation.plain-answer-strict`，默认严格，需要时放宽）。
- **来源**：2026-10-15 写 `docs/design/作答批改报告逻辑详解.md` §10.3 逐分支核对时发现。

### 3.15 注册的两层限制颗粒度不一致（共享出口 IP 会先撞请求级限流） — P2

- **现状**：`/api/auth/register` 上有两层限制——请求级 `@RateLimit` 同 IP **5 次/小时**，
  以及成功配额同 IP **3 个/24 小时** + 全站 **5 个/天**。2026-10-15 线上验收时实测：
  同一出口 IP 连续成功注册 4 个（第 4 个被 12014 配额拦下）后再发请求就变成 `8001 请求过于频繁`，
  说明**请求级限流比成功配额更早触发**，而且把失败请求（用户名被占用、密码不合规）也算进去。
- **影响**：学校/公司/家庭这类共享 NAT 出口下，几个人先后注册会互相挤占额度；用户自己输错一次也要占掉一次。
- **建议做法（任选）**：① 请求级限流放宽到 10~20 次/小时，成功配额仍兜底；② 只对**失败**的注册请求计入请求级限流；
  ③ 给管理员留"白名单 IP"旁路（用户此前明确说先不做邀请码，可留作以后）。
- **来源**：2026-10-15 部署后线上验证注册配额时实测触发。

### 3.16 每次续期会多发一个"没人持有"的刷新令牌 — P2

- **现状**：`AuthService.refresh()` 先调 `refreshTokenService.rotate(rawToken, …)`，而 `rotate()` 内部**已经**
  `issue()` 了一个新刷新令牌，并把它的 tokenId 写进旧行的 `replaced_by`；但 `rotate()` 的返回值只有 `userId`，
  这个令牌被丢弃。紧接着 `AuthService` 又调了一次 `refreshTokenService.issue(...)`，**把第二个令牌写进 Cookie**。
- **后果**：
  1. 每次续期往 `refresh_tokens` 写 **2 行**，其中 1 行是客户端永远不会持有的"孤儿令牌"，`revoked_at` 一直为空，
     要等 30 天过期才被 `purgeExpired` 清掉；
  2. `replaced_by` 指向的不是客户端手里的那个令牌，**令牌重放/泄露排查时这条链是错的**；
  3. 孤儿行仍是「有效刷新令牌」，库或备份一旦泄露可以直接换 Access Token。
- **线上证据（2026-10-15）**：`user_id=1` 共 30 行、其中 14 行仍未撤销未过期；典型三元组
  id=79（16:49:37.856511 撤销，`replaced_by` = id80 的 tokenId）、id=80（16:49:37.856882 签发、`replaced_by` 为空）、
  id=81（16:49:37.888543 签发、`replaced_by` 为空）——79→80 是 `rotate()` 的产物，81 才是真正下发到浏览器的那个。
- **建议做法**：让 `rotate()` 返回 `(userId, newRawToken)`，`AuthService.refresh()` 直接用它，删掉多余的那次 `issue()`；
  补一条测试断言「一次 refresh 只新增 1 行，且旧行的 `replaced_by` 指向它」。历史孤儿行不必手工删（30 天后自动过期清理），
  想立刻收敛可以按 `revoked_at is null and id not in (客户端持有的那些)` 清一次——但客户端持有哪些服务端并不知道，
  所以更稳的做法是等其自然过期，或直接 `revokeAllForUser` 让所有人重新登录一次。
- **来源**：2026-10-15 为解释鉴权链路逐行读代码 + 核对生产库 `refresh_tokens` 时发现。
