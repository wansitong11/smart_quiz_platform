# 待优化事项（统一清单）

> **这个文件是"已知该做、但还没做"的唯一入口**：功能增强、工程质量欠账、验证时发现但暂缓的问题都记在这里。
> 做完一项就把对应条目删掉（或移到 `docs/改造说明.md` 的"已完成"里），不要在多处各留一份。
>
> 记录约定：每条写清 **现状 → 建议做法 → 优先级 → 来源**（哪个设计稿/哪次验证发现）。
> 优先级：**P0**＝影响正确性或线上可用性，尽快做；**P1**＝该做，有明显收益；**P2**＝优化/清理，可延后。

## 一、教学内容（学科板块与资料）

### 1.1 学科板块与参考资料仍是高中口径 — P1（已定"后置"）

- **现状**：`app/src/main/resources/skills/{math,chinese,english}/skill.meta.yml` 里的板块是「集合与不等式 / 函数与导数 / 数列 / 三角函数与解三角形 / 立体几何与解析几何 / 概率与统计」这类**高中板块**；`_shared/references/*.md` 里同样写着"高考高频 3500 词""高中课标篇目""新高考重点"。
- **影响**：模拟测验选「数学」时抽的就是高中板块；小学知识库虽然 persona 已按学段自适应（见 `docs/design/知识库出题-追加与难度统一.md`），但**板块表本身**仍是高中那一套，做小学测验时对不上。
- **建议做法**：为小学（必要时加初中）设计一套学科板块 + 对应参考资料，与现有高中那套共存，按知识库/资料的实际学段选择；需要先定学段范围与学科范围（语数英 or 更多），属于内容设计工作。
- **来源**：知识库出题改造时确认（用户决定"放到后面优化"）。

### 1.2 切题漏题没有校验 — P1

- **现状**：同一份《高三语文模拟试卷》两次切题，一次切出 23 题/150 分、一次只有 22 题/144 分——模型漏掉了第 9 题（6 分），而流水线里 `warnings_json` 是空的，界面照常显示 144 分，没有任何提示。
- **根因**：`PaperQuestionExtractionService` 分批切题时，`splitByQuestionNo()` 已经从原文扫出权威题号集合、`buildScopeInstruction()` 也告诉了模型本次处理哪几题，但回包后**只判断"整批没返回"**，没有比对"期望题号 vs 返回题号"。
- **建议做法**：① 每批回包做题号对账，缺题就写一条 warning（"第 9 题未识别到，卷面总分可能偏低"）；② 对缺失题号做一次**定向补抽**（prompt 只要求这几题）再合并；③ 前端把 `warnings` 展示到解析页，别让用户自己算总分。
- **来源**：用户反馈"解析出来是150分，但显示144"。

### 1.3 出题可选"覆盖"模式 + 保护手工题 — P2

- **现状**：生成题目已改为**追加**语义（不覆盖）。若用户想"清空重来"，目前只能自己去题库里删。
- **建议做法**：生成弹窗加「生成方式：追加（默认）/ 覆盖」；覆盖要二次确认，并**保护手工新增/编辑过的题**——需要给题目加 `source`（GENERATED / MANUAL）或 `edited_by_user` 标记（一条迁移），覆盖只删模型生成且未被编辑过的。
- **来源**：知识库出题改造时讨论（用户选"追加"，覆盖方案暂缓）。

## 三、工程质量与清理

### 3.1 后端测试编译不过 — P1

- **现状**：`./gradlew :app:test` 停在 `:app:compileTestJava` FAILED，一个测试都跑不起来。6 个测试类没跟上服务构造参数（新增 `OwnerScope`）与 `QuestionDTO` 记录字段（新增考卷字段）的变更：`InterviewPersistenceServiceTest`、`KnowledgeBaseInterviewServiceTest`、`KnowledgeBaseQuestionServiceTest`、`KnowledgeBaseUploadServiceTest`、`QuestionGenerationAsyncTest`、`QuestionGenerationStateServiceTest`。
- **建议做法**：补齐 mock/构造参数与记录字段；顺手给题库生成补一条"追加不删除"的回归测试（`QuestionGenerationStateServiceTest` 里已按新语义改好断言，只等编译通过）。
- **来源**：用户数据隔离改造后遗留；本轮已同步更新受影响断言，但整体仍编不过。

### 3.2 实体注解与迁移不一致：`fileHash` 的列级唯一 — P2

- **现状**：`PracticePaperEntity` / `KnowledgeBaseEntity` 的 `fileHash` 仍是 `@Column(unique = true)`，而唯一约束已经改成 `(owner_id, file_hash)` 复合索引。
- **影响**：正式库由 Flyway 建表（`ddl-auto: validate`）所以线上没影响；但 H2 `create-drop` 跑测试时会多出一条列级唯一约束，与"同一文件多人各存一份"的语义冲突。
- **建议做法**：删掉这两个字段上的 `unique = true`。
- **来源**：`docs/design/用户数据隔离设计稿.md`「明确不做 / 遗留」。

### 3.3 遗留错误码常量与语义不符 — P2

- **现状**：`RESUME_NOT_FOUND(2001)` / `INTERVIEW_SESSION_NOT_FOUND(3001)` / `KNOWLEDGE_BASE_NOT_FOUND(6001)` 已经没有业务引用了（越权统一走 `NOT_FOUND(404)`）；只剩 `PaperTree` 用 `INTERVIEW_SESSION_NOT_FOUND` 表达"试卷结构为空"，语义不符。
- **建议做法**：清理无用常量；`PaperTree` 那处换成 `BAD_REQUEST` 或 `INTERNAL_ERROR`。
- **来源**：越权返回码统一改造。

### 3.4 疑似死代码：前端 `components/HistoryList.tsx` — P2

- **现状**：`frontend/src/components/HistoryList.tsx` 没有任何地方 import（页面用的是 `pages/HistoryPage.tsx`），而且它调用的 `historyApi.getStatistics()` 打的是 `/api/resumes/statistics`——**后端根本没有这个接口**。
- **建议做法**：直接删掉这个文件；若将来真要做试卷统计，再补后端接口。
- **来源**：本轮排查"/api/resumes/statistics 是否存在"时发现。

### 3.5 `RagChatMessageRepository` 里一段注释没闭合 — P2

- **现状**：`countBySessionId` 上方只写了 `/**` 没有 `*/`，导致该方法被注释掉、且把下一个方法的 javadoc 一起吞了（现在能编译只是因为没人调用它）。
- **建议做法**：补上 `*/`（或按意图删掉这个方法）。
- **来源**：排查仓库方法时发现。

### 3.6 本地库里的孤儿向量行 — P2

- **现状**：`vector_store` 里还留着 `kb_id = 5/6` 的向量（对应的资料记录早已不存在），是历史测试遗留。
- **建议做法**：清一次 `vector_store`（或写个"资料不存在就清理向量"的巡检任务）。
- **来源**：本轮核对向量清理时发现。

### 3.7 后端发版仍要传 235MB 的 jar — P2

### 3.8 知识库解析没有超时，单份文件卡死就能拖垮整机 — P0

- **现状（2026-10-14 00:02 线上事故）**：用户上传一份 **90KB** 的《数学知识点.pdf》，向量化消费者走到
  `DocumentParseService` 的「开始解析文件（从字节数组）」后**再也没有输出**（解析成功的 INFO 日志始终没出现），
  说明进程卡在 Tika/PDFBox 解析内部；同时 JVM 持续分配把容器内存顶到 687MB/700MB，
  宿主机 `/proc/pressure/memory` 的 some 到 **95%**、CPU 97% 花在内核态（内存回收），load 冲到 38，
  站点卡到基本不可用；期间 **postgres 一个后端进程被拖崩**（postmaster 自动恢复、数据无损）。
  排障时只能把该知识库置为 FAILED + 清掉 Redis 里那条待确认消息 + 重启 app 才恢复。
- **根因要点**：
  1. 解析没有**超时/中断**：Tika 一卡就无限期占着线程 + CPU + 内存（这是本次的主因）；
  2. 资源余量太小：app 容器上限 700MB，正常态已用约 **570MB**，单任务一膨胀就顶到上限，
     触发内核不停回收（表现为 `sy` 高、内存 PSI 高），把同机所有服务一起拖慢；
  3. 恢复调度器虽然有 `maxRecoveryCount=3`（到上限会转 FAILED），但**卡死在解析里的线程**它管不了，
     所以"卡住 → 补投 → 再卡"这类循环仍要靠人工介入。
- **建议做法**：
  1. 解析加超时（放进独立线程 + `Future.get(timeout)`，超时判 FAILED 并中断），并限制单文件页数/字符数，
     超限直接提示「请转成 txt 或拆分后上传」；
  2. 给解析设内存边界（独立进程/容器，或限制文档尺寸与并发），别让单个任务吃满整个容器；
  3. 视余量把 app 的 `mem_limit`/`-Xmx` 抬一档（当前 idle 570MB/700MB 几乎没有缓冲）；
  4. 把"解析/向量化长时间无进展"做成告警（而不是等用户先感觉到慢）。
- **来源**：2026-10-14 线上事故根因分析。

### 3.9 缺资源水位告警 — P2

- **现状**：这次的症状是"站点慢慢变卡"，先由用户感知；主机内存 PSI 到 95%、load 38、容器内存接近上限
  都没有任何告警，只能靠人上服务器看。
- **建议做法**：至少在服务器上放一个轻量巡检（cron 每 1~5 分钟采一次内存 PSI / 容器内存 / load，
  超阈值就发通知），或接阿里云云监控告警。
- **来源**：2026-10-14 线上事故。

- **现状**：前端已经不算问题了——构建上下文收窄到 `frontend/`（约 2MB，秒级，见 `frontend/Dockerfile` 与 `deploy/docker-compose.server.yml`）。但后端镜像必须 `COPY app/build/libs/app.jar`，上下文仍是仓库根（约 235MB），在这台 1.6G 的机器上现传现建还是慢。
- **建议做法**：后端走 CI（`.github/workflows/deploy.yml` 已经会构建镜像并推 ACR）或本地 `docker build` + `docker save | gzip` + `scp` + `docker load`，避免在服务器上现传现建。
- **来源**：2026-10-13 上线实测（当时前端也要 13 分钟，已修）。
