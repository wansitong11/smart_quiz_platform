## 一、这个项目是什么

把上游开源项目「AI 面试官平台」改造成面向**个人职业资格 / 考证备考**的 AI 学习平台。
用户上传自己的习题、试卷或资料，由系统完成识别、切题、练习、批改、历史复盘和知识库问答。

产品最终定位已经确定为「个人备考」，但当前代码和数据库命名仍保留试卷、练习等教育语义；
**业务概念批量重命名暂缓**，先保证切题、作答、批改和报告链路正确，再统一改造名称与文案。
简历项目名称可使用：**AI 个人备考平台：习题导入、智能练习、复习与知识库问答**。

改造原则：**保留后端骨架，替换业务外壳，补上教育内核**。骨架（Redis Stream 异步、限流、
结构化输出、统一评估引擎、RAG、对象存储、PDF 导出、SSE/WebSocket、Micrometer）继续沿用。

主要产品线：

| 能力 | 入口 | 说明 |
| --- | --- | --- |
| 试卷分析 | `/papers` | 上传做过的试卷 → 结构化切题 → 整卷作答 → 一次交卷 → 批改报告（含按小节得分） |
| 扫描件识别 | `/papers` 上传区 | 扫描 PDF / 拍照 JPG/PNG → 视觉模型逐页转写 → 预览校对 → 确认后切题 |

| 资料问答 | `/knowledgebase/chat` | 上传资料 → 向量化 → 检索问答（范围可选：全部资料 / 按分类 / 指定资料） |
| 资料库管理 | `/knowledgebase` | 资料上传、分类、向量化状态、重新向量化 |

## 四、核心机制（改相关代码前必读）

### 4.1 试卷层级树（唯一数据源）

- 切题产出 `PaperTree`（`PAPER → SECTION → QUESTION_GROUP(MATERIAL + QUESTION) / QUESTION`），
  落在 `practice_sessions.paper_json`
- 扁平题目列表由 `PaperTree.flattenQuestions()` **运行时派生**，不落第二份
- `depth` / `leaf` / `meta` 由 `PaperTree.recalculate()` 回写；同级顺序按 `order`
- 批改上下文用 `PaperTree.contextOf(index)`（路径上的小节标题 + 材料原文）
- 前端按节点类型统一经 `NodeBlock` 渲染（`components/PaperTreeView.tsx`）；根级和嵌套
  `MATERIAL` 都通过 `MaterialBlock` 显示正文，整篇阅读文章直接挂在 PAPER 下时也不会只显示标题
- 答题卡按最近小节分段

### 4.2 题型与判分

- 题目统一用 `InterviewQuestionDTO`：`questionType`（SINGLE_CHOICE / MULTI_CHOICE / TRUE_FALSE / FILL_BLANK / SHORT_ANSWER / READING / WRITING / CASE_ANALYSIS / OTHER）、`options[{key,text}]`、`fullScore`、`referenceAnswer`、`keyPoints`、`scoringRubric`、`analysis`（解析）
- 客观题走 `ObjectiveAnswerGrader` **确定性判分**（不调用模型）；评语拼「你的选择 / 正确答案 / 考点」，解析由报告单独展示
- 判断题固定生成「正确 / 错误」选项，按单选同路径本地判分；案例分析走主观题统一评估引擎
- 主观题走统一评估引擎；报告按分值折算卷面分（`utils/paperScore.ts` 与后端同口径）
- 试卷切题后由 `AnswerKeyPreparationService` 预生成内部答案键：纯文字题走 plain chat，含图题按页走视觉模型；
  答案键存在结构快照中，**不进入学生端结构预览 / 作答接口**
- 选择题答案采用三段式生成：主求解 → 独立复核 → 仅冲突题第三次裁决；
  主求解和复核使用 non-thinking 普通客户端，冲突裁决使用单题 reasoning ChatClient。
  这样既避免整批开启 thinking 导致 60 秒超时，又不把思考过程放进学生文案
- 答案权威顺序为「人工 > 卷末官方答案 > 结构显式答案 > AI（TEXT/VISION）」；
  结构答案写入时带 `source=STRUCTURE`，卷末答案区解析为 `source=OFFICIAL`，AI 只补真正缺失的题
- 答案键按题复用：每题保存 `fingerprint`（题型 + 规范化题干 + 选项 + 来源行/页），
  题号存在且指纹一致才复用；题干变化只重算该题，不再“题号集合不一致就整张作废”
- 主观题用 `answerMode` 表达评分依据：`FIXED`（必须有确定答案）、`SAMPLE`、`RUBRIC_ONLY`、
  `MANUAL_REVIEW`；无评分依据只转人工复核并记 warning，不阻断整卷
- 当前 `TEXT_BATCH_SIZE=10`；解析付费模型默认 `analysis-batch-size=3`，免费文本模型默认 4 题/批，
  固定批次冷却默认 0 秒；一致时正常 8 题文字卷共 2 次答案批量调用 + 2 次解析批量调用，冲突题才追加
  reasoning 裁决
- 答案键批次、解析批次和结构分块统一走分轮背压：执行器队列满时先等待已提交任务完成，
  再提交下一轮，不在 Stream 消费线程内联调用模型；每批成功后增量落库，进程中断不会丢掉已成功题
- 解析按小批次生成，既避免逐题调用打满同一分钟 RPM，也避免一次输出过长导致 JSON 截断；
  解析前若检测到 `PAPER_EXTRACTION` 当前分钟 RPM 已满，会等待窗口恢复，最多
  `analysis-rate-limit-max-wait`（默认 65 秒）；上游 429 统一按限流失败处理，优先读取
  `Retry-After`，没有响应头时按 5 秒起步退避（单次最多 30 秒），只重试当前解析批次
- 结构切题、答案主求解/复核/裁决、解析批次共用同一 pacer；本地 `AI_RATE_LIMIT_EXCEEDED`、
  上游 429 和视觉并发拒绝都按“限流/可等待”处理，不再直接判确定性失败
- 解析失败不会伪造解析：缺题或整批失败时写入“解析未生成，请稍后重新生成。”并记录
  “第 X 题解析未生成，已保留标准答案”的 warning；报告页继续展示真实 `analysis`
- 选择题答案协议增加 `derivedResult`：模型先返回映射选项前的计算结果，再返回
  `selectedOptions`；后端优先按计算结果匹配选项，冲突时纠正错误字母
- `AnswerConsistencyResolver` 输出 `CONSENSUS / MAJORITY / CONFLICT / SINGLE`；
  2:1 采用多数答案，三者都不同时保留最高置信度候选并标记低置信度，不能重新落成“暂缺”
- 答案键即使置信度低于 60 也必须保留候选答案；只有空白或“暂缺”才视为答案键缺失。
  已有候选时客观题正常判分，主观题正常评估，`practice_answers` 和报告标记低置信度；
  视觉主观题失败标记 `MANUAL_REVIEW`，不自动给 0 分
- 答案必须由答案键模型调用阶段直接返回；缺答案时带具体 `questionIndex` 重试，最多 3 次，
  仍缺失的题转 `MANUAL_REVIEW` 并记 warning，不阻断整卷，也不能把“暂缺”当作可用答案键
- `practice_answers` 通过 `V20261022__grading_quality_metadata.sql` 保存 `score_status / low_confidence /
  answer_key_confidence / score_message`，历史报告重新打开后提示不会丢失

### 4.3 资料分类与检索范围

- 分类表 `kb_categories`（code / name / subject_code / sort_order / is_system），资料用 `knowledge_bases.category_code` 关联；code 是系统标识，改名不影响历史数据与历史会话
- 会话范围 `rag_chat_sessions.kb_scope`：`ALL`（默认）/ `CATEGORY` / `SELECTED`；解析器在 `service/scope/`，检索层只认「一组 kbId 或空集合」
- 跨库召回：`topK × candidate-multiplier` 召回 → 每份资料保底 `per-kb-quota` 条 → 剩余按分数补齐 → 收口 topK
- 回答末尾追加「出处」块；资料提问计数按**实际命中的资料**归位，不按会话范围全量加

### 4.4 问答工具化（function calling）+ ChatMemory + 轨迹

- 两个工具（`service/tool/`）：`search_knowledge_base`（检索范围通过 `ToolContext` 隐式注入，模型不能改范围）、`get_conversation_history`（`ASC` 取最早 / `DESC` 取最近）
- 对话上下文由 Spring AI `ChatMemory` + `MessageChatMemoryAdvisor` 注入；`RagChatMemoryRepository` 是**只读适配**（读 `rag_chat_messages`，写操作空实现，落库仍由业务侧负责），窗口裁剪在读取侧按 `app.ai.rag.tools.chat-memory-max-messages` 完成
- 主流程**没有**规则式意图路由：模型按工具描述自行决定是否调用；预检索片段仍会注入作为保底
- 轨迹表 `rag_query_traces`（intent / outcome / tools_json / retrieved_kb_ids / top_score / latency_ms），榜单接口 `GET /api/rag-chat/traces/summary | /no-hit-questions | /unused-knowledge-bases`
- 2026-11-13 新增可选的“补邻后短复核 → 流式回答 → 有效编号出处”链路；同步、普通流、预检索及工具搜索共用，工具结果也不能跳过复核。原文与章节不再被摘要替换。
- `app.ai.rag.review.enabled` 默认 `false`，环境变量 `APP_AI_RAG_REVIEW_ENABLED`；不是原有分数筛选开关。复核 provider 留空复用现有档位文字模型，不需要新密钥，不迁移历史库。
- 启用后出处按回答实际有效引用生成，不按检索命中汇总；请求内编号/缓存、累计 6000 token 和最多两批新复核共同约束。复核失败中断，不恢复未复核资料。默认关闭时仍走旧出处规则。
- 代码与真实验证分开看：完整设计/签名见 `docs/design/RAG轻量复核与流式引用-设计稿.md`，原始证据、严格门禁和运行启用状态见 `docs/design/RAG轻量复核与流式引用-实现验证报告.md`。不要把“代码完成”直接当成“已为 IDEA 运行环境启用”。

### 4.5 图片试卷识别（视觉模型 → 文本 → 复用切题）

- 详细方案见 [`docs/design/复杂试卷识别与结构化-设计稿.md`](design/复杂试卷识别与结构化-设计稿.md)
- 入口 `POST /api/papers/upload`（1~10 个 PDF/JPG/PNG，合并为一份试卷）；旧 `POST /api/resumes/upload` 遇到无文字层 PDF 会自动转到这条链路
- 输入统一成 `Document → Page(行 + assets)`：PDF 用 PDFBox 取文字行与图片位置；DOCX 用 POI 顺序取段落与内嵌图片（不走视觉模型）；JPG/PNG 每张一页走视觉模型
- 页源判定不再只看字符数：图像覆盖率 >50% 且字符 <150、或字符 <120 且无题号，一律走识图（修复"第一页只有标题文字层导致正文丢失"）
- 结构化改为"模型标块类型 + 行号，后端按行切片建树"（`PaperStructureService`），不再依赖中文数字标题正则；
  支持 PART/SECTION/MATERIAL/QUESTION/SUB_QUESTION/BLANK，后端还会生成内部 `EXCERPT`
- 切题前 `PaperSubQuestionFoldNormalizer` 先按 `(type, startLine, endLine)` 去重，
  再把被 `QUESTION` 行号范围完全覆盖且自身无分值的 `SUB_QUESTION` / `BLANK` 折叠进父题；
  有独立分值的子问仍走题干组拆问。答案键复用前逐题校验 `fingerprint`，
  题干或选项变化的题单独丢弃重算，其余题继续复用
- `PaperMaterialHierarchyNormalizer` 会把跨页续写材料合并；题目旁重复展示的段落摘录按正文
  6~12 字符 n-gram 覆盖率识别（阈值 88%），不依赖 `Paragraph 1`、`第 1 段` 等固定标签。
  重复段落只参与行覆盖，不切换材料父节点，保证题目仍挂在完整阅读文章下
- 作答端 `PaperTreeView` 的统一节点入口同时支持根级和嵌套 MATERIAL，整篇阅读文章直接位于根节点时
  也会渲染正文，不会只显示材料标题
- 页面资源落 `paper_assets`：图形选项 `OPTION_ROW` 用墨迹投影切分（等宽兜底），题干图 `FIGURE`；`QuestionOption.assetId` 驱动前端图片选项
- 行内标记 `{{字}}` = 加点、`[[u:]]` = 下划线、`[[w:]]` = 波浪线；前端 `MarkupText` 渲染
- 页级状态表 `paper_pages`（source=TEXT/IMAGE、status、text、image_key、attempt），试卷状态 `practice_papers.recognition_status`：`PENDING → PROCESSING → NEEDS_REVIEW → EXTRACTING → READY`
- 切题阶段失败或入队失败时，已确认的识图卷会把 `EXTRACTING` 恢复为 `READY`，同时保留
  `analysis_status=FAILED`；确认接口只把 `PENDING / PROCESSING` 视为真正在途，失败残留可直接重新切题
- TXT / DOCX / 带文字层 PDF 在统一上传入口内直接生成 `TEXT/READY` 逻辑页，
  再用 `PageTextMerger.mergePlain` 合并正文；所有新任务只走 `PaperStructureService`
- 切题错误按 `STRUCTURE` / `ANSWER_KEY` 阶段落库；模型连接中断归类为
  `AI_SERVICE_TIMEOUT`，不再统一伪装成“试卷切题失败：请稍后重试”
- 逐页判定：PDF 有可信文字层就零成本直接用；抽不到/乱码/短页无题号才渲染成 JPEG 调视觉模型
- 视觉客户端独立：`LlmProviderRegistry.getDefaultVisionChatClient()`，独立缓存键 `:vision`、独立默认项 `app.ai.default-vision-provider`（默认 `dashscope-vl` / `qwen3.8-flash`），**不挂 SafeGuard／Memory／Tools**
- 所有模型客户端都设置 **callTimeout**（`app.ai.chat-request-timeout` 默认 5m、`app.ai.vision-request-timeout` 默认 3m），并把 SDK 的 `maxRetries` 设为 0，重试统一交给 `StructuredOutputInvoker`。只设 readTimeout 不够：HTTP/2 连接靠 PING 保活时 socket 不空闲，服务端迟迟不返回响应头会让调用永久挂住；SDK 内部再重试还会把"单次超时"成倍放大
- 视觉调用统一为单次入口并经过 `VisionRequestGuard`：单 provider 在途上限默认 4、有界等待、CLOSED / OPEN / HALF_OPEN 轻量熔断；运输超时不原地重发
- 每页视觉调用总预算默认 3。单阶段路径按失败分类有限重试；输出 JSON 在结束前截断归类为 `OUTPUT_TRUNCATED`，只做一次减少输出的定向重试。两阶段路径由
  `PaperPageVisionRecognizer` 先 OCR、再按需定位资源几何，OCR 最多使用「总预算 - 1」，几何失败不会回头重新 OCR
- 单阶段只要求模型输出 `lines`，整页 `text` 由后端派生；“加点 / 着重号”无标记时不重抽整页，只追加人工校对提示
- `app.paper.recognition.two-stage-recognition-enabled` 默认 `false`；固定样本验收前保留现有单阶段兼容路径
- 识别只做"图片 → 保留版式文本"；切题统一走 `PaperStructureService` 的行号块树与默认文本模型
- 结构模型按页面行号定位题目和页面范围，结果写入 `InterviewQuestionDTO.sourcePageFrom/To`
- 异步任务 `paper:recognition:stream`，与切题同构的条件领取、心跳、fencing token 与卡死恢复
- 单卷内图片页通过统一 `BoundedExecutor` 并行，默认 3 个 worker，且不得超过 `PAPER_IMPORT` 预算并发与视觉准入上限；Redis 仍是一卷一条消息，
  不修改 Producer / Consumer 协议。`paper_pages.recognition_attempt_id` 负责页级 fencing，只有当前
  attempt 能写 `READY / FAILED`，恢复扫描不会重跑已完成页
- 页图存私有 S3（`papers/{paperId}/pages/{n}-{random}.jpg`），通过 `GET /api/papers/{id}/pages/{n}/image` 按归属鉴权读取
- `OPTION_ROW` 的视觉 bbox 可能过高；识别时限制高宽比，`OptionRowSplitter` 再按 `layout`
  做纵向收紧，选项 tile 每次切题覆盖更新，避免继续展示旧的长图
- 资源归属不再由结构模型 `assetRefs` 决定：识别阶段把行 bbox 与最终资源 rect 写入
  `paper_pages.assets_json`，切题阶段用 `PaperAssetOwnershipResolver` 按同栏 + 纵向距离计算；
  TEXT 页由 `TextPageGeometry` 补齐行几何，DOCX 图片使用解析行号生成合成 rect
- 页资源键按识别代次隔离为 `基础 key@12 位识别代次`。重新识别、重试页或整卷重识别不会覆盖旧图；
  历史会话、历史报告和错题快照仍可按旧键读取，当前结构只消费当前页几何快照中的资源键
- 图片选项 `OPTION_ROW` 每次按当前行图重新切分当前代次的 `OPTION_ITEM`，不再复用同父节点下的旧切片
- 试卷内容版本 `practice_papers.content_revision` 在页识别成功、改文字、删页、确认切题和重新分析时原子推进；
  PAPER 作答会话创建时冻结 `paper_content_revision`
- 改页、删页、重试、重识别、确认切题和重新分析统一受试卷内容锁与活动会话检查保护。锁只覆盖短操作，
  不包住 LLM、S3 或长耗时识别；Redis 不可用时请求失败关闭，不会在没有护栏时继续改内容
- 开始作答时 `CREATED` 立即转 `IN_PROGRESS`。进行中会话版本过期则拒绝继续，未开始且版本过期的草稿会被忽略；
  已交卷后再次作答从当前结构重建题目树，不复用上一场 `PaperTree`
- 批改消费者在解析旧树和调用视觉模型前校验会话冻结版本；版本不一致直接失败关闭，不自动用新资源重批旧会话
- 连续 MATERIAL 与其后连续 QUESTION 由 `PaperQuestionGroupAssembler` 生成 `QUESTION_GROUP`；
  题组内多段材料共同进入批改上下文，结构 hash 同时包含文本、资源几何和层级 schema 版本
- 结构缓存 `practice_papers.structure_json` 当前保存 `PaperStructureSnapshot`：行号块树 + 内部答案键；
  `practice_papers.structure_hash` 由页文本、规范化资源几何和层级 schema 版本共同生成
- 公共接口通过 `InterviewQuestionDTO.forAttemptView()` / `PaperTree.forAttemptView()` 移除答案键；
  内部答案键维护走仅管理员可访问的 `PUT /api/admin/papers/{paperId}/answer-keys/{questionIndex}`
- 开始作答前会检查客观题答案键；只有候选答案为空或“暂缺”时才自动触发重新分析，
  低置信度但已有答案不阻止作答
- 答案键解析在 Prompt 中通常要求 200~500 个中文字符、最长约 500；代码硬限制解析 520 字符、
  图形摘要 120 字符、最终评语 900 字符，旧快照加载时也会自动裁剪
- 解析生成和最终展示都会过滤“等等 / 不对 / 让我重新算 / 逆向推演”等草稿式句子，
  不把模型内部试算暴露给学生
- 含图题优先使用选项/题干/材料裁图；整页图只在裁图缺失时兜底，避免同页多题重复发送整页造成视觉 token 浪费

### 4.6 模拟测验考试科目化（考试 → 科目 → 考点）

- 目录分层为「考试 → 科目 → 考点」：系统考试固定内置（教师 / 初级会计 / 计算机 + 归档的
  中小学学科练习 + 其他自定义桶），系统科目放 classpath `skills/{subjectCode}/skill.meta.yml`，
  考试分组放 `skills/_exams.yml`；用户自定义科目落库 `quiz_subjects`（`owner_id` 归属 + 软删除）
- 组卷入参 `skillId` 语义是「科目代码」，后端由 `QuizCatalogService.resolveSubject()` 统一解析
  系统 / 自定义科目，把考试名、考点、题型默认分与权重、大纲文本注入组卷 Prompt
- 自定义科目配置存 `config_json`：说明、平铺考点、题型 + 默认分 + 权重、建议时长（仅展示）、

- 判断题 `TRUE_FALSE` 本地判分、案例分析 `CASE_ANALYSIS` 走主观批改；计算机类按后端面试风格
  以简答为主（权重 7:2:1，简答约 70%）
- 材料长度分档：普通板块单篇 1200 字、阅读型板块单篇 4000 字、整卷合计 6000 字、单卷最多 1 个
  长阅读板块；阅读材料被截断时整板块丢弃（宁缺毋错），题目只基于最终材料命制，避免「题在料缺」。
  对应配置为 `app.quiz.max-reading-material-chars-per-material` /
  `max-total-material-chars` / `max-long-reading-sections-per-paper`；改 Java 默认值时必须同步
  `application.yml`（yml 的 3600 曾覆盖类默认值）

### 4.7 产品级错题本（收录 → 分类 → 回顾 → 重练 → 掌握）

- 详细方案见 [`docs/design/错题本改造-设计稿.md`](design/错题本改造-设计稿.md)
- 只收录 `QUIZ` / `QUIZ_WRONG` 来源，错题按 `owner_id + question_key` 唯一聚合；同一题多次做错只保留一条
- 指纹由科目、题型、归一化题干、归一化选项组成；选项图片 `assetId` 参与身份，READING 额外并入
  章节标题与材料原文，避免不同阅读材料误合并
- `wrong_questions` 保存完整原题快照（题干、选项、材料、答案键、`paperId`/图片资源 ID），
  列表另行保存我的答案、参考答案、解析、得分率和掌握进度；快照不依赖源会话
- 状态为 `PENDING / MASTERED / ARCHIVED`；累计答对 3 次自动掌握，答错清零并降级；
  支持手动移出/恢复；只有批改回写会按答题结果改变学习状态，列表查询不会改写状态
- 列表按考试 → 科目 → 考点分组，支持状态、考点、题型、关键字筛选和分页；状态页签计数
  在当前科目/考点/题型/关键字范围内统计
- 重练支持勾选题目与按当前筛选范围随机抽题；随机只抽 `PENDING`，默认 10 题、上限 20 题
- 批改完成（EVALUATED）后由 `EvaluateStreamConsumer` 回写；会话行锁 + 逐题事件唯一键保证
  异步重试不重复累计
- 历史回填保留用户手动设置的 `ARCHIVED` 状态；重练页展示单张源试卷的题干图、材料图和图片选项
- 图片回看依赖源试卷资源仍在；源会话删除不影响题干、选项文字、材料、答案与解析快照
- 已知边界：混合多张源试卷重练时，会话只能带一个 `paperId`，作答页图片回看不完整；
  错题列表仍按每题快照逐一展示

### 4.8 试卷导入分析诊断日志

- 试卷上传、文件解析、逐页视觉识别、bbox 与资源归属、结构切题、答案键生成、Redis Stream
  生产/消费统一写专用 logger `paper.flow`；控制台 appender 为 `PAPER_FLOW_CONSOLE`
- 日志字段固定包含 `paperTraceId / paperStage / paperId / pageNo / attemptId`，异常原样打印完整
  cause chain；模型原始回包、OCR 文本、结构 JSON、资源坐标和页状态不做 `ErrorLogSanitizer` 过滤
- 入口使用 `PaperFlowLog.open(...)` 建 MDC scope，模型回包用 `PaperFlowLog.raw(...)`，结构化对象用
  `PaperFlowLog.json(...)`，异常必须通过 `PaperFlowLog.error(message, error, args...)` 保留 Throwable
- 这些日志会包含试卷正文和模型原始输出，只用于本地诊断/受控环境排查；用户可见 API 错误仍由
  `BusinessException` 的文案决定，不把原始异常返回给前端。生产若需降噪，只调整 `paper.flow`
  logger 级别，不要重新接脱敏器，否则会失去定位失败页所需信息

### 4.9 会话创建与文件解析异步化（D/E）

- 创建练习会话时，请求线程只写「壳会话」与 `questionGenRequestJson` 请求快照，投递
  `interview:question-gen:stream` 后立即返回；题目由 `SessionQuestionGenerationService` 在
  `interview-question-gen` 的 Stream worker 池中生成，状态为
  `PENDING / PROCESSING / COMPLETED / FAILED`
- `/api/papers/upload` 请求线程只校验、读字节、哈希去重、上传原始件到 RustFS 的 `paper-input`
  前缀并写 `paper_input_files`；解析由 `paper:input:stream` 的 `PaperInputProcessingService`
  在 `paper-input` Stream worker 池中完成，状态为 `inputStatus`
- 所有 Stream 消费者统一采用「每条 Stream 1 条分发线程 → 有界在途队列 → N 个 worker」；
  worker 内完成条件领取、业务、终态和单条消息 ACK，继续使用 `attemptId` 心跳与恢复调度器
- 带 Redis 会话缓存的条件状态迁移统一收口到业务 Service：只有数据库条件更新命中才清理缓存，
  且在事务提交后执行；缓存清理失败只告警，不把已完成的状态迁移反向判成任务失败
- 外层并发与业务内部并发分开配置：`app.async.stream.consumers.<consumer-key>` 控制每个
  Stream 的 `worker-threads / queue-capacity / drain-timeout`，原有页级、题级执行器继续保留
- 前端 `InterviewPage` 轮询出题状态并支持失败后重新出题；`usePaperAnalysis` 增加 `input` 阶段，
  原始文件解析完成后再进入识别校对或切题进度，失败时可用现有重新解析入口重试

### 4.10 知识库图片识图与混合文档解析

- 详细方案见 [`docs/design/知识库图片识图与混合PDF解析-设计稿.md`](design/知识库图片识图与混合PDF解析-设计稿.md)
- 知识库上传支持 JPG / JPEG / PNG；图片经 `KnowledgeBaseImageOcrService` 转成文字后再进入原有切块和向量化。
  识图文本只参与本次向量化，不落库；点击“重新向量化”会重新识图
- PDF 按页判定：文字层可信页直接使用文字层，扫描或薄文字层页渲染后识图；
  因此纯文字、纯扫描、文字 + 扫描混合 PDF 都走同一条链路
- DOCX 按段落 / 表格顺序抽取正文，内嵌图片单独 OCR 后插回锚点段落；小于 64px 的装饰图标跳过，
  超过 `app.ai.rag.ocr.max-docx-images` 时整份失败并提示
- 单份资料识图页数上限为 `app.ai.rag.ocr.max-pages`（默认 10）；图片算 1 页，PDF 只累计 IMAGE 页。
  超限、图片为空、识图失败或视觉队列拒绝都会写回 `FAILED`，可手动重新向量化
- 复用 `LlmProviderRegistry.getDefaultVisionChatClient()`、`StructuredOutputInvoker`、
  `VisionRequestGuard`、`PageImageNormalizer` 与试卷解析器，不新建 Provider 或第二套解析框架
- 知识库向量化 worker 默认从 2 上调为 4；全局视觉并发默认从 2 上调为 4，试卷与知识库共用额度。
  单文件内部仍逐页 / 逐图串行，页数上限用于限制单任务时长

### 4.11 用户月度成本配额、模型分档与成本页（2026-11-07）

- 用户档位只有 `FREE` / `AUTHORIZED` 两种；管理员账号天然豁免。免费用户占月度总量池，
  授权用户与管理员不限额度、也不计入免费用户人数。
- 免费用户文本和识图固定走 `dashscope-3.7` / `dashscope-3.7-vl`（模型 `qwen3.7-flash`）；
  授权用户、管理员和无用户上下文的系统任务走系统默认 `dashscope` / `dashscope-vl`
  （默认模型 `qwen3.8-flash`）。用户级模型绑定也不能覆盖这条档位路由。
- 月度总量池默认 `¥100`，落库在 `ai_quota_config`，管理员可在「设置 → 调用成本 → 额度总池」
  修改。每个免费用户的额度按 `总量 ÷ 当前免费用户数` 实时计算，不预发、不落库；
  每月 1 日切换带 `yyyyMM` 的新 Redis 键，自然月自动重置。
- 用户端只显示月度累计百分比，不显示总额、已用金额或剩余余额。已有百分比不会因调整总量或
  免费用户数而回跳；下一笔模型调用结算时才按当时的人均额度继续累加，额度变大则增长变慢，
  额度变小则增长变快。
- 当月首次读取额度时，会从 `ai_call_events` 明细补齐本月历史成本后再写 Redis 基线；
  CNY 明细直接取账本金额，历史非 CNY 明细按 token 数用当前 CNY 价格重算。补基线只取
  `max(账本, Redis)` 并写 `seeded` 标记，后续只累加结算增量，不会重复计入同一笔成本。
- 额度记账复用“先预占、后按真实费用结算”：同步入口在调用前预占，异步任务在入队前预占、
  消费者结束后结算；没有实际模型调用时释放预占。Redis 计数使用人民币微元，价格表与成本页
  统一按 CNY 展示。同一操作号的预占是幂等的，避免结构切题并行分块重复占额度；
  “开始作答”内部触发自动重切时会生成独立异步操作号，同步请求结算不会把后台重切成本一起结掉。
- 多阶段异步链路由最终阶段结算：原始文件解析成功时保留同一操作号的预占，解析失败才释放；
  用户百分比最多保留两位小数，避免几角钱的真实调用被取整成 `0%`、看起来没有增长。
- 超额后上传、切题、模拟出题、问答助手、知识库上传、批改、语音评测等入口返回统一业务错误；
  普通浏览、历史查看和编辑非 AI 内容不受影响。用户侧边栏只展示百分比圆环，
  授权用户和管理员显示“不限额度”。
- 管理端用户配额列表保留 RPM / TPM / 并发限流，并支持分页、搜索、单个/批量编辑和恢复默认；
  用户档位在「额度总池」中切换，改完后当前调用立即按新档位路由。
- 实时语音 WebSocket 仍是独立链路：LLM 没有写入用户调用上下文，ASR/TTS 也没有接入月度额度，
  开启前需要补齐路由、预占与结算，已登记到 `docs/待优化事项.md`；默认配置关闭语音面试。

### 4.12 批改失败收敛与提交幂等（2026-11-05）

- `common/ai/RetryableFailureClassifier` 按 `ErrorCode` 与异常 cause 判断是否值得重试；
  限流、AI 超时、连接中断和视觉并发拒绝走 Stream 重试，只有确定性业务失败才直接 `FAILED`
- 批改任务使用 `evaluateAttemptId + evaluateHeartbeatAt` 做领取、心跳与卡死恢复；
  `PROCESSING` 超过阈值且心跳过期时由 `EvaluateRecoveryScheduler` 重置为 `PENDING` 并补投，
  补投消息会恢复 `ownerId / AiFeature.ANSWER_EVALUATE`，限流归因不丢失
- 文本模型漏评时不再补 0 分；`UnifiedEvaluationService` 只返回已评估题，
  `ReportAssembler` 把缺失题标为 `MANUAL_REVIEW`
- 交卷入队改为条件更新：只有 `evaluateStatus` 为 `PENDING / FAILED` 才置 `PENDING` 并投递；
  `PROCESSING / COMPLETED` 不重复入队，已 `COMPLETED / EVALUATED` 的会话拒绝重复提交，
  避免覆盖已批改答案

## 五、依赖与构建上的两个硬约束

1. **Spring AI 必须 ≥ 2.0.1**：2.0.0 的 `OpenAiChatModel$ChunkMerger` 用「分片是否带 id」判断工具调用是否为新调用，
   DashScope / DeepSeek 这类「续传分片不带 id」的厂商会抛 `NoSuchElementException`；2.0.1 改为按 tool call `index` 合并。
2. **编译必须带 `-parameters`**（已写在 `app/build.gradle`）：Spring AI 的 `@Tool` / `@ToolParam` 依赖参数名生成工具 schema，
   关掉后模型看到的入参会退化成 `arg0`。

两个必踩的坑（README 也有记录，这里再强调）：

- 本机开着 HTTP 代理（v2rayN 等）时，JVM 会把 `localhost:9000` 的 S3 请求也发给代理，导致启动报
  「检查存储桶失败: Service Unavailable (503)」。给后端进程加 `NO_PROXY=localhost,127.0.0.1` 即可。
- 仓库路径含中文或空格时，Gradle **测试进程**会因类路径编码问题抛 `ClassNotFoundException`（编译不受影响）。
  跑测试前把仓库复制到纯 ASCII 路径（例如 `C:\work\smart_quiz_platform`）再执行。

`vector_store`、`oral_practice_*`、`study_plans`、`llm_provider_config` 等。

迁移注意：

1. **不兼容老数据**：`paper_json` 只认树结构；开发库可以直接重建（`DROP DATABASE` + `FLUSHDB`）。
2. **改过 `V1__init_schema.sql` 会触发 Flyway 校验和失败**。开发库的常规做法：手工把结构改到位（或用新 V1 重建），
   再把 `flyway_schema_history.checksum` 更新为启动日志里的 `Resolved locally` 值（等价于 `flyway repair`）。
3. **不要在应用运行时 `FLUSHDB`**：Redis Stream 的消费组会被一起删掉，消费者会刷 `NOGROUP`。

## 九、工程约定（摘自 `AGENTS.md`，务必遵守）

- 分层 `Controller → Service → Repository`；`@Transactional` 只放 Service 且范围最小
- 业务异常统一 `BusinessException(ErrorCode.XXX, "描述")`；对外响应统一 `Result<T>`，禁止返回 Entity
- 请求体用不可变 `record`；Entity→DTO 优先 MapStruct；构造器注入 + `@RequiredArgsConstructor`
- **LLM / S3 / 外部 HTTP 不得放在数据库事务内**
- 取模型统一 `LlmProviderRegistry.getChatClientOrDefault(provider)`；结构化输出统一 `StructuredOutputInvoker`
- Prompt 模板放 `app/src/main/resources/prompts/*.st`（StringTemplate）
- 限流用可重复 `@RateLimit`；线程池不要用 `Executors.newXxxThreadPool()`
- 代码 2 空格缩进、无通配符导入、日志用 SLF4J 占位符且异常放最后一个参数

## 十、已知坑清单（都踩过，别再踩）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 测试抛 `ClassNotFoundException`，但编译正常 | 仓库路径含中文/空格 | 复制到 ASCII 路径再跑测试 |
| 启动报 503「检查存储桶失败」 | JVM 把 localhost 请求走了代理 | 加 `NO_PROXY=localhost,127.0.0.1` |
| 启动失败：Flyway 校验和不匹配 | 改过 `V1__init_schema.sql` | 修 `flyway_schema_history.checksum`（见 8.2） |
| Redis 刷 `NOGROUP` | 应用运行时执行了 `FLUSHDB` | 重启应用重建消费组 |
| 前端 `listen EACCES 0.0.0.0:5173` | Windows/Hyper-V 把 5141–5240 保留成系统端口段，绑定直接拒绝 | 默认端口已改为 3000；用 `netsh interface ipv4 show excludedportrange protocol=tcp` 查看本机保留段 |
| IDEA 启动报 `Unable to start embedded Tomcat` | 多半是 `APP_AUTH_JWT_SECRET` 没注入（IDEA 不读 `.env`），其次才是 8080 被占 | Run Configuration 里补 `APP_AUTH_JWT_SECRET` / `APP_AUTH_COOKIE_SECURE=false` / `NO_PROXY`，或用 EnvFile 插件指向 `.env`；完整 `Caused by` 若为 `Port 8080 was already in use` 则先释放端口 |
| IDEA 启动报 `Unable to start embedded Tomcat`，完整根因是 Redis `Connection refused` | Windows 可能把 `6379` 放进系统保留端口段，导致 Redis 容器无法映射宿主端口 | `docker-compose.dev.yml` 的 Redis 宿主端口已参数化为 `${REDIS_PORT:-6379}`；本机 `.env` 使用 `REDIS_PORT=16379`，启动 compose Redis 后后端会连接 `localhost:16379` |
| RustFS 报 `Permission denied (os error 13)` | 镜像默认以 `uid=10001(rustfs)` 运行，而 Windows bind mount 在容器内表现为 `root:root 755` | Windows 本地开发如果必须把数据落到宿主机目录，使用固定版本 `rustfs/rustfs:1.0.0-rc.6` 并加 `--user 0:0`；生产 Linux 环境下应把宿主目录 `chown` 给 `10001:10001`，不要长期使用 root |
| RustFS 日志出现 `Unsupported filesystem type: V9FS` | Docker Desktop 会把 Windows 目录通过 V9FS 提供给 Linux 容器；rc.6 对此只告警，当前可正常读写 | 本机保留 Windows 目录 bind 时属于开发环境折中，必须定期备份；更稳妥的运行方式是 Docker 命名卷。主机访问 9000/9001 时还要设置 `NO_PROXY=localhost,127.0.0.1`，否则代理可能把请求转走并表现成 503 |
| 识别停在第 N 页、状态一直 PROCESSING | 视觉请求卡在 HTTP/2 等响应头，且历史上没有 callTimeout | 已加 `app.ai.vision-request-timeout`（默认 3m）；重启后卡住页会失败并继续后面的页，可在预览页单独重试 |
| 视觉识别每次精确 60 秒被取消，后续页面快速触发熔断 | Spring AI `OpenAiChatOptions` 自带 60 秒默认值，并会在每次请求时覆盖底层 Client 超时；只改 Client 超时无效 | 已在构建 `OpenAiChatOptions` 时同步 `app.ai.vision-request-timeout`；固定样本完整识别约 109 秒，默认 3m 为模型抖动留出余量 |
| 工具入参变成 `arg0` | 编译没开 `-parameters` | 已在 `app/build.gradle` 固定 |
| AI 调用每次精确 60 秒后 `OpenAIIoException` | Spring AI `OpenAiChatOptions` 的 60 秒默认值覆盖了本地 Client 配置 | 已显式同步 `app.ai.chat-request-timeout` / `app.ai.vision-request-timeout`；thinking 仍按单题、限额使用 |
| 页面只显示阅读文章标题、没有正文 | 根级 MATERIAL 被当成 SECTION 渲染，只遍历子节点 | 已统一走 `NodeBlock → MaterialBlock`；根级和嵌套材料必须共用此入口 |
| 数据库模型与 `.env` 不一致 | `llm_provider_config` 的运行值覆盖配置文件 | 以启动 WARN 和数据库为准，修改后调用 `/api/llm-provider/reload` |
| 电脑睡眠唤醒后批量报 Redisson `Check CPU usage of the JVM` / Hikari `connection has been closed` | Windows 睡眠打断 PostgreSQL、Redis 的 TCP 连接；Redisson 提示文案只是通用兜底，不代表 JVM 真有 CPU 或内存故障 | 先确认 Docker、PostgreSQL、Redis 已恢复；连接池未自动恢复时重启应用或基础设施。IDEA 同时短暂冻结时，以 `threadDump` 中 GC 和阻塞栈为准，不要只凭提示调整 JVM |
| `pnpm run build` 报 `EPERM ... dist/assets` | Windows 下旧 `dist` 被开发服务器、资源管理器或杀毒软件占用 | 关闭占用后重试；临时验证可用 `pnpm exec vite build --outDir <tmp-dir>` |
| 仓库根目录出现几百 MB 的 `java_pid*.hprof` | JVM 被强杀时生成堆转储 | 已在 `.gitignore` 忽略，可手动删除释放空间 |
| `git add` 报 `index.lock` 已存在 | git 进程异常退出留下 0 字节锁 | 确认无 git 进程后删 `.git/index.lock` |
