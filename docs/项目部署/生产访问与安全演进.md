## 二、为什么数据库不能直接开放到公网

### 现状拓扑

```
DBeaver（本机 Windows）
    │  必须经过 SSH 隧道
    ▼
ssh -L 15432:127.0.0.1:5432 hk
    │
    ▼
8.210.200.94（阿里云香港）
    │
    ▼
127.0.0.1:5432  ← docker-proxy，只有宿主机自身可达
    │
    ▼
[smart-quiz-postgres]  ← 容器内网，公网完全不可达
```

### `-L` 参数的语义（容易理解错的地方）

```bash
ssh -L 15432:127.0.0.1:5432 hk
       ↑     ↑          ↑
     本机端口  目标地址    目标端口
```

含义是：**在本机开 15432；连上它的流量经过 SSH 通道送到服务器，再由服务器去连 `127.0.0.1:5432`。**

关键点：中间那个 `127.0.0.1` 是**以服务器为视角**解析的，不是本机地址。所以哪怕数据库对外完全不可达，只要服务器自己能连上它，隧道就能把你送进去。

### 开放公网的代价

| 风险 | 说明 |
| --- | --- |
| 被扫被爆 | 公网 PostgreSQL 端口上线数分钟内即被扫描器发现，随后是持续暴力破解 |
| 明文过网 | 容器内 PostgreSQL 未配置 SSL，密码明文传输 |
| 数据全裸 | 密码一旦失守，试卷、资料、账号、向量数据全部泄露 |
| 漏洞面扩大 | 数据库版本本身的漏洞直接暴露给全世界 |

> 反例：仓库里的 `docker-compose.dev.yml` 把 5432 / 6379 / 9000 映射到 `0.0.0.0`，
> 那是**本地开发**用的。切勿把它部署到公网机器上。

## 三、企业级通常怎么做

核心思路：**数据库永远不在公网；人也永远不直连生产库；所有访问必经过一个可认证、可授权、可审计的入口。**

### 3.1 网络分层

```
Internet
   │
[公网子网]  ALB / SLB / 堡垒机          ← 唯一暴露面
   │
[私有子网]  应用服务器（无公网 IP）
   │
[私有子网]  数据库（无公网 IP，仅接受应用安全组访问）
```

数据库与应用**不同机**，目的是爆炸半径隔离、能力复用（主从/备份/读写分离）、责任边界清晰。

### 3.2 访问入口

| 层级 | 做法 | 代表组件 |
| --- | --- | --- |
| 最小 | SSH 端口转发（**本项目当前方案**） | `ssh -L` |
| 小团队 | 专用跳板机，内网机器只接受它的连接 | 一台最小 ECS 作 Bastion |
| 中型 | 堡垒机 / PAM：账号托管、会话录制、命令审计、临时授权 | JumpServer、Teleport、HashiCorp Boundary |
| 大型 | PAM + 零信任：申请-审批-限时生效 | CyberArk、BeyondTrust、阿里云 SASE |

堡垒机比 SSH 隧道多出的能力：

- **账号托管**：工程师不知道生产密码，堡垒机代填
- **会话录制**：谁、何时、执行了什么 SQL，可回放（等保 / SOC2 硬要求）
- **临时授权**：申请 → 审批 → 2 小时自动失效
- **命令拦截**：`DROP TABLE`、无 `WHERE` 的 `DELETE` 直接拦下

### 3.3 凭据管理

| 层级 | 做法 |
| --- | --- |
| 当前 | `env.prod` 明文，600 权限 |
| 进阶 | 凭据入 Secrets Manager（阿里云凭据管家 / AWS Secrets Manager / Vault），应用启动时拉取 |
| 企业级 | 动态凭据：Vault 发放短时效临时账号，按时轮换 |

### 3.4 数据访问治理

- 查询走**只读从库**，主库只服务应用写入
- 写操作走**工单审批**：申请 → DBA 审核 → 自动执行 → 留痕（Archery / Yearning / Bytebase）
- 报表走 Metabase / Superset，不直接看原始表
- 敏感字段出库**脱敏**，测试环境只用脱敏数据

### 3.5 审计与合规

- 数据库开启 DDL（或全量）日志，接入 SIEM
- 所有生产访问有会话记录
- 变更管理：变更单、审批、窗口期、回滚预案
- 定期权限复核

## 四、对照表：当前 vs 企业级

| 当前 | 企业级等价物 |
| --- | --- |
| `ssh -L` 手动隧道 | 堡垒机 / Teleport / PAM（含审计与临时授权） |
| Docker 内网 + 只绑回环 | 私有子网 + 安全组白名单 |
| 数据库与应用同机 | 托管 RDS + 主从 + 自动备份 + PITR |
| `env.prod` 明文密码 | Secrets Manager / Vault 动态凭据 |
| `docker exec psql` 查数据 | 只读从库 + SQL 工单平台 |
| 手工 `pg_dump` | 自动备份 + 定期恢复演练 |
| 单机 Docker Compose | K8s / ACK + CI/CD + 灰度发布 |
| 靠自觉不改生产 | 变更管理 + 权限复核 + 全会话审计 |

## 五、可实施的改进项（按性价比排序）

> 每项都可独立实施，互不阻塞。建议顺序：1 → 2 → 3 → 4 → 5 → 6。
>
> **实施前必读**：本仓库的 `deploy/`、`docker-compose.prod.yml` 与服务器上
> `/opt/smart-quiz/` 下的对应文件是**两份拷贝**。任何编排/配置改动都要
> ①改仓库 → ②传到服务器（`scp`）→ ③在服务器上执行 `up -d` 才算生效。
> 只改仓库不改服务器，线上不会有任何变化。

### 改进项 1：让 `ssh hk` 自动带上隧道（成本最低）

**目标**：不用再记两条命令，登录服务器时自动把数据库和 RustFS 控制台转发到本机。

**步骤**：修改本机 `C:\Users\<用户名>\.ssh\config`，在 `Host hk` 段里加两行：

```
Host hk
  HostName 8.210.200.94
  User admin
  IdentityFile ~/.ssh/id_ed25519
  IdentitiesOnly yes
  StrictHostKeyChecking accept-new
  ProxyCommand node C:\Users\<用户名>\.ssh\socks-bridge.js %h %p
  LocalForward 15432 127.0.0.1:5432
  LocalForward 9001 127.0.0.1:9001
```

**验收**：`ssh hk` 登录期间，另开一个窗口执行
`Test-NetConnection 127.0.0.1 -Port 15432` 应为 `True`；退出 SSH 后应变为 `False`。

**限制**：隧道只在该 SSH 会话存活期间有效。

### 改进项 2：用 Tailscale 组网替代手工隧道（体验最好）

**目标**：服务器与本机加入同一个虚拟内网，数据库像局域网一样直连，不需要任何隧道命令。

**为什么选 Tailscale**：基于 WireGuard，零配置、免费额度够用、NAT 穿透好，
是本项目规模下最接近"企业零信任"的方案。

**步骤**：

1. 服务器上安装并加入网络：
   ```bash
   curl -fsSL https://tailscale.com/install.sh | sh
   sudo tailscale up --ssh
   ```
2. 本机安装 Tailscale 客户端，用**同一个账号**登录。
3. 在服务器上取它的 tailnet IP：
   ```bash
   tailscale ip -4        # 形如 100.x.y.z
   ```
4. 修改 `deploy/docker-compose.server.yml`，让 postgres 同时监听 tailnet 地址
   （保留 `127.0.0.1` 以便服务器本地排查）：
   ```yaml
   postgres:
     ports:
       - "127.0.0.1:5432:5432"
       - "100.x.y.z:5432:5432"      # 换成上一步查到的 tailnet IP
   ```
5. 应用变更：
   ```bash
   ssh hk "cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.server.yml --env-file deploy/env.prod up -d postgres"
   ```
6. DBeaver 连接改为 `100.x.y.z:5432`（其余参数不变）。

**验收**：

- 本机 `ping 100.x.y.z` 通
- DBeaver 用 `100.x.y.z:5432` 能连上
- **关闭 Tailscale 后连不上**（证明没有意外暴露）
- 公网侧 `8.210.200.94:5432` 仍然不可达

**注意**：

- **阿里云防火墙不要放行 5432**，Tailscale 流量走的是它自己的接口。
- 不要执行 `tailscale up --advertise-exit-node`（那是把服务器当出口网关，用途完全不同）。
- Tailscale 控制台的 ACL 建议限制为"仅自己的设备"。
- 回滚：删掉 compose 里那行 tailnet 端口映射，执行第 5 步即可。

### 改进项 3：给 GUI 客户端单独建只读数据库账号

**目标**：用 DBeaver 查数据时用只读账号，杜绝误执行 `UPDATE` / `DELETE` / `DROP`。

**为什么**：应用连接的是 `postgres` 超级用户，用它连 GUI 等于"用管理员账号随手翻生产库"。

**步骤**：在服务器上执行

```bash
ssh hk
docker exec -it smart-quiz-postgres psql -U postgres -d smart-quiz
```

在 psql 里执行（把密码换成新生成的随机串）：

```sql
-- 1. 建只读角色
CREATE ROLE quiz_ro WITH LOGIN PASSWORD '在此填入一个随机强密码';

-- 2. 允许连接与访问 schema
GRANT CONNECT ON DATABASE "smart-quiz" TO quiz_ro;
GRANT USAGE ON SCHEMA public TO quiz_ro;

-- 3. 现有对象的只读权限
GRANT SELECT ON ALL TABLES IN SCHEMA public TO quiz_ro;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO quiz_ro;

-- 4. 将来新建的表自动授权（Flyway 以 postgres 身份建表，所以对 postgres 设默认权限）
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  GRANT SELECT ON TABLES TO quiz_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  GRANT SELECT ON SEQUENCES TO quiz_ro;
```

**验收**：

1. 用 `quiz_ro` 连上后 `select count(*) from users;` 正常返回
2. 用 `quiz_ro` 执行 `update users set display_name='x' where id=1;` 必须报
   `ERROR: permission denied for table users`
3. 应用本身不受影响（应用仍用 `postgres` 账号）

**注意**：

- 默认权限只对**今后**由 `postgres` 创建的对象生效；如果以后换迁移账号需要重设。
- 数据库名带连字符，SQL 里必须写 `"smart-quiz"`（带双引号）。
- 也可为本机 Tailscale 场景单独建一个"可写"角色用于紧急修复，但**默认不给**。

### 改进项 4：开启数据库审计日志

**目标**：记录所有 DDL（建表/改表/删表），出问题时能追溯"谁在什么时候改了什么"。

**步骤**：修改 `deploy/docker-compose.server.yml` 里 postgres 的 `command`，追加：

```yaml
      - -c
      - log_statement=ddl
      - -c
      - log_line_prefix=%m [%p] %q%u@%d
```

然后：

```bash
ssh hk "cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.server.yml --env-file deploy/env.prod up -d postgres"
```

**验收**：执行一次 `CREATE TABLE t_test(id int); DROP TABLE t_test;`，
`docker logs smart-quiz-postgres | tail -20` 里能看到对应语句。

**注意**：

- `log_statement=ddl` 只记录结构变更；若需记录全部语句改成 `all`，但日志量会明显增大。
- 日志已通过 Docker 的 `max-size=30m / max-file=3` 限制大小，不会吃满磁盘。

### 改进项 5：自动备份 + 真的演练一次恢复

**目标**：每天自动备份数据库与对象存储，保留 14 天；并且**至少成功恢复一次**。

**为什么**：备份的价值不在"有备份"，而在"恢复得了"。没演练过的备份等于没有备份。

**步骤**：

1. 在服务器上创建 `/opt/smart-quiz/scripts/backup.sh`：
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   cd /opt/smart-quiz
   STAMP=$(date +%F)
   mkdir -p backup/postgres backup/rustfs

   docker exec smart-quiz-postgres pg_dump -U postgres -Fc -d smart-quiz \
     > "backup/postgres/smart-quiz-${STAMP}.dump"

   docker run --rm -v smart-quiz-prod_rustfs_data:/data:ro \
     -v /opt/smart-quiz/backup/rustfs:/backup alpine \
     tar czf "/backup/rustfs-${STAMP}.tar.gz" -C /data .

   find backup -type f -mtime +14 -delete
   ```
2. `chmod +x scripts/backup.sh`
3. 加入 crontab（服务器上执行 `crontab -e`）：
   ```
   0 3 * * * /opt/smart-quiz/scripts/backup.sh >> /var/log/smart-quiz-backup.log 2>&1
   ```
   > 注意已有的证书重载任务（`30 3 * * * docker exec smart-quiz-gateway nginx -s reload`）不要删掉。
4. 手工先跑一次：`bash scripts/backup.sh && ls -lh backup/postgres backup/rustfs`
5. **恢复演练**（在测试库里做，别动生产）：
   ```bash
   docker exec smart-quiz-postgres psql -U postgres -c 'CREATE DATABASE "smart-quiz-restore-test";'
   docker exec -i smart-quiz-postgres pg_restore -U postgres -d "smart-quiz-restore-test" \
     < backup/postgres/smart-quiz-$(date +%F).dump
   docker exec smart-quiz-postgres psql -U postgres -d "smart-quiz-restore-test" -c 'select count(*) from users;'
   docker exec smart-quiz-postgres psql -U postgres -c 'DROP DATABASE "smart-quiz-restore-test";'
   ```

**验收**：备份文件按时生成、能恢复到独立库、`select count(*) from users` 结果与生产一致。

### 改进项 6：凭据管理（进阶，可选）

**目标**：数据库密码不再长期明文躺在 `env.prod` 里。

**可选路线**：

| 路线 | 成本 | 说明 |
| --- | --- | --- |
| 阿里云 KMS 凭据管家 | 低 | 把密码托管进去，`env.prod` 只留引用；需改造启动流程 |
| HashiCorp Vault | 中 | 动态凭据，每次启动发临时账号；需部署 Vault |
| 至少做到 | 极低 | 定期（如每季度）轮换一次密码，并更新 `env.prod` |

**注意**：轮换数据库密码要**同时**更新 `deploy/env.prod` 里的 `POSTGRES_PASSWORD`
和数据库里的实际密码，然后 `up -d postgres app`。顺序错了应用会连不上。

## 六、明确不要做的事

| 反模式 | 为什么 |
| --- | --- |
| 把 5432 / 6379 开放到公网 | 数分钟内被扫描，随后是持续爆破 |
| 用 `postgres` 超级用户连 GUI 客户端 | 一次误操作就能删库，且无法追责 |
| 在服务器上装 Adminer/phpMyAdmin 之类 web 管理页且不鉴权 | 相当于给数据库开了个公网后门 |
| 把生产密码写进仓库、聊天记录、截图 | 一旦扩散无法回收 |
| 执行 `docker compose down -v` | `-v` 会连数据卷一起删除，等于清库 |
| 在服务器上跑 Gradle 构建 | 该机器内存不足，会 OOM 并可能影响其他容器 |
