# 登录鉴权与发布方案（Spring Security + JWT 双 Token + RBAC）

> 对应实现：`app/src/main/java/interview/guide/modules/auth/`、
> 迁移脚本 `app/src/main/resources/db/migration/V20261011__auth_rbac.sql`、
> 前端 `frontend/src/context/AuthContext.tsx`。部署部分见 `docs/项目部署/阿里云部署方案.md`。

## 一、方案选型说明

你给的三条参考路线指向三种做法，先说清楚为什么最后落在第一条：

| 参考路线 | 是否采用 | 原因 |
| --- | --- | --- |
| Spring Security + JWT + 双 Token + RBAC | 采用 | 与单体 Spring Boot 架构天然契合，不引入额外组件 |
| Sa-Token + Redis（自动续签 / 踢人下线） | 部分借鉴 | 已引入 Spring Security，再叠一套 Sa-Token 会形成两套认证体系；但"Redis 承载令牌状态 + 踢人下线"的思路完整保留 |
| Spring Cloud Gateway + GlobalFilter 统一认证网关 | 不采用（用单体的等价实现） | 本项目是单体应用，没必要为认证单独引入网关进程；它的"统一入口拦截 + 向下游传递用户上下文"由 `JwtAuthenticationFilter` + `SecurityContextHolder` 等价实现，真正的边缘网关是 nginx，只做 TLS 与转发 |

结论：Spring Security 7 + Nimbus JOSE 做无状态认证；Redis 承载"黑名单 + 用户令牌版本"，
支撑退出登录与踢人下线；PostgreSQL 存 RBAC 三张表 + `refresh_tokens` 白名单表，支撑双 Token 轮换。

## 二、认证模型

### 2.1 双 Token

| 维度 | Access Token | Refresh Token |
| --- | --- | --- |
| 形态 | JWT（HS256 签名） | 随机串 `tokenId.secret`（不透明令牌） |
| 有效期 | 2 小时（`APP_AUTH_ACCESS_TOKEN_TTL`） | 30 天（`APP_AUTH_REFRESH_TOKEN_TTL`） |
| 下发方式 | 响应体 `data.accessToken` | HttpOnly + SameSite=Lax Cookie |
| 前端存放 | 只在内存（页面刷新即丢） | 浏览器 Cookie，JS 读不到 |
| 服务端状态 | 无状态，靠 jti 黑名单 + 用户版本号撤销 | 白名单，库里只存 SHA-256(secret) |

续期流程：

```
页面加载 → POST /api/auth/refresh（浏览器自动带 Cookie）→ 新 Access Token + 轮换后的 Refresh Token
任意接口返回 401 / 12002 / 12003 / 12004
   → 前端 axios 拦截器单飞（single-flight）调用一次 refresh
   → 成功：自动带上新令牌重放原请求，业务代码无感知
   → 失败：清空会话，路由守卫跳转 /login
```

Refresh Token 每次续期都轮换：旧令牌立即撤销并记录 `replaced_by`。旧令牌被再次使用
（典型的令牌泄露特征）时，直接撤销该用户全部刷新令牌并强制下线。

### 2.2 RBAC

```
users ──< user_roles >── roles ──< role_permissions >── permissions
```

| 内置角色 | 权限范围 |
| --- | --- |
| ROLE_ADMIN | 全部 12 个权限点 |
| ROLE_USER | 除 user:manage、provider:manage 外的 10 个权限点 |

权限点（`PermissionCode`）：paper:read、paper:write、practice:use、kb:read、kb:write、
kb:manage、rag:chat、trace:read、voice:use、schedule:use、provider:manage、user:manage。

关于数据行级隔离：当前只做功能级权限，不做 `owner_id` 数据隔离——按你的说明
"少数人共用一套数据、都可以用"，所有人都应看到全部试卷与资料。将来若要按用户隔离数据，
需要给业务表加 `owner_id` 并改查询条件，工作量另算。

### 2.3 踢人下线

两层机制，缺一不可：

1. Access Token 撤销：`users.token_version` 自增。令牌带 `ver` 声明，校验时与当前版本比对，
   不一致即失效。版本号在 Redis 缓存 5 分钟，踢人时同步刷新缓存，因此是立即生效的。
2. Refresh Token 撤销：把该用户所有刷新令牌标记 `revoked_at`。

触发场景：管理员「踢下线」、禁用账号、改角色、重置密码、用户自己改密码。
退出登录只撤销当前这一个刷新令牌，并把当前 Access Token 的 jti 加入 Redis 黑名单
（TTL = 令牌剩余有效期，过期自动清理）。

### 2.4 接口清单

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | /api/auth/login | 匿名（按 IP 限流 10 次/分钟） | 登录 |
| POST | /api/auth/register | 匿名（按 IP 限流 5 次/小时） | 自助注册，只创建账号不发令牌 |
| POST | /api/auth/refresh | 匿名（凭 Cookie） | 续期 + 轮换 |
| POST | /api/auth/logout | 匿名（幂等） | 退出登录 |
| GET | /api/auth/me | 已登录 | 当前用户与权限 |
| POST | /api/auth/password | 已登录 | 修改本人密码 |
| GET/POST/PUT/DELETE | /api/admin/users | user:manage | 账号管理 |
| POST | /api/admin/users/{id}/password、/kick | user:manage | 重置密码 / 踢下线 |
| GET | /api/admin/roles | user:manage | 角色与权限点 |

除上述匿名路径外，所有接口默认要求登录（`anyRequest().authenticated()`）。

### 2.6 自助注册

登录页「登录」按钮下方有「注册」按钮，注册只填用户名和密码，成功后回到登录界面
并带出刚注册的用户名，继续登录即可（注册接口本身不下发令牌，避免绕过登录流程）。

- 新账号固定拿 `ROLE_USER`，不能通过请求体指定角色；
- 用户名与密码规则和管理员建号一致（用户名 3~64 位字母数字 `_ . -`，密码至少 8 位）；
- 用户名重复返回 `12007 用户名已存在`；
- 限流：每 IP 每小时 5 次、全局每小时 50 次（`@RateLimit`）。

**风险提示**：开放注册意味着任何人都能创建账号并使用 AI 能力，直接消耗你的百炼额度。
只给少数人用时，把 `APP_AUTH_REGISTRATION_ENABLED` 设为 `false` 即可关闭注册入口
（此时接口返回 `12013 当前未开放注册`），改为在「账号管理」里由管理员建号。

### 2.5 首次启动的管理员

启动时如果 `users` 表为空，会自动创建 `admin`：

- 配置了 `APP_AUTH_BOOTSTRAP_ADMIN_PASSWORD` 就用该密码；
- 未配置则随机生成并打印到启动日志（WARN 级，只打印一次）。

登录后请立刻改用左下角「修改密码」。生产建议直接配置密码，免得从日志里捞。

## 四、实现要点与踩过的坑

1. `JwtAuthenticationFilter` 必须是 Spring Bean，但又不能注册到 Servlet 过滤链。
   它是 `@Component`，Boot 会额外把它注册成全局 Filter；一旦在 Spring Security 链之前先跑一次，
   `OncePerRequestFilter` 的"已执行"标记会让安全链内的那次注册被跳过，而
   `SecurityContextHolderFilter` 会在链首清空上下文——表现为"带着合法令牌依然 401"。
   解决方式是在 `SecurityConfig` 里注册 `FilterRegistrationBean.setEnabled(false)`。
2. `iss` 声明必须是 URL 形态。Spring Security 的 `Jwt#getIssuer()` 会把 `iss` 强制转成 URL，
   写成普通服务名会抛 `Unable to convert claim 'iss' of type String to URL`。
   当前默认 issuer 为 `https://smart-quiz-platform`，且校验时改用原始 claim 字符串比对。
3. JWT 数字声明反序列化后是 `Long` 不是 `Integer`，`jwt.getClaim("ver")` 必须按 `Number` 接，
   否则 `ClassCastException`。
4. `@PreAuthorize` 抛出的 `AccessDeniedException` 会被 `GlobalExceptionHandler` 的
   `@ExceptionHandler(Exception.class)` 兜底吞掉（返回 HTTP 200）。必须在它之前单独处理并返回
   真实 403，否则前端无法区分"没权限"和"服务出错"。
5. CORS 只保留 `CorsConfigurationSource` Bean，由 Spring Security 的 `cors()` 统一应用，
   不再注册独立的 `CorsFilter`，避免两份 CORS 响应头导致浏览器拒绝。
6. WebSocket 握手无法携带请求头，令牌走 `?token=`，由 `WebSocketAuthInterceptor` 复用同一套校验。
7. 前端 Access Token 只在内存，刷新页面会重新走一次 `/api/auth/refresh`，这是设计行为。
8. **前端 SSE 必须自己带令牌**。`frontend/src/api/stream.ts` 是唯一不走 axios 的 HTTP 调用，
   拦截器对它无效，曾经表现为"登录后问答助手回一句『登录状态无效，请重新登录』"。
   现在 `fetchWithAuth()` 会附带 `Authorization`，并在 401 / 认证类业务码时静默续期后重放一次。
9. **流式（SSE / Flux）接口要额外处理异步派发**。问答助手这类接口返回 `Flux`，
   Spring MVC 按异步请求处理，流结束或抛异常时容器会再发起 ASYNC / ERROR 派发；
   Spring Security 的授权过滤器在这两个阶段会再执行一次，而无状态会话不保存
   SecurityContext，请求会突然变成"未认证"并抛 `AuthorizationDeniedException`；
   此时响应已提交，日志里就会出现
   `Unable to handle the Spring Security Exception because the response is already committed.`。
   解决办法：`JwtAuthenticationFilter` 覆写 `shouldNotFilterAsyncDispatch()` 与
   `shouldNotFilterErrorDispatch()` 返回 `false`，在异步与错误派发阶段重新解析一次令牌。
10. **AI 报错要看真实原因，别一律说"服务不可用"**。百炼免费额度用尽时返回
   `403: Free quota exhausted...`，原先被统一映射成"AI服务暂时不可用"，很容易误判成网络问题。
   现在 `common/ai/AiErrorMessages` 会把额度不足 / 密钥失效 / 频率超限 / 模型不存在 /
   网络不通分别翻译成人话，`GlobalExceptionHandler` 与知识库流式问答都走它。

## 五、发布与同步更新（CI/CD）

前提：仓库在 GitHub，服务器能访问外网。产物走阿里云容器镜像服务 ACR 个人版（免费）。

### 5.1 流水线结构

```
push 到 main
   │
   ├─ build-and-push：GitHub Actions 构建后端/前端镜像 → 推 ACR（tag = 提交短 SHA + latest）
   │
   └─ deploy：SSH 到服务器执行 deploy/deploy-remote.sh
                 同步 git → 记录旧镜像 → pull → up -d
                 → 健康检查（容器 healthy）→ 失败自动回滚到上一个镜像并报错
```

关键文件：

| 文件 | 作用 |
| --- | --- |
| `.github/workflows/deploy.yml` | GitHub Actions 发布流水线 |
| `deploy/deploy-remote.sh` | 服务器端发布脚本（含健康检查与自动回滚） |
| `docker-compose.prod.yml` | 生产编排，镜像由 `APP_IMAGE` / `FRONTEND_IMAGE` 指定 |

镜像 tag 用提交短 SHA 而不是 `latest` 唯一决定：回滚时只要把 tag 改回上一个版本即可，
`latest` 仅作为"最新一份"的便利标签。

### 5.2 需要在 GitHub 配置的 Secrets

仓库 Settings → Secrets and variables → Actions：

| Secret | 示例 | 说明 |
| --- | --- | --- |
| ACR_REGISTRY | registry.cn-hangzhou.aliyuncs.com | ACR 公网地址 |
| ACR_NAMESPACE | your-namespace | ACR 命名空间 |
| ACR_USERNAME | 阿里云账号名 | ACR 登录用户名 |
| ACR_PASSWORD | 固定密码 | ACR 登录密码（在 ACR 控制台设置） |
| SERVER_HOST | 1.2.3.4 | 新加坡服务器公网 IP |
| SERVER_USER | deploy | 部署用的 SSH 账号 |
| SERVER_SSH_KEY | 私钥内容 | 能登录服务器的私钥（对应公钥已加到 authorized_keys） |
| SERVER_APP_DIR | /opt/smart-quiz | 服务器上的项目目录 |

### 5.3 服务器一次性准备

```bash
# 1) 克隆仓库（部署目录，后续由流水线 git reset 到最新）
sudo mkdir -p /opt/smart-quiz && sudo chown deploy:deploy /opt/smart-quiz
su - deploy
git clone https://github.com/wansitong11/smart_quiz_platform.git /opt/smart-quiz
cd /opt/smart-quiz

# 2) 准备生产环境变量（不进 Git）
cp deploy/env.prod.example deploy/env.prod
chmod 600 deploy/env.prod
vim deploy/env.prod          # 至少填：DOMAIN、POSTGRES_PASSWORD、RUSTFS 三个密钥、
                             #        AI_BAILIAN_API_KEY、APP_AI_CONFIG_ENCRYPTION_KEY、
                             #        APP_AUTH_JWT_SECRET、CORS_ALLOWED_ORIGINS

# 3) 首次启动（首次用本机构建，或先手工跑一次流水线）
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod up -d --build

# 4) 首次管理员：日志里会打印随机密码（或提前在 env.prod 配好 BOOTSTRAP_ADMIN_PASSWORD）
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod logs app | grep -i "初始管理员"
```

之后每次合入 main，流水线自动完成构建与发布，无需手工登录服务器。

### 5.4 手工发布与回滚

```bash
cd /opt/smart-quiz

# 手工发布指定版本
APP_IMAGE=registry.cn-hangzhou.aliyuncs.com/ns/smart-quiz-app:abc1234 \
FRONTEND_IMAGE=registry.cn-hangzhou.aliyuncs.com/ns/smart-quiz-frontend:abc1234 \
bash deploy/deploy-remote.sh

# 回滚：把 deploy/env.prod 里的 APP_IMAGE / FRONTEND_IMAGE 改回上一个 tag 再执行
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod up -d
```

### 5.5 发布纪律

- 生产库结构只通过新增 `V<n>__xxx.sql` 迁移，不允许改历史迁移文件（改了会触发 Flyway 校验和失败）；
- 每次发布前 `deploy-remote.sh` 会先拉代码，所以服务器目录里的本地改动会被覆盖，
  请勿直接在服务器上改受 Git 跟踪的文件；
- 上线前先跑一次备份（见 `docs/项目部署/阿里云部署方案.md` 第 8 节）。
