# 运维速查（香港生产环境）

日常只需要记住三件事：`ssh hk` → `sq ps` / `sq logs -f app` / `sq restart app`。

## 0. 环境一览

| 项 | 值 |
| --- | --- |
| 服务器 | 阿里云轻量应用服务器（**香港**），2 核 / 1.87 GiB 内存（2026-10-15 关闭 kdump 后）/ 40 GB 系统盘 |
| Swap | 2 GB（`/swapfile`，`vm.swappiness=60`） |
| 公网 IP | `8.210.200.94` |
| 站点 | https://quiz.stonev2ray.top |
| DNS | Cloudflare，`quiz` A 记录 → 上述 IP，**DNS only（灰云）** |
| 部署目录 | `/opt/smart-quiz` |
| 初始管理员 | 用户名 `admin`；`deploy/env.prod` 的 `APP_AUTH_BOOTSTRAP_ADMIN_PASSWORD` **只在首次初始化（`users` 表为空）时生效**，之后改过就以库里的哈希为准（2026-10-15 实测：改 env 不会覆盖已有密码） |
| 旧服务器 | `47.84.95.219`（新加坡，只跑 Xray 代理，与本应用无关，未改动） |

> **国内直连该 IP 不通**（阿里云香港这个 IP 段的路由问题），所以本机 `~/.ssh/config` 的 `hk`
> 别名配了 ProxyCommand，走本机 v2ray 代理（`127.0.0.1:10808`）。
> 依赖脚本：仓库内 `tools/socks-bridge.js`，实际使用的是 `~/.ssh/socks-bridge.js`。
> 如果哪天直连恢复了，把 `~/.ssh/config` 里 `Host hk` 的 `ProxyCommand` 那行删掉即可。

> **自助注册默认开着**，并且有两道配额：同一来源 IP 24 小时内最多 **3** 个、全站每天最多 **5** 个成功注册
> （超限时接口返回 12014 与可读提示）。想调整就用 `APP_AUTH_REGISTER_MAX_PER_IP_PER_DAY` /
> `APP_AUTH_REGISTER_MAX_GLOBAL_PER_DAY`（设 0 表示不限制）；
> 只给少数人用时更省事的做法是把 `APP_AUTH_REGISTRATION_ENABLED=false`，注册入口交给管理员建号。

## 1. 架构与容器

```
Internet ──80/443──> [gateway] nginx（TLS 终止、跳转）
                        └─> [frontend] nginx（静态资源 + 反代 /api、/ws）
                              └─> [app] Spring Boot 8080（JWT + RBAC）
                                    ├── [postgres] pgvector
                                    ├── [redis]
                                    └── [rustfs]
                     [certbot] 证书续期
```

| 容器名 | 作用 | 内存上限 | 对外端口 |
| --- | --- | --- | --- |
| `smart-quiz-gateway` | 公网入口、TLS 终止 | 48m | **80 / 443** |
| `smart-quiz-frontend` | 前端静态资源 + 内网反代 | 48m | 无 |
| `smart-quiz-app` | 后端服务 | **832m**（`-Xmx448m` + Metaspace192m + Direct48m + ParallelGC） | 无 |
| `smart-quiz-postgres` | 数据库（含 pgvector） | 224m | `127.0.0.1:5432` |
| `smart-quiz-redis` | 缓存 + Redis Stream 队列 | 80m | `127.0.0.1:6379` |
| `smart-quiz-rustfs` | 对象存储（试卷 / 资料原件） | 176m | `127.0.0.1:9001`（控制台） |
| `smart-quiz-certbot` | Let's Encrypt 续期 | 32m | 无 |

后三个的端口只绑在 `127.0.0.1`，**公网访问不到**，只用于本机隧道调试。

上限之和 **1440 MB**（app 832 + postgres 224 + rustfs 176 + redis 80 + frontend 48 + gateway 48 + certbot 32），
刻意压在整机可用内存之下，让 OOM 发生在**容器自己的 cgroup 里**而不是宿主机内核。改这个文件前先看
[§3.2 内存配额与 OOM 事故收口](#32-内存配额与-oom-事故收口2026-10-15)。

健康基线（2026-10-15 重启后实测）：整机 `MemTotal` 1.87 GB、`available` 约 690 MB，
7 个容器合计约 800 MB（app 约 630 MB / 上限 832 MB，峰值 797 MB），swap 用了 45 MB 左右。
`available` 掉到 200 MB 以下、或 `docker stats` 里 app 逼近 832 MB，就该查 §3.2。

### 3.1 自动巡检与告警（2026-10-14 加的）

`deploy/health-check.sh` 由 cron 每 5 分钟跑一次，检查四项：宿主机内存压力（PSI）、各容器内存占上限、
**postgres 是否又重建了集群**、1 分钟 load。正常时静默退出；超阈值时写日志并（可选）推送机器人消息。

```bash
# 日志（正常情况下文件为空）
tail -f /opt/smart-quiz/logs/health-check.log

# 手动跑一次（正常应无输出）
/opt/smart-quiz/deploy/health-check.sh

# 想验证告警链路：把阈值压到 0 再跑
PSI_THRESHOLD=0 LOAD_THRESHOLD=0 MEM_THRESHOLD=0 LOG_FILE=/tmp/hc-test.log \
  /opt/smart-quiz/deploy/health-check.sh && cat /tmp/hc-test.log
```

推送机器人：在 `deploy/env.prod` 里设置 `ALERT_WEBHOOK_URL`（钉钉/飞书/企业微信的群机器人地址），
脚本会自己读这个文件，不用改 cron。阈值可用环境变量覆盖（`PSI_THRESHOLD` / `MEM_THRESHOLD` / `LOAD_THRESHOLD`）。

### 3.2 内存配额与 OOM 事故收口（2026-10-15）

**两次事故**：10-14 是 app 上限（700m）贴着 JVM 实际用量；10-15 12:10 内核直接 OOM 杀掉 app 的 java
（`anon-rss:613008kB`），随后内存回收进入死循环，整机僵死约 3 小时，靠强制重启恢复。
根因是**容器上限之和（1700 MB）超过了机器实际可用内存（1613 MB）**——2 GB 的机器被 kdump 预留
256 MB、固件再吃掉约 130 MB，于是各组容器都还没到自己的上限，宿主机先没内存了。

| 措施 | 落点 | 效果 |
| --- | --- | --- |
| 关闭 kdump | `systemctl disable --now kdump-tools`，并给 `/etc/default/grub` 加 `crashkernel=0` | 释放 256 MB，`MemTotal` 1.58 GB → 1.87 GB（`crashkernel` 需**重启**生效） |
| 上限之和压到 1440 MB | `deploy/docker-compose.server.yml` | 给宿主与页缓存留约 400 MB |
| `vm.swappiness=60` | `/etc/sysctl.d/99-smart-quiz.conf`（覆盖 `/etc/sysctl.conf` 里旧的 `=0`） | swap 真正参与换页 |
| `"userland-proxy": false` | `/etc/docker/daemon.json` | 注册接口能记到真实公网 IP，而不是 docker 网桥的 `172.19.0.1` |

```bash
# 四项是否都还生效（重启后逐条确认）
grep MemTotal /proc/meminfo                 # 约 1913952 kB
grep -o 'crashkernel=[^ ]*' /proc/cmdline   # crashkernel=0
cat /proc/sys/vm/swappiness                 # 60
systemctl is-active kdump-tools             # inactive
systemctl show -p ExecReload docker || true # daemon.json 改动需 restart docker 才生效

# 各容器本次开机的内存峰值 vs 上限（cgroup v2）
for c in app postgres rustfs; do
  CID=$(docker inspect -f '{{.Id}}' smart-quiz-$c)
  printf 'smart-quiz-%s peak=%sMB\n' "$c" \
    "$(( $(cat /sys/fs/cgroup/system.slice/docker-$CID.scope/memory.peak) / 1048576 ))"
done
```

> rustfs 的 `memory.peak` 会长期贴着上限，这是**页缓存被算进 cgroup**造成的，不是真占用
> （`memory.stat` 里 `anon` 只有 50 MB 上下，内核需要时会直接回收）。`docker stats` 会扣掉
> `inactive_file`，看它更接近真实压力。

**仍然要盯的**：app 的 JVM 上限之和 688 MB / 容器上限 832 MB，实测峰值 797 MB，余量只有 35 MB。
真撞上限时是**容器内被杀并自动重启**（宿主机不再陪葬），用
`docker inspect -f '{{.State.OOMKilled}}' smart-quiz-app` 和 `dmesg -T | grep -i oom` 可以确认。

## 5. 查看数据

> **为什么必须先开隧道**：数据库只绑在服务器的 `127.0.0.1` 上，公网完全不可达——这是有意的安全设计。
> 而 DBeaver 跑在你本机，两者不在同一网络里，所以必须先建一条 SSH 隧道，把本机的 15432
> "接"到服务器的数据库上（`-L` 里的目标地址是以**服务器视角**解析的）。
> 报 `Connection refused` 就是隧道没开，不是密码错。
>
> 原理、开放公网的风险、企业级做法对照，以及后续 6 项可实施的改进，见
> [生产访问与安全演进.md](./生产访问与安全演进.md)。
>
> ⚠️ 当前 GUI 客户端用的是 `postgres` 超级用户，**误执行 UPDATE/DELETE 没有兜底**。

## 6. 发版流程

**前提**：这台服务器只有 1.87 GB 内存（2026-10-15 关闭 kdump 后），**不要在服务器上构建**，必须在本地编译好再传。

```powershell
# ① 本地构建（在仓库根目录）
.\gradlew.bat :app:bootJar
cd frontend; pnpm run build; cd ..

# ② 传产物
scp app/build/libs/app-0.0.1-SNAPSHOT.jar hk:/opt/smart-quiz/app/build/libs/app.jar
scp -r frontend/dist hk:/opt/smart-quiz/frontend/

# ③ 服务器重建并重启（只会重建 app / frontend 两个镜像）
ssh hk "cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.server.yml --env-file deploy/env.prod up -d --build"
```

改了编排或配置（`docker-compose.prod.yml`、`deploy/docker-compose.server.yml`、`deploy/nginx/templates/*`）时，同样要先把对应文件传到服务器再执行第 ③ 步。

**只改前端时用这种方式**（别用第 ③ 步整包发布：`up --build` 会顺带尝试构建 app 镜像，
而 app 镜像在服务器上会因内存不足 / BuildKit 不稳而失败，2026-10-14 实测踩过）：

```powershell
scp -r frontend/dist hk:/opt/smart-quiz/frontend/
# ① 只构建前端镜像（上下文已收窄到 frontend/，约 6MB）
ssh hk "cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.server.yml --env-file deploy/env.prod build frontend"
# ② 只重启前端容器（不 build）
ssh hk "cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.server.yml --env-file deploy/env.prod up -d frontend"
```

服务器这台机器**导出镜像层很慢**（BuildKit 报 `exporting layers` 要 2~3 分钟，慢盘），
而且 BuildKit 偶发 `NotFound: forwarding Ping`（构建器被打断）——遇到失败就重试，
或改用下面这条**本机构建 + 传镜像**的路子（实测 66MB 镜像压缩后传 1 分钟，最稳）：

```powershell
docker build -t smart-quiz-frontend:local -f frontend/Dockerfile frontend/
docker save smart-quiz-frontend:local -o $env:TEMP\fe.tar
scp $env:TEMP\fe.tar hk:/tmp/fe.tar
ssh hk "docker load -i /tmp/fe.tar && rm -f /tmp/fe.tar && cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.server.yml --env-file deploy/env.prod up -d frontend"
```

后端同理（`docker build -t smart-quiz-app:local -f deploy/server/Dockerfile.app .`），
这也是 3.7 里记的"别在服务器上现传现建 235MB"的做法。

**回滚**：镜像 tag 是 `smart-quiz-app:local`，没有版本历史。要回滚就重新传上一版的 jar / dist 再执行第 ③ 步。

**数据库结构变更**：只允许新增 `V<n>__xxx.sql` 迁移脚本，不要改历史迁移文件（会触发 Flyway 校验和不匹配）。发布前先备份。

## 7. 备份与恢复

```bash
ssh hk
sudo mkdir -p /opt/smart-quiz/backup/postgres

# 数据库全量备份（自定义格式，带压缩）
docker exec smart-quiz-postgres pg_dump -U postgres -Fc -d smart-quiz \
  > /opt/smart-quiz/backup/postgres/smart-quiz-$(date +%F).dump

# 对象存储卷备份
docker run --rm -v smart-quiz-prod_rustfs_data:/data:ro -v /opt/smart-quiz/backup:/backup alpine \
  tar czf /backup/rustfs-$(date +%F).tar.gz -C /data .
```

恢复：

```bash
# 数据库（先备份现有数据！）
docker exec -i smart-quiz-postgres pg_restore -U postgres -d smart-quiz --clean --if-exists \
  < /opt/smart-quiz/backup/postgres/smart-quiz-2026-10-11.dump

# 对象存储（先停 app，避免读写冲突）
sq stop app
docker run --rm -v smart-quiz-prod_rustfs_data:/data -v /opt/smart-quiz/backup:/backup alpine \
  sh -c 'rm -rf /data/* && tar xzf /backup/rustfs-2026-10-11.tar.gz -C /data'
sq start app
```

## 8. HTTPS 证书

证书由 `smart-quiz-certbot` 容器管理，每 12 小时尝试续期；续期后由 crontab 每天 03:30 重载网关。

```bash
# 查看证书有效期
docker exec smart-quiz-gateway ls -l /etc/letsencrypt/live/quiz.stonev2ray.top/
echo | openssl s_client -connect 127.0.0.1:443 -servername quiz.stonev2ray.top 2>/dev/null | openssl x509 -noout -dates

# 手工强制续期（一般不需要）
# 注意 --entrypoint：certbot 服务的默认 entrypoint 是续期循环脚本，必须覆盖掉
sq run --rm --entrypoint certbot certbot renew --webroot -w /var/www/certbot --force-renewal
sq exec gateway nginx -s reload

# 查看续期定时任务
crontab -l
```

## 9. 故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 浏览器打不开站点 | 国内到该 IP 段路由不通 | 先确认不是本机网络问题：用手机 4G 试；仍不行就在 Cloudflare 把 `quiz` 记录改成 **Proxied（橙云）** |
| 页面能开但接口 502 | 后端没起来 | `sq ps` 看 app 状态；`sq logs --tail 100 app` |
| 登录报"用户名或密码错误" | 密码错，或账号被禁用 | 用 admin 登录后在「账号管理」里重置 |
| 管理员自己也忘了密码 | `AuthDataInitializer` 只在 `users` 表为空时写入初始密码，改 env 不生效 | 用任意 BCrypt 工具生成哈希（`python -c "import bcrypt;print(bcrypt.hashpw(b'新密码',bcrypt.gensalt(10)).decode())"` 或 `htpasswd -bnBC 10 "" '新密码' \| tr -d ':\n'`），再 `docker exec smart-quiz-postgres psql -U postgres -d smart-quiz -c "update users set password_hash='<哈希>', token_version=token_version+1 where username='admin';"`，登录后在页面上改回自己的密码 |
| 登录后立刻被踢回登录页 | Refresh Token Cookie 失效 | 确认访问的是 `https://`（http 下 Secure Cookie 会被丢弃） |
| 上传后一直"待向量化" | Redis Stream 消费异常 | `docker logs smart-quiz-app \| grep -i vectorize`；重启 app |
| 某个容器反复重启 | 触到 `mem_limit` 被 OOM 杀死 | `docker inspect smart-quiz-app \| grep -i oom`；把 `deploy/docker-compose.server.yml` 里对应的 `mem_limit` 调大 |
| 站点变慢 | 内存吃紧开始换页 | `free -h` 看 swap used；`vmstat 1 10` 看 si/so 是否持续非零 |
| 磁盘快满 | 日志/镜像/备份堆积 | `docker system df`；`docker image prune`；清理旧备份 |

排查内存相关的死机：

```bash
dmesg -T | grep -i -E 'oom|killed'      # 有没有进程被 OOM Killer 杀掉
vmstat 1 10                              # si/so 持续非零 = 内存不够
```
