# 阿里云轻量应用服务器部署方案（智能刷题平台）

> 目标：把当前项目真正部署上线，用独立域名访问，让 PostgreSQL / Redis / RustFS
> 从"只有本地能跑"变成"服务器上常驻、可持久化、可备份"的生产形态。
>
> 本文基于仓库当前代码（提交 `de08f7d` + 未提交改动）实际核查后编写，
> 涉及行号与文件路径均可直接定位验证。

---

## 0. 结论摘要

**推荐形态**：一台阿里云轻量应用服务器 + 一个域名 + Docker Compose 跑全栈。

```
                       Internet
                           │
                    DNS: stonev2ray.top → A 记录 → 公网 IP
                           │
        ┌──────────────────▼──────────────────────────────────┐
        │  阿里云轻量应用服务器（Ubuntu 24.04 + Docker）        │
        │                                                      │
        │   [gateway: nginx]  ← 唯一映射 80/443 到公网          │
        │        │  TLS 终止 + 证书自动续期                     │
        │        ▼                                             │
        │   [frontend: nginx]  静态资源 + 内部反代 /api /ws     │
        │        │                                             │
        │        ▼                                             │
        │   [app: Spring Boot 8080]                            │
        │        │                                             │
        │        ├──► [postgres: pgvector/pg16]   ┐            │
        │        ├──► [redis: 7, AOF]             ├ 仅容器内网  │
        │        └──► [rustfs: S3 兼容]            ┘ 不开放端口  │
        │                                                      │
        └──────────────────────────────────────────────────────┘
                           │
                   出站调用阿里云百炼 DashScope（LLM / ASR / TTS）
```

**关键判断**：Redis / RustFS / PostgreSQL **不是"只在本地能跑"**，而是应该在服务器上以
容器常驻、用 Docker 数据卷持久化、只在内网互通、**不向公网暴露端口**。这才是正确做法。
把 5432 / 6379 / 9000 直接开到公网，才是真正会出事的选择（见第 5.2 节）。

**上线前有 3 个阻断项必须处理**（第 1 节）。其中"登录鉴权"已经落地实现，
详见 `docs/项目部署/登录鉴权与发布方案.md`；备案与 AI 额度两条仍然成立。

## 1. 上线前的三个阻断项

### 1.1 登录鉴权（已实现）

> 状态：已完成。实现说明见 `docs/项目部署/登录鉴权与发布方案.md`。
> 原先项目**完全没有鉴权**（无 Spring Security、无用户表、无 owner 字段），
> 域名一挂出去任何人都能上传删除资料、烧 API 额度。现在已经补上
> Spring Security + JWT 双 Token + RBAC 用户体系。

下面保留当初的风险分析，作为"为什么必须做这件事"的记录。

**核查结论**：全仓库搜索 `SecurityFilterChain` / `@EnableWebSecurity` / `JWT` / `login`
均无业务实现，`app/build.gradle` 也没有引入 `spring-boot-starter-security`；
所有业务表（`practice_papers`、`knowledge_bases`、`rag_chat_sessions` …）都没有
`owner_id` / `user_id` 之类的归属字段。

**后果**：域名一旦解析到公网，任何拿到网址的人都能

- 上传/删除资料和试卷，看到别人上传的全部内容；
- 无限次调用大模型（`AI_BAILIAN_API_KEY` 是你的计费凭证）；
- 通过 `/api/llm-provider` 相关接口读写模型配置。

**三个可选方案，按实施成本排序**：

| 方案 | 做法 | 工作量 | 适用 |
| --- | --- | --- | --- |
| A. 网关 Basic Auth | 在 `deploy/nginx/templates/smart-quiz.conf.template` 的 `location /` 与 `location /api/` 加 `auth_basic`，用 `htpasswd` 生成账号 | 半天 | 自己 / 家里几个人用 |
| B. 网关白名单 | 同一处加 `allow <IP>; deny all;`，或加一个固定邀请路径 | 半天～1 天 | 固定几个人、IP 相对稳定 |
| C. 正式用户体系 | 新增 `spring-boot-starter-security` + JWT + `users` 表，给核心业务表加 `owner_id` 并改查询条件 | 1～2 周 | 真正对外运营、多用户隔离 |

**当前状态**：已按方案 C 落地（Spring Security + JWT + RBAC + 账号管理页），
所有业务接口默认要求登录，管理员可创建/禁用/踢下线账号。上线时只需在
`deploy/env.prod` 里配好 `APP_AUTH_JWT_SECRET` 与初始管理员密码。

### 1.2 域名备案（决定服务器地域）

| 服务器地域 | 是否要 ICP 备案 | 说明 |
| --- | --- | --- |
| 中国大陆（杭州/北京/深圳…） | **必须** | 未备案域名解析到大陆节点，80/443 会被拦截；阿里云要求备案用的实例有效期 ≥ 3 个月 |
| 中国香港 / 新加坡 | 不需要 | 可立即上线；国内访问延迟略高，个别网络运营商可能有波动。**你的服务器在新加坡，走这条** |

另外：域名必须先在阿里云完成**实名认证**（.cn 类域名认证通过前无法解析）。
备案通过后 30 日内还需完成**公安联网备案**。

> 你的服务器在新加坡，免备案，可以直接解析域名上线。
> 如果以后面向国内中学生正式运营，再迁移到大陆节点 + 备案
> （迁移只需换 Docker 主机，镜像和数据卷搬过去即可）。
> 唯一注意：**HTTPS 需要域名**，Let's Encrypt 不能给纯 IP 签证书。
> 尚未购买域名时，可以先用 `http://<公网IP>` + `APP_AUTH_COOKIE_SECURE=false`
> 验证登录与基本功能，但口语练习（浏览器要求安全上下文）要等域名 + HTTPS 就绪。

### 1.3 AI 额度会被消耗

- 项目已有 `@RateLimit`（按 IP / 会话维度），但**没有总量预算控制**；
- 单次"上传试卷切题"或"整卷批改"可能触发多次模型调用；
- 语音练习会额外消耗 ASR + TTS 额度。

**必做**：在百炼控制台配置**用量告警**和**额度上限**；给 Key 设置可用的模型白名单；
定期在控制台核对账单。如果你后续做公开运营，建议为每个用户加日配额。

## 2. 方案选型：自建全家桶 vs 云托管

### 方案 A（推荐起步）：一台轻量服务器跑全部依赖

优点：成本最低、部署最简单、无跨网络延迟、本项目开箱即用。
缺点：单点故障；备份、升级、监控要自己做。

### 方案 B（成熟期演进）：中间件托管

| 组件 | 自建（方案 A） | 云托管（方案 B） |
| --- | --- | --- |
| PostgreSQL | `pgvector/pgvector:pg16` 容器 + 数据卷 | 云数据库 RDS PostgreSQL，**需确认内核版本支持 `vector` 扩展，并把 `vector` 加入 `rds.allowed_extensions`** |
| Redis | `redis:7` 容器 + AOF | 云数据库 Redis / Tair |
| 对象存储 | RustFS 容器 + 数据卷 | 阿里云 OSS |
| 迁移成本 | — | 改 `.env` 的 host/endpoint 即可，代码无需改 |

**关于 OSS**：项目用的是 AWS SDK v2（`software.amazon.awssdk:s3`，见
`app/src/main/java/interview/guide/common/config/S3Config.java`），并强制
`forcePathStyle(true)`。OSS 提供了 S3 兼容接口，但签名版本、路径风格、region 取值
与标准 S3 有差异，**切换前必须先在测试环境跑通上传/下载/建桶**。
如果不想踩这个坑，自建 RustFS 反而是最稳的。

**结论**：先用方案 A 上线；当日活上来、或数据不可丢成为硬要求时，优先把 PostgreSQL
替换成 RDS（最痛的是数据库备份和恢复），Redis / 对象存储可以晚一步。

## 3. 服务器与域名准备

### 3.1 规格建议

| 项 | 最低 | 推荐 | 说明 |
| --- | --- | --- | --- |
| CPU/内存 | 2 核 4G | **4 核 8G** | 同时跑 JVM + PG + Redis + RustFS + nginx |
| 系统盘 | 60G SSD | 100G SSD | pgvector 向量表 + 上传文件会持续增长 |
| 带宽 | 3 Mbps | 5 Mbps | 上传 50MB 文件、SSE 流、WebSocket 都占带宽 |
| 系统 | Ubuntu 24.04 LTS | 同 | 与 Docker / 本文命令最贴合 |

**内存分配参考（4G 机器）**：JVM 2.2G（`MaxRAMPercentage=60` 已给系统留 40%）+
PostgreSQL 0.8G + Redis 0.77G（`REDIS_MAXMEMORY`）+ RustFS 0.5G + 系统/nginx 0.5G。
如果只有 2G 内存，请把 `JAVA_TOOL_OPTIONS` 调到 `-XX:MaxRAMPercentage=45`，
并把 `REDIS_MAXMEMORY` 调到 `256mb`，否则高峰期容易被 OOM Killer 杀掉进程。

> **重要**：在服务器上执行 `docker compose build` 编译后端（Gradle + Java 25）
> 需要额外 2～3G 内存和大量 CPU。2 核 4G 机器构建很容易卡死或 OOM。
> 内存 ≤ 4G 时，请用第 6.2 节的方式二（本地/CI 构建后推镜像）。

### 3.2 阿里云控制台操作

1. 购买**轻量应用服务器**（选地域与镜像 Ubuntu 24.04）；
2. 在**轻量服务器控制台 → 防火墙**中，只放行：

| 端口 | 协议 | 来源 | 用途 |
| --- | --- | --- | --- |
| 22 | TCP | 你的办公/家庭 IP（不要 `0.0.0.0/0`） | SSH |
| 80 | TCP | `0.0.0.0/0` | HTTPS 跳转 + 证书校验 |
| 443 | TCP | `0.0.0.0/0` | 站点访问 |

**绝对不要放行 5432 / 6379 / 9000 / 9001 / 8080 / 3000。**

3. 域名添加 A 记录：`@`（或 `quiz`）→ 服务器公网 IP，详细步骤与代理开关的取舍见第 3.4 节；
4. 先在本地 `nslookup stonev2ray.top 8.8.8.8` 确认解析生效再申请证书。

### 3.3 服务器初始化（一次性）

```bash
# ---- 以 root 执行 ----
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
systemctl restart ssh

timedatectl set-timezone Asia/Shanghai

# 2～4G 内存建议加 swap，给构建和高峰留缓冲
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 安装 Docker（阿里云官方源）
apt-get update && apt-get install -y ca-certificates curl git
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc && chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://mirrors.aliyun.com/docker-ce/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  > /etc/apt/sources.list.d/docker.list
apt-get update && apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

# 配置 Docker 日志与镜像加速（避免日志吃满系统盘、拉镜像慢）
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'JSON'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "5" },
  "registry-mirrors": ["https://<你的专属加速地址>.mirror.aliyuncs.com"]
}
JSON
systemctl enable --now docker && systemctl restart docker

# 部署用户
useradd -m -s /bin/bash deploy && usermod -aG docker deploy
mkdir -p /opt/smart-quiz && chown -R deploy:deploy /opt/smart-quiz
```

> `registry-mirrors` 的专有地址在**容器镜像服务 ACR → 镜像加速器**页面获取。

### 3.4 域名接入（NameSilo 注册 + Cloudflare 托管）

当前状态（已核实）：域名 `stonev2ray.top` 在 NameSilo 注册，NS 已经委托给 Cloudflare
（`neil.ns.cloudflare.com` / `uma.ns.cloudflare.com`），但还没有任何 A 记录。

**第 1 步：补一条 A 记录**

Cloudflare 控制台 → 选择 `stonev2ray.top` → DNS → Records → Add record：

| 字段 | 值 |
| --- | --- |
| Type | A |
| Name | `@`（用顶级域名）或 `quiz`（用子域名 `quiz.stonev2ray.top`） |
| IPv4 address | 你的新加坡服务器公网 IP |
| Proxy status | **DNS only（灰云）** ← 见下 |
| TTL | Auto |

**第 2 步：代理状态怎么选（这一步选错会踩坑）**

| 选项 | 优点 | 代价 |
| --- | --- | --- |
| **DNS only（灰云，推荐）** | 直连新加坡节点，延迟最低；Let's Encrypt 证书正常签发；没有额外超时限制 | 源站 IP 暴露 |
| Proxied（橙云） | 隐藏源站 IP，自带基础攻击防护 | Cloudflare 免费版**源站响应超时是 100 秒**，而本项目的 AI 切题/整卷批改、SSE 流式问答都可能超过 100 秒，会被直接掐断（524）；另外必须把 SSL/TLS 模式设成 **Full (strict)** 并给源站装可信证书，否则 http↔https 会重定向死循环 |

结论：**先用灰云**。项目里 `/api/` 的超时是 600 秒，就是为了长耗时 AI 请求准备的，
套上 Cloudflare 代理反而会削掉这个能力。等确实需要隐藏源站时再评估。

**第 3 步：确认解析生效**

```bash
# 本机执行，应返回服务器公网 IP
nslookup stonev2ray.top 8.8.8.8
dig +short stonev2ray.top @1.1.1.1
```

**两个容易忽略的点**：

1. NameSilo 注册后会发一封 ICANN 注册人验证邮件，**15 天内不点确认域名会被暂停解析**。
   如果没收到，去 NameSilo 控制台重新触发。
2. 这个域名如果以后还要兼作代理/科学上网用途，注意两点：一是用**子域名**把两者分开
   （例如应用用 `quiz.stonev2ray.top`，代理用别的记录），二是这类域名有被墙的风险，
   一旦被墙会连带影响应用访问。应用侧建议保住一个独立域名或独立子域。

### 3.5 443 已被 Xray 占用时：SNI 分流共存

服务器上如果已经有 Xray / V2Ray 节点占了 443（本机情况就是这样：证书是通配符
`*.stonev2ray.top`，客户端 SNI 是 `sto1.stonev2ray.top`），不要硬抢端口，用 SNI 分流共存。

**完整操作手册见 [`deploy/sni-split/README.md`](../../deploy/sni-split/README.md)**，要点：

- 分流器是独立于应用栈的 Docker 项目（`network_mode: host`），应用发版不会影响代理；
- 443 由分流器接管，按 SNI 精确匹配 `quiz.stonev2ray.top` 走应用，其余原样回 Xray；
- 应用网关改为只绑定回环 `127.0.0.1:8443`（HTTP 是 `127.0.0.1:8080`），不再直接占 80/443；
- 迁移分两步：先在 9443 上干跑验证，再切换 443，切换窗口只有几秒，回滚是一条命令。

证书可以直接复用面板那张通配符证书（`*.stonev2ray.top` 覆盖 `quiz` 子域），
在 `deploy/env.prod` 里把 `TLS_CERT_FILE` / `TLS_KEY_FILE` 指向 `/opt/certs/` 即可。

## 4. 需要改动的代码与配置（逐条核查结果）

以下问题都是我在仓库里实际核对出来的，按严重程度排序。

### 4.1 【阻断】容器重启不自恢复

`docker-compose.yml` 与 `docker-compose.dev.yml` 的所有服务都**没有 `restart` 策略**，
服务器重启或 docker 守护进程重启后容器不会自动起来。
→ 已在新写的 `docker-compose.prod.yml` 中统一加 `restart: unless-stopped`。

### 4.2 【阻断】依赖端口直接发布到公网

`docker-compose.dev.yml` 把 PostgreSQL `5432`、Redis `6379`、RustFS `9000/9001`
直接映射到宿主机。在公网上这等于把数据库、缓存、对象存储裸奔（Redis 默认无密码，
PostgreSQL 弱口令可爆破）。
→ `docker-compose.prod.yml` 中这些服务**不写 `ports`**，只挂在 `internal` 网络里。

### 4.3 【阻断】生产编排用的是 MinIO 且默认弱口令 + 公共桶

`docker-compose.yml` 里对象存储是 MinIO，账号密码写死 `minioadmin/minioadmin`，
`createbuckets` 还执行了 `mc anonymous set public`（桶匿名可读）。
而应用默认配置（`.env.example`、`application.yml`）用的是 **RustFS**，两套不一致。
→ 生产统一为 RustFS + `.env.prod` 里的强随机凭证；桶保持私有（应用下载走
`s3Client.getObjectAsBytes`，见 `FileStorageService`，不需要公共读）。

### 4.4 【阻断】试卷原件下载用的是内部存储直链

`FileStorageService.getFileUrl()`（`infrastructure/file/FileStorageService.java:197`）返回
`<endpoint>/<bucket>/<key>`，被存进 `practice_papers.storage_url`；
前端 `frontend/src/components/HistoryList.tsx:181` 直接把它塞进 `<a href>` 下载。

- 本地：`http://localhost:9000/...` —— 浏览器刚好能连上，所以一直没暴露问题；
- 生产：会变成 `http://rustfs:9000/...` —— **浏览器根本无法解析这个主机名**，下载必然失败。

**修法（推荐，与知识库一致）**：知识库已有后端下载接口
`GET /api/knowledgebase/{id}/download`（`KnowledgeBaseController.java:152`），
前端也走的是 `knowledgeBaseApi.downloadKnowledgeBase`。给试卷补一个同样的：

```java
// ResumeController，与 export/delete 并列
@GetMapping("/api/resumes/{id}/download")
public ResponseEntity<byte[]> downloadResume(@PathVariable Long id) {
    var result = historyService.downloadOriginal(id);   // 内部：storageService.downloadFile(key)
    byte[] content = result.fileBytes();
    String encoded = URLEncoder.encode(result.filename(), StandardCharsets.UTF_8)
            .replaceAll("\\+", "%20");
    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION,
                    "attachment; filename=\"" + encoded + "\"; filename*=UTF-8''" + encoded)
            .contentType(MediaType.APPLICATION_OCTET_STREAM)
            .body(content);
}
```

前端把 `HistoryList.tsx` 的 `handleDownload` 改成
`request.download('/api/resumes/' + resume.id + '/download')` 后触发保存。

> 这样改之后，历史数据里那些 `http://localhost:9000/...` 的 `storage_url`
> 就不需要做数据订正了（前端不再读它）。
>
> 另一种做法是给 S3 预签名 URL 并让网关反代 RustFS，但会额外增加一条公网暴露面，
> 在还没做鉴权的当前阶段不建议。

### 4.5 【重要】流式问答经过 nginx 会被缓冲

`frontend/nginx.conf` 的 `/api/` 段落没有关闭 `proxy_buffering`（只有 `/ws/` 关了）。
而 `KnowledgeBaseQueryPage` 与 RAG 问答用的是 fetch 流式读取
（`frontend/src/api/stream.ts` → `/api/rag-chat/.../messages/stream`、
`/api/knowledgebase/query/stream`）。nginx 默认缓冲会把分片攒起来，
用户看到的就是"卡很久然后一次性吐出来"。

在 `frontend/nginx.conf` 的 `location /api/` **之前**插入：

```nginx
    # 流式接口：关闭缓冲，保证逐字输出
    location ~ ^/api/(knowledgebase/query/stream|rag-chat/sessions/[^/]+/messages/stream)$ {
        proxy_pass http://app:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 透传边缘网关的协议，避免被容器内的 $scheme(http) 覆盖
        proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
```

（`docker-compose.prod.yml` 用的边缘网关已经对 `/api/` 关闭了缓冲；两层都关才彻底。）

### 4.6 【重要】WebSocket 的 Origin 校验依赖环境变量

`WebSocketConfig`（`modules/voiceinterview/config/WebSocketConfig.java:26`）用
`corsProperties.getAllowedOrigins()` 作为 `setAllowedOrigins`。默认值是
`http://localhost:3000,...`（`application.yml` 的 `app.cors.allowed-origins`；本地开发默认端口是 3000，旧版是 5173）。
生产必须设成：

```
CORS_ALLOWED_ORIGINS=https://stonev2ray.top
```

否则**口语练习的 WebSocket 握手会被直接拒绝**。
另注意：语音录制依赖浏览器的 `getUserMedia`，**必须是 HTTPS**，所以证书不是可选项。

### 4.7 【重要】JVM 没有内存上限

`app/Dockerfile` 的 `ENTRYPOINT ["java", "-jar", "app.jar"]` 没有内存参数，
容器看到的又是宿主全部内存，JVM 会按整机比例吃内存，容易把 PostgreSQL 挤死。
→ `docker-compose.prod.yml` 通过 `JAVA_TOOL_OPTIONS` 注入
`-XX:MaxRAMPercentage=60 -XX:+ExitOnOutOfMemoryError`，**不需要改 Dockerfile**。

### 4.8 【重要】Redis 的定位不只是缓存

Redis 同时承载 `@RateLimit` 计数和 Redis Stream 异步队列（向量化、切题）。
默认 RDB 快照在异常宕机时可能丢最近数据，任务就永久卡在 `pending`。
→ 生产开启 AOF（`--appendonly yes --appendfsync everysec`），淘汰策略用
`noeviction`。**不要**用 `allkeys-lru`，那会把待处理任务直接淘汰掉。

另外注意 `docs/改造说明.md` 的已知坑：应用运行时**不要 `FLUSHDB`**，否则消费组被删，
消费者会刷 `NOGROUP`。

### 4.9 【重要】运行时 Provider 配置目录没有挂卷

`application.yml` 中 `app.ai.config-yaml-path` 默认写到
`${user.home}/.smart-quiz-platform/llm-providers.yml`（容器内是 `/root/...`）。
不挂卷的话，容器重建后运行时配置的模型 Provider 与加密 API Key 就丢了。
→ `docker-compose.prod.yml` 挂载命名卷 `app_config:/root/.smart-quiz-platform`。

同时：`APP_AI_CONFIG_ENCRYPTION_KEY` **一旦上线就不能再改**，改了已存的密钥无法解密。
建议把它和 `.env.prod` 一起放进密码管理器备份。

### 4.10 【一般】上传临时目录在容器内

`app.resume.upload-dir` 指向 `${java.io.tmpdir}/smart-quiz-platform/resumes`。
容器内 `/tmp` 默认随容器生命周期。原件本身在 RustFS 里，但解析中途重启会丢临时文件。
→ 挂卷 `app_tmp:/tmp/smart-quiz-platform`（已包含在编排里）。

### 4.11 【一般】容器日志无限增长

Docker 默认 `json-file` 日志不限制大小，后端日志 + nginx access log 长期堆积会吃满系统盘。
→ `docker-compose.prod.yml` 统一 `max-size: 50m, max-file: 5`（已在
`/etc/docker/daemon.json` 里再加一层兜底）。

### 4.12 【合规】AGPL-3.0

`README.md:404` 与 `docs/交接说明.md:178` 都写明：本项目以 **AGPL-3.0** 发布，
若基于它部署公开可访问的网络服务，**必须向使用者提供完整源码**。
如果站点对外公开，请在页脚加源码地址。

### 6.3 第三步：填写 `deploy/env.prod`

必填项如下，其余保持模板默认即可：

| 变量 | 说明 |
| --- | --- |
| `DOMAIN` | 只写主机名，如 `stonev2ray.top`（不要带 `https://`） |
| `POSTGRES_PASSWORD` | 强随机，≥ 24 位 |
| `APP_STORAGE_ACCESS_KEY` / `APP_STORAGE_SECRET_KEY` / `RUSTFS_RPC_SECRET` | 三组独立随机值 |
| `AI_BAILIAN_API_KEY` | 百炼 API Key |
| `APP_AI_CONFIG_ENCRYPTION_KEY` | 强随机；**上线后不可更改** |

> 一旦拿到域名，再按第 6.5 节申请证书。此时记得把
> `APP_AUTH_COOKIE_SECURE` 改回 `true`、`CORS_ALLOWED_ORIGINS` 改成 https 域名。

### 6.4 第四步：启动服务


**此时 `https://DOMAIN` 还打不开**——证书还没签发，nginx 会因找不到证书文件而启动失败，
这是预期现象。先做下一步。

### 6.5 第五步：签发证书

```bash
cd /opt/smart-quiz

# 0) 确保 gateway 没有占着 80 端口（首次部署时它本来就在崩溃重启）
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod stop gateway || true

# 1) 首次签发：standalone 模式（直接占用 80 端口完成 HTTP-01 校验）
mkdir -p deploy/certbot/conf deploy/certbot/www
docker run --rm -p 80:80 \
  -v "$PWD/deploy/certbot/conf:/etc/letsencrypt" \
  certbot/certbot certonly --standalone \
  -d stonev2ray.top \
  --email you@example.com --agree-tos --no-eff-email \
  --cert-name stonev2ray.top

# 2) 证书就绪后启动全部服务
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod up -d

# 3) 校验
curl -I https://stonev2ray.top
```

**为什么首次必须用 standalone**：证书文件不存在时，nginx 加载 `ssl_certificate` 会直接
报错退出，所以"先起 nginx 再用 webroot 签"这条路在首次部署时走不通。
签发完成后，`deploy/certbot/www` 已经是 gateway 的 webroot 挂载点，
后续**续期**走的就是 webroot（不需要再占用端口、不需要停服）。

**替代方案**：在阿里云**数字证书管理服务**申请免费 DV 证书（当前有效期 3 个月，
需定期更换），下载 nginx 格式后放到 `deploy/certbot/conf/live/<域名>/`
（`fullchain.pem` + `privkey.pem`），把 `certbot` 服务停掉即可。

**续期后自动 reload**：`certbot` 容器每 12 小时尝试续期并写入共享卷，
nginx 需要重新加载才能读到新证书。在宿主机加一条 cron：

```bash
sudo crontab -e
# 每天 03:30 重新加载网关（证书未更新时 reload 也无副作用）
30 3 * * * cd /opt/smart-quiz && docker compose -f docker-compose.prod.yml --env-file deploy/env.prod exec -T gateway nginx -s reload >/dev/null 2>&1
```

## 7. 把本地数据迁移到云端（可选）

如果你希望线上沿用本地已有的试卷和资料：

```bash
# ---- 本地：导出数据库 ----
docker exec smart-quiz-postgres pg_dump -U postgres -Fc -d smart-quiz > smart-quiz.dump

# ---- 上传到服务器后：导入 ----
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod cp \
  smart-quiz.dump postgres:/tmp/smart-quiz.dump
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod exec -T postgres \
  pg_restore -U postgres -d smart-quiz --clean --if-exists /tmp/smart-quiz.dump
```

**注意**：

1. 导入前先让线上库处于"刚初始化"状态，或备份后再 `--clean` 覆盖；
2. `vector_store` 表的向量数据会一起带过去，需要 `vector` 扩展已存在
   （`docker/postgres/init.sql` 已在首次启动时创建）；
3. 对象存储文件需要单独搬：

```bash
# 本地导出 RustFS 卷数据
docker run --rm -v smart_quiz_platform_rustfs_data:/data -v "$PWD:/out" alpine \
  tar czf /out/rustfs-data.tar.gz -C /data .

# 服务器导入（先停 app，避免读写冲突）
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod stop app
docker run --rm -v smart-quiz-prod_rustfs_data:/data -v "$PWD:/in" alpine \
  sh -c 'rm -rf /data/* && tar xzf /in/rustfs-data.tar.gz -C /data'
docker compose -f docker-compose.prod.yml --env-file deploy/env.prod start app
```

4. **Redis 不用迁移**：Stream 里的任务重新触发一次即可（重新上传/重新向量化）。
   迁移时千万不要 `FLUSHDB` 到正在运行的生产实例上。

> 卷名前缀为 Compose 项目名（`docker-compose.prod.yml` 里是 `name: smart-quiz-prod`），
> 用 `docker volume ls` 确认实际名称再操作。
